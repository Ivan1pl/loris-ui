# Component Model & Backend Extension

### Marker Interfaces and Abstract Base Classes
Toolkit-neutral abstractions in `api` are empty marker interfaces (`Component`, `Style`, `Font`), as is the opaque `StyleApplier.Styles` token in `imgui`; backends downcast to their concrete type (e.g. `(ImGuiFont) component.getFont()`).
Use abstract classes for shared behaviour / template methods (`Renderer`, `LorisScreen`, `ImGuiBackend`, `Panel.BaseBuilder`); use interfaces for stateless contracts (`RendererProvider`, `StyleApplier`, `BundleKeyResolver`) and for the `Backend` port, whose implementations also hold its settings (`ImGuiBackend` stores them in `public final` methods).

### Toolkit-Neutral `Backend` Port
`Backend` declares `render(int w, int h, List<Component> components, BundleKeyResolver bundleKeyResolver)` plus the keyboard-navigation settings as JavaBean pairs: `ActivationKey getActivationKey()` / `setActivationKey(ActivationKey)` (`requireNonNull`; the `api` enum, `ENTER` including keypad Enter, or `SPACE`) and `boolean isKeyboardNavigationEnabled()` / `setKeyboardNavigationEnabled(boolean)`. Settings on the port are toolkit-neutral values (an `api` enum, not a Dear ImGui key) whose behavior `Backend`'s Javadoc describes without naming the toolkit; `ImGuiBackend` implements them as `public final` with the defaults `ENTER` and enabled. Toolkit concerns stay in the backend module:
- **Textures** belong to each `ImGuiBackend` instance. Renderers load and draw them only through the `RendererProvider` they receive: `TextureData loadTexture(String resourcePath)`, `TextureData loadTexture(String resourcePath, Color maskedR, Color maskedG, Color maskedB)` (both `throws IOException`, cached per backend with keys normalized to class-path style, failures not cached), `TextureData loadTexture(Canvas canvas)` (no checked exception) and `renderTexture(long id, ImageMode imageMode, int width, int height, int textureWidth, int textureHeight)`. `ImGuiBackend` implements the three `loadTexture` methods as `public final` on top of its graphics-API hooks `protected abstract TextureData createTexture(String resourcePath, Color maskedR, Color maskedG, Color maskedB) throws IOException` (called on a cache miss with the normalized path, no leading `/`), `protected abstract TextureData createCanvasTexture(int width, int height, ByteBuffer rgbaPixels)` and `protected abstract void updateCanvasTexture(TextureData texture, int x, int y, int width, int height, ByteBuffer rgbaPixels)` (tightly packed RGBA rows, top row first, in a backend-owned direct scratch buffer the hook must not keep; the texture is UNORM and sampled nearest-neighbor where the renderer variant allows it, clamped to the edge) and `protected abstract void deleteTexture(TextureData texture)` (the four hooks are implemented by the four final backends, one per graphics API: `ImGuiOpenGlBackend` for OpenGL texture names, `ImGuiOpenGlEsBackend` for OpenGL ES texture names, `ImGuiSdlGpuBackend` for `SDL_GPUTexture*` handles and `ImGuiVulkanBackend` for `VkDescriptorSet` handles; a custom subclass implements all four). Canvas textures are per backend and per canvas (an identity map): the first load creates the texture from the whole image, later loads upload only the canvas's changed rectangle (`Canvas.takePixelUpdate`), a failed update makes the next load upload the whole image, and an outermost `render` first deletes the textures of canvases not drawn since the previous outermost `render` (so it assumes one outermost `render` per frame, and an override of `render` calls `super.render`). `public final unloadTextures()` releases every texture, canvas textures included, and throws `IllegalStateException` while the backend is drawing; renderer teardown calls it. The `TextureData(long id, int width, int height)` record lives in `imgui.backend`; its `id` is the backend-specific handle.
- **Input capture** is exposed to hosts by the sealed `ImGuiRenderer`, so by every variant (`wantsMouseInput()`, `wantsKeyboardInput()`, `isHoveringScrollablePanel()`), never by the API. `isHoveringScrollablePanel()` (the flag `ImGuiState.hoveringScrollableWindow`) covers scrollable top-level panels and enabled canvases that take input, so hosts withhold the wheel from the game over both without code of their own; a canvas never adds to `wantsKeyboardInput()`, because it takes no keyboard focus and makes no Dear ImGui item active. `wantsKeyboardInput()` includes the keyboard-focus capture (Dear ImGui's `WantCaptureKeyboard` ORed, while navigation is enabled, with the state `KeyboardFocus` committed for the last completed frame), so hosts need no code of their own for the capture itself. Because the capture switches while keys are held, every host decides a key's release by the key's own key-downs, never by the capture at the moment of release: the release reaches the application exactly when the key's press or a repeat of the same hold reached it, so the application sees neither a key stuck down nor a release it never saw pressed (a package-private, native-free `DeliveredKeys` per host module, keyed by the host's physical-key identity: jME key code, SDL scancode, GLFW key token or `~scancode` for keys without one). Only the release of a key with no recorded key-down, and everything else, follows the capture. Capture and queued Tab moves are per frame, so hosts render every frame while forwarding events, or turn navigation off or close the display while the UI is hidden.
- **Keyboard focus** is owned by `ImGuiRenderer`: one internal, native-free `imgui.impl.KeyboardFocus` per renderer, begun and committed around `screen.render` and published to the renderers only during that call through `ImGuiState.keyboardFocus` (`null` when navigation is off, so "off" is the renderers' plain path). How keys are read stays in the variants: none of them forwards a Tab event to Dear ImGui (no Ctrl+Tab windowing; `NavEnableKeyboard` stays off), and a Tab press or repeat without Ctrl, Alt or Super queues a focus move through the package-private `divertTab(TabKeyFilter.Result)`, the one place that maps a classification to a move. Only the built-in renderers take part; there is no focus SPI for custom components. SDL text input is not a host concern: the four SDL variants start it on their window while Dear ImGui wants text input, and stop it when it no longer does and on `dispose()` (through the package-private `SdlTextInput`), so hosts and applications must not start or stop it for the same window; GLFW always delivers characters.
- **Fonts** are registered with `ImGuiRenderer` (or through a host display) and returned as `ImGuiFont` handles in the `com.ivan1pl.lorisui.imgui` package.

Do not add toolkit-specific methods or types to `Backend`.

### Hosts Pass the Logical Window Size
Every host passes the platform's logical window size (window coordinates as reported by `SDL_GetWindowSize` for SDL3 windows or `glfwGetWindowSize` for GLFW windows, never framebuffer pixels such as `glfwGetFramebufferSize`) to the renderer variant's `render` on every frame; Dear ImGui's SDL3 or GLFW platform backend applies the HiDPI framebuffer scale. On Windows and X11, GLFW measures windows in pixels, so the GLFW size equals the framebuffer size and the UI is not scaled up on HiDPI monitors (documented, not fixed). The same `w` / `h` are the screen size that position, size and content functions receive.
- `ImGuiJmeDisplay` queries `SDLVideo.SDL_GetWindowSize` on its window handle each frame in `drawCurrentScreen()`, inside a `MemoryStack` frame closed before rendering, and throws `IllegalStateException` with `SDLError.SDL_GetError()` when the query fails.
- `ImGuiLwjglSdlGl3Display.render(width, height)`, `ImGuiLwjglSdlGpuDisplay.render(width, height, commandBuffer, targetTexture)` and `ImGuiLwjglSdlVulkanDisplay.render(width, height, commandBuffer, targetImageView)` take the size the application reads with `SDL_GetWindowSize`. The Vulkan renderer draws over the window's pixel size (`SDL_GetWindowSizeInPixels`, the draw data's framebuffer size), so its target image must be at least that large; while the swapchain extent is smaller, the application passes `targetImageView = 0` (the UI updates, nothing is drawn).
- `ImGuiLwjglGlfwGl3Display.render(width, height)` takes the size the application reads with `glfwGetWindowSize`.
- Never size the UI from the jME camera, the viewport or `SceneProcessor.reshape`; those are framebuffer pixels on HiDPI displays. A new host (and the planned neutral host SPI) follows the same contract.

```java
try (MemoryStack stack = MemoryStack.stackPush()) {
    IntBuffer widthBuffer = stack.mallocInt(1);
    IntBuffer heightBuffer = stack.mallocInt(1);
    if (!SDLVideo.SDL_GetWindowSize(window.getWindowHandle(), widthBuffer, heightBuffer)) {
        throw new IllegalStateException("Could not read the window size: " + SDLError.SDL_GetError());
    }
    width = widthBuffer.get(0);
    height = heightBuffer.get(0);
}
```

### Hosts Provide an sRGB Framebuffer
Image textures are sRGB on every backend (`GL_SRGB_ALPHA` in `ImGuiOpenGlBackend`, `GL_SRGB8_ALPHA8` in `ImGuiOpenGlEsBackend`, because OpenGL ES 3.0 rejects the unsized format, `R8G8B8A8_UNORM_SRGB` in `ImGuiSdlGpuBackend`, `R8G8B8A8_SRGB` in `ImGuiVulkanBackend`) and the Dear ImGui font atlas is UNORM on every variant, so every host must write through an sRGB framebuffer for all variants to look the same:
- GL3 hosts: an sRGB-capable default framebuffer (`SDL_GL_FRAMEBUFFER_SRGB_CAPABLE` or `GLFW_SRGB_CAPABLE`) with `GL_FRAMEBUFFER_SRGB` enabled.
- jME: gamma correction, which is on by default, for both renderers (OpenGL 3 and OpenGL ES 3 through ANGLE).
- SDL_GPU: the `SDL_GPU_SWAPCHAINCOMPOSITION_SDR_LINEAR` swapchain, set by the application before `initialize()`; check `SDL_WindowSupportsGPUSwapchainComposition` first and fail with a clear message when it is unsupported.
- Vulkan: an sRGB swapchain format (`VK_FORMAT_B8G8R8A8_SRGB` or `VK_FORMAT_R8G8B8A8_SRGB` with `VK_COLOR_SPACE_SRGB_NONLINEAR_KHR`), passed as the colour-attachment format (the example fails with a clear message when the surface supports neither).

Canvas textures are the one exception: they are UNORM on every backend (`GL_RGBA8` on OpenGL and OpenGL ES, `R8G8B8A8_UNORM` on SDL_GPU and Vulkan), so canvas pixels are stored like the font atlas and vertex colors and match widget colors through the same sRGB framebuffer (the same bytes in an sRGB `Image` file look different).

A new host documents this requirement in its Javadoc, as the bundled hosts do.

### Class-Keyed Renderer and StyleApplier Registry
Each `api` Component has exactly one `Renderer` and each `Style` exactly one `StyleApplier`, registered by class in the `ImGuiBackend` constructor (written directly to the maps, so the constructor calls no overridable method). Lookup (`getRenderer` / `getStyleApplier`, both `public final`) walks the superclass chain, so subclasses (Button, Popup, ModalPopup) reuse their parent's renderer unless registered explicitly. The built-ins are Panel, Text, Image, TextInput, NumberInput, Spacer, ComboBox, ProgressBar, TabbedPanel and Canvas (`CanvasRenderer`). A missing registration fails fast with `IllegalStateException`.
- New component: class with Builder in `api/component` + `imgui/renderer/impl/<Name>Renderer` (no-argument constructor) + one `renderers.put(...)` line.
- New style: class in `api/component/style` + `imgui/renderer/style/impl/<Name>Applier` + one `styleAppliers.put(...)` line.

```java
renderers.put(ProgressBar.class, new ProgressBarRenderer());
renderers.put(Canvas.class, new CanvasRenderer());
styleAppliers.put(TextInputStyle.class, new TextInputStyleApplier());
```

### Custom Components and Styles Through Registration
Library users plug in their own components and styles by registering a `Renderer` / `StyleApplier`, never by subclassing the backend:
- **On a backend**: `ImGuiBackend.registerRenderer(Class<ComponentType>, Renderer<? super ComponentType>)` and `registerStyleApplier(Class<StyleType>, StyleApplier<? super StyleType>)`, both `public final`. A registration replaces any existing mapping, including a built-in one, and takes effect from the next lookup; subclasses without their own mapping use the nearest registered ancestor. Null arguments throw `NullPointerException`; an interface class throws `IllegalArgumentException`, because lookup walks only the superclass chain. Not gated by lifecycle; UI thread only.
- **On a display**: `ImGuiJmeDisplay`, `ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay` and `ImGuiLwjglSdlVulkanDisplay` offer the same two methods (the LWJGL displays inherit them from their package-private base), delegating to their private backend. They throw `IllegalStateException` while the display is initialized or unusable (jME: failed initialization; LWJGL: closed). Registrations persist across jME re-attach.
- **Keyboard-navigation passthroughs**: `ImGuiRenderer` and the five displays (the LWJGL displays again through their base) offer `setActivationKey(ActivationKey)` and `setKeyboardNavigationEnabled(boolean)`, delegating to the backend. Unlike registration they are not gated by state: they work in any state (before initialization, attached, after a failed initialization or `close()`) and take effect from the next key event or frame (disabling ends the navigation capture at once and clears the focus from the next frame drawn while disabled). Navigation is on by default; screens where Tab or other keys belong to the game (gameplay HUDs) turn it off, which the setter Javadoc says. There are no getters on the renderer or displays.
- **Generic component types** need an unchecked class cast, kept to the narrowest scope: `(Class<ComboBox<String>>) (Class<?>) ComboBox.class`.
- Custom renderers load and draw textures through their `RendererProvider`, and apply fonts with `((ImGuiFont) font).useFont(...)`.
- imgui-java is only a runtime dependency of `loris-ui-imgui`, so code with a custom `Renderer` adds imgui-java to its own build and, on the module path, `requires imgui.binding`.
- Subclass `ImGuiBackend` (implementing the four hooks `createTexture`, `deleteTexture`, `createCanvasTexture` and `updateCanvasTexture`) only for different texture handling on OpenGL or OpenGL ES, for example other texture loading; such a backend pairs only with the GL3 or GLES3 renderers (`ImGuiSdlGl3Renderer`, `ImGuiGlfwGl3Renderer`, `ImGuiSdlGles3Renderer`), because its textures must be texture names of the renderer's OpenGL or OpenGL ES context. The SDL_GPU and Vulkan renderers take their own typed backend (`ImGuiSdlGpuBackend`, `ImGuiVulkanBackend`). A new graphics API needs a new variant of the sealed `ImGuiRenderer` and its own final backend inside `lorisui.imgui` (one final backend per graphics API), which is not an extension point. All four concrete backends are final, and each bundled display uses its own backend: the jME display `ImGuiOpenGlBackend` or `ImGuiOpenGlEsBackend`, chosen with the renderer variant from jME's renderer setting; the two GL3 displays `ImGuiOpenGlBackend`; the SDL_GPU display `ImGuiSdlGpuBackend`; the Vulkan display `ImGuiVulkanBackend`.
- **One backend per renderer**: an `ImGuiBackend` instance belongs to exactly one `ImGuiRenderer` (one Dear ImGui context) and is never shared between renderers, because its renderers keep cross-frame input state keyed by ImGui ID (button presses and hovers, canvas gestures); a shared backend loses clicks. Likewise a `Canvas` is drawn by one backend only, because the backend that uploads its changed pixels takes them from the canvas. A shared backend would also share one navigation switch and activation key between the renderers. `ImGuiBackend`'s Javadoc states this (re-initializing the same renderer with its backend is fine).

```java
ImGuiJmeDisplay display = new ImGuiJmeDisplay(context, inputManager, guiViewPort);
display.registerRenderer(Gauge.class, new GaugeRenderer());
display.registerStyleApplier(GaugeStyle.class, new GaugeStyleApplier());
```

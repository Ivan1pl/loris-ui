# Component Model & Backend Extension

### Marker Interfaces and Abstract Base Classes
Toolkit-neutral abstractions in `api` are empty marker interfaces (`Component`, `Style`, `Font`), as is the opaque `StyleApplier.Styles` token in `imgui`; backends downcast to their concrete type (e.g. `(ImGuiFont) component.getFont()`). The exception is a behavioral interface that extends a marker and states a contract between applications and backends without naming the toolkit (e.g. `Focusable extends Component`): it carries no toolkit types, documents its backend-called methods as such and states the threading contract of every method, including any race it accepts (e.g. a request lost when renewed from another thread while the backend clears it), is implemented by the built-in components through a package-private holder, and follows the backend-consumed request pattern (see `components/builders.md`). Implementing it on a custom component does nothing unless a backend supports it.
Use abstract classes for shared behaviour / template methods (`Renderer`, `LorisScreen`, `ImGuiBackend`, `Panel.BaseBuilder`); use interfaces for stateless contracts (`RendererProvider`, `StyleApplier`, `BundleKeyResolver`) and for the `Backend` port, whose implementations also hold its settings.

### Toolkit-Neutral `Backend` Port
`Backend` declares `render(int w, int h, List<Component> components, BundleKeyResolver bundleKeyResolver)` plus the keyboard-navigation settings as JavaBean getter/setter pairs (`ActivationKey`, the navigation switch). Settings on the port are toolkit-neutral values (an `api` enum, never a Dear ImGui key) whose behavior `Backend`'s Javadoc describes without naming the toolkit; `ImGuiBackend` implements them as `public final`. Do not add toolkit-specific methods or types to `Backend`. Toolkit concerns stay in the backend module:
- **Textures** belong to each `ImGuiBackend` instance. Renderers load and draw them only through the `RendererProvider` they receive (`loadTexture(...)` for resources and canvases, `renderTexture(long id, ...)`). `ImGuiBackend` implements the `loadTexture` methods and `unloadTextures()` as `public final` on top of four graphics-API hooks (`createTexture`, `deleteTexture`, `createCanvasTexture`, `updateCanvasTexture`), whose contracts are in their Javadoc; a subclass implements all four. An override of `render` calls `super.render`, and each frame draws the UI with one outermost `render` (canvas texture eviction depends on it). The `TextureData(long id, int width, int height)` record lives in `imgui.backend`; its `id` is the backend-specific handle.
- **Input capture** is exposed to hosts by the sealed `ImGuiRenderer` (`wantsMouseInput()`, `wantsKeyboardInput()`, `isHoveringScrollablePanel()`), never by the API. The queries include everything LorisUI captures (scrollable panels and enabled canvases for the wheel, the keyboard-focus capture for keys), so hosts add no capture logic of their own.
- **Key releases in hosts** follow the key's own key-downs, never the capture at the moment of release: a release reaches the application exactly when that hold's press or repeat reached it (e.g. the per-host `DeliveredKeys`). Capture and queued Tab moves are per frame, so hosts render every frame while forwarding events, or turn navigation off or close the display while the UI is hidden.
- **Keyboard focus** is owned by `ImGuiRenderer` (one native-free `imgui.impl.KeyboardFocus` per renderer, published to renderers through `ImGuiState` only during `screen.render`; see `components/renderers-and-styles.md`). The navigation switch gates only LorisUI's navigation keys and their capture; focus tracking, the `isFocused()` write-back and focus requests always run. No variant forwards Tab to Dear ImGui; Tab presses are mapped to focus moves in one place (`divertTab`). Only the built-in renderers register with `KeyboardFocus`, so a custom `Focusable` component is not focusable.
- **SDL text input** is owned by the SDL renderer variants (`SdlTextInput`); hosts and applications never start or stop it for the same window.
- **Fonts** are registered with `ImGuiRenderer` (or through a host display) and returned as `ImGuiFont` handles in the `com.ivan1pl.lorisui.imgui` package.

### Hosts Pass the Logical Window Size
Every host passes the platform's logical window size (window coordinates as reported by `SDL_GetWindowSize` or `glfwGetWindowSize`, never framebuffer pixels such as `glfwGetFramebufferSize`) to the renderer variant's `render` on every frame; Dear ImGui's platform backend applies the HiDPI framebuffer scale. The same `w` / `h` are the screen size that position, size and content functions receive. Never size the UI from the jME camera, the viewport or `SceneProcessor.reshape`; those are framebuffer pixels on HiDPI displays. A new host (and the planned neutral host SPI) follows the same contract and documents it in its Javadoc, as the bundled displays do (including the Vulkan display's target-`0` rule while the swapchain is smaller than the window's pixel size).

### Hosts Provide an sRGB Framebuffer
Image textures are sRGB on every backend and the Dear ImGui font atlas is UNORM, so every host must write through an sRGB framebuffer for all variants to look the same (GL3: an sRGB-capable default framebuffer with `GL_FRAMEBUFFER_SRGB`; jME: gamma correction; SDL_GPU: the `SDR_LINEAR` swapchain composition, checked for support first; Vulkan: an sRGB swapchain format passed as the colour-attachment format). Canvas textures are the one exception: they are UNORM on every backend, so canvas pixels match widget colors. A new host documents this requirement in its Javadoc, as the bundled hosts do.

### Class-Keyed Renderer and StyleApplier Registry
Each `api` Component has exactly one `Renderer` and each `Style` exactly one `StyleApplier`, registered by class in the `ImGuiBackend` constructor (written directly to the maps, so the constructor calls no overridable method). Lookup (`getRenderer` / `getStyleApplier`, both `public final`) walks the superclass chain, so subclasses (Button, Popup, ModalPopup) reuse their parent's renderer unless registered explicitly. A missing registration fails fast with `IllegalStateException`.
- New component: class with Builder in `api/component` + `imgui/renderer/impl/<Name>Renderer` (no-argument constructor) + one `renderers.put(...)` line.
- New style: class in `api/component/style` + `imgui/renderer/style/impl/<Name>Applier` + one `styleAppliers.put(...)` line.

```java
renderers.put(ProgressBar.class, new ProgressBarRenderer());
styleAppliers.put(TextInputStyle.class, new TextInputStyleApplier());
```

### Custom Components and Styles Through Registration
Library users plug in their own components and styles by registering a `Renderer` / `StyleApplier`, never by subclassing the backend:
- **On a backend**: `ImGuiBackend.registerRenderer(Class<ComponentType>, Renderer<? super ComponentType>)` and `registerStyleApplier(Class<StyleType>, StyleApplier<? super StyleType>)`, both `public final`. A registration replaces any existing mapping, including a built-in one. Null arguments throw `NullPointerException`; an interface class throws `IllegalArgumentException`, because lookup walks only the superclass chain. Not gated by lifecycle; UI thread only.
- **On a display**: every bundled display offers the same two methods, delegating to its private backend, and rejects them with `IllegalStateException` while initialized or unusable.
- **Keyboard-navigation passthroughs**: `ImGuiRenderer` and every display offer `setActivationKey(ActivationKey)` and `setKeyboardNavigationEnabled(boolean)`, delegating to the backend. Unlike registration they are not gated by state and take effect from the next key event or frame. The passthroughs are setters only: the settings are read through the `Backend` getters, so do not add getters to the renderer or displays. The setter Javadoc says that screens where Tab or other keys belong to the game turn navigation off.
- **Generic component types** need an unchecked class cast, kept to the narrowest scope: `(Class<ComboBox<String>>) (Class<?>) ComboBox.class`.
- Custom renderers load and draw textures through their `RendererProvider`, and apply fonts with `((ImGuiFont) font).useFont(...)`.
- imgui-java is only a runtime dependency of `loris-ui-imgui`, so code with a custom `Renderer` adds imgui-java to its own build and, on the module path, `requires imgui.binding`.
- Subclass `ImGuiBackend` (implementing the four texture hooks) only for different texture handling on OpenGL or OpenGL ES; such a backend pairs only with the GL3 or GLES3 renderers, because its textures must be texture names of the renderer's context. A new graphics API needs a new variant of the sealed `ImGuiRenderer` and its own final backend inside `lorisui.imgui` (one final backend per graphics API), which is not an extension point. Each bundled display uses its own backend.
- **One backend per renderer**: an `ImGuiBackend` instance belongs to exactly one `ImGuiRenderer` and is never shared, because its renderers keep cross-frame input state keyed by ImGui ID. Likewise a `Canvas` and a `Focusable` are drawn by one backend (one display) only. The `ImGuiBackend` and `Focusable` Javadoc state this for renderers and canvases, and for `Focusable`s, respectively.

```java
ImGuiJmeDisplay display = new ImGuiJmeDisplay(context, inputManager, guiViewPort);
display.registerRenderer(Gauge.class, new GaugeRenderer());
display.registerStyleApplier(GaugeStyle.class, new GaugeStyleApplier());
```

# System Architecture

## Overview
LorisUI is a layered, multi-module Java library. Game code describes UI as trees of plain component objects defined in a toolkit-agnostic API. A **backend** turns those trees into draw calls each time the host renders, and a **host integration** connects the backend to an application's render loop and input. Two hosts ship with the library: one for jMonkeyEngine 3 and one for an application's own LWJGL/SDL3 window and loop.

```
examples ──┬──▶ loris-ui-jme3  ──┬──▶ loris-ui-imgui ──▶ loris-ui-api
 (demos)   │    (jME3 host)      │    (ImGui/OpenGL       (component model,
           └──▶ loris-ui-lwjgl ──┘     backend and         Backend port, screens;
                (LWJGL/SDL3 host)      renderer)           zero dependencies)
```

## Architecture Pattern
**Pattern**: Layered library with a ports-and-adapters style backend abstraction, plus registries of strategies (renderers and style appliers) inside the backend.

- **Port**: `api/.../api/backend/Backend.java` declares a single method, `render(int w, int h, List<Component> components, BundleKeyResolver bundleKeyResolver)`. It contains nothing toolkit-specific: textures, fonts and input capture are backend concerns.
- **Adapters**: `imgui/.../imgui/backend/ImGuiBackend.java` (abstract: registries with the registration API, the per-instance texture cache, texture drawing, and the protected abstract texture creation and deletion) and `ImGuiOpenGlBackend.java` (final; OpenGL textures).
- **Frame driver**: `imgui/.../imgui/ImGuiOpenGlRenderer.java` owns the Dear ImGui context and the SDL3/OpenGL 3 platform and renderer objects, and runs one frame per call. Both hosts use it.
- **Hosts**: `jme3/.../jme3/ImGuiJmeDisplay.java` drives the renderer from jMonkeyEngine; `lwjgl/.../lwjgl/ImGuiLwjglDisplay.java` is embedded in an application that owns its SDL window, OpenGL context and loop. Both keep their screens in an `api` `ScreenManager`, resolve text with an `api` `ResourceBundleKeyResolver` and defer teardown with an `api` `DeferredRelease`. These host-support helpers live in `lorisui.api` because the automatic `lorisui.jme3` module can only read exported packages.

**Rule**: dependencies only point towards `api`. `loris-ui-api` must not depend on any toolkit, engine or third-party library.

## System Structure

### loris-ui-api (`api/`)
- **Purpose**: the public, toolkit-agnostic contract: component model, styles, backend port, screens and their lifecycle, fonts and i18n.
- **JPMS module**: `lorisui.api`. It exports `backend`, `component`, `component.style`, `core`, `font`, `resolver` and `screen`, each with a `package-info.java`; the module descriptor has a module doc comment.
- **Packages** (`com.ivan1pl.lorisui.api.*`):
  - `component`: the `Component` marker interface and concrete components (`Panel`, `Button`, `Text`, `Image`, `TextInput`, `NumberInput`, `ComboBox`, `ProgressBar`, `TabbedPanel`, `Popup`, `ModalPopup`, `Spacer`), plus `Layout`, `Background` and the sealed `ImageMode`
  - `component.style`: `Style` and its concrete styles (`ScrollbarStyle`, `ComboBoxStyle`, `ComboBoxPopupStyle`, `ComboBoxItemStyle`, `TextInputStyle`)
  - `backend`: the `Backend` interface (only)
  - `screen`: the abstract `LorisScreen` (template method for screens; static `shutdownLayoutUpdates()` stops the background layout work, which restarts lazily on the next requested layout), the final `ScreenManager` and the final `DeferredRelease`.
    - `ScreenManager` is the host-neutral registry of named screens. It validates registration and switching, fires matched `onStartScreen`/`onEndScreen` hooks through `activate()`/`setCurrentScreen`/`deactivate()`, and rejects `setCurrentScreen`, `activate()` and `deactivate()` called from inside a hook (`IllegalStateException`, before any state change). `beginDeactivation()` makes it inactive without firing a hook (allowed inside hooks); `deactivate()` later ends the screen that was started.
    - `DeferredRelease` is the host-neutral teardown helper: `run(operation)` tracks operations that can call application code, `request()` releases at once or after the outermost running operation (`isRunning()`, `isPending()` report the state), and the static `runAll(steps...)`/`runAfterFailure(failure, cleanup)` run multi-step releases keeping every failure.
    - Both are not thread-safe; hosts call them on their UI thread.
  - `core`: the final `Color` and `IntBiFunction<ResultType>`
  - `font`: the `Font` marker interface
  - `resolver`: `BundleKeyResolver` (i18n) and the final `ResourceBundleKeyResolver`, which resolves `bundleName.key` keys from `ResourceBundle`s registered by name
- **Conventions**: components are immutable-ish value holders built with nested static `Builder`s and non-public constructors. The Panel family is closed to the package: `Panel`'s constructor and its self-typed `BaseBuilder<PanelType, BuilderType>` are package-private, and `Button`, `Popup` and `ModalPopup` have private constructors.

### loris-ui-imgui (`imgui/`)
- **Purpose**: renders the API component model with Dear ImGui on OpenGL, and drives Dear ImGui frames for the hosts.
- **JPMS module**: `lorisui.imgui`, with `requires transitive lorisui.api` so consumers of the backend read the API types. It exports `imgui`, `imgui.backend`, `imgui.renderer` and `imgui.renderer.style` (each with a `package-info.java`; the descriptor has a module doc comment). **It does not export** `imgui.impl`, `backend.impl`, `renderer.impl` or `renderer.style.impl`, which are internal. There is no `imgui.font` package.
- **Key Files** (`com.ivan1pl.lorisui.imgui.*`):
  - `ImGuiOpenGlRenderer.java`: final; the frame driver. Lifecycle:
    - The constructor takes any `ImGuiBackend` and the SDL window handle and makes no native calls.
    - `registerFontFromFile`/`registerFontFromResources` (each with an optional glyph-range overload) read the font bytes eagerly (`IOException` naming the path, also for data of 100 bytes or less, on which Dear ImGui would fail a JVM-ending assertion; the `registerFont*` Javadoc asks for fonts from trusted sources only, because Dear ImGui's font loader is not hardened against malicious data), are allowed only while not initialized, and return a stable `ImGuiFont` handle. Glyph ranges are validated (`IllegalArgumentException` for no range, no terminating `0`, a missing last code point or a reversed range) and built as unsigned 16-bit code points, so ranges above `U+7FFF` (CJK) work; the font bytes stay in memory for the renderer's lifetime.
    - `initialize()` creates a fresh Dear ImGui context and makes it current, applies the IO configuration (no ini/log files, error-recovery assert and tooltip disabled), replays the registered fonts in registration order (a font Dear ImGui cannot load throws `IllegalStateException` naming its source) and builds the atlas, creates fresh `ImGuiImplSdl3`/`ImGuiImplGl3` objects (each kept only after its `init` succeeded; the SDL3 backend sets three global SDL hints that stay set after `dispose()`), and applies the LorisUI style overrides. A failed `initialize()` releases whatever it had set up (`DeferredRelease.runAfterFailure`) and leaves the renderer uninitialized, so it can be retried (a failure caused by a registered font recurs, because fonts cannot be unregistered).
    - `dispose()` releases, in order and running every step even after a failure: the backend's textures (`unloadTextures()`), `ImGuiImplGl3`, `ImGuiImplSdl3`, the context; then it unbinds the font handles. It is a no-op when not initialized, and the renderer can be initialized again afterwards (fonts are replayed, handles stay valid).
    - A private `rendering` flag covers each `render` call: `initialize()`, `dispose()` and a re-entrant `render` throw `IllegalStateException` while a frame is open, before any state change. Hosts therefore defer teardown requested from inside a frame (see Screen Lifecycle).
    - Every entry point makes the renderer's context current and records its pointer in `ImGuiState.currentContextPtr`; the renderer leaves its context current afterwards, so an application with its own Dear ImGui context must make that context current again. Only one renderer may be in use at a time.
    - `render(screen, w, h, resolver)` takes the display size in **logical window coordinates** (as reported by `SDL_GetWindowSize`); Dear ImGui's SDL3 backend applies the framebuffer scale. The jME host passes its camera size, which is in pixels (the HiDPI gap under Known Architectural Concerns). The frame is always closed; if the screen threw, its exception propagates and a frame-close failure is added to it as suppressed.
    - Input-capture queries for hosts: `wantsMouseInput()`, `wantsKeyboardInput()`, `wantsTextInput()` and `isHoveringScrollablePanel()`, each describing the most recently rendered frame and returning `false` while not initialized.
    - Dear ImGui UI state (selected tabs, scroll positions, open popups, keyboard focus) starts fresh after `dispose()` + `initialize()`; state held by LorisUI components and their bindings is unaffected.
  - `ImGuiFont.java`: final; the ImGui implementation of `Font`, in the `imgui` package so the renderer can bind it through package-private members. Instances are created only by the renderer's registration methods; there are no static loaders. A handle keeps the font bytes and built glyph ranges for replay (imgui-java passes the glyph-range pointer from a JNI critical array, so keeping the array reachable does not guarantee Dear ImGui a stable address; a known binding limitation), is re-bound on each `initialize()`, and `useFont(Runnable)` throws `IllegalStateException` (without running the code) while its renderer is not initialized or another renderer's context is current.
  - `backend/ImGuiBackend.java`: implements `Backend` and `RendererProvider`; protected constructor that fills the registries `Map<Class<? extends Component>, Renderer<?>>` and `Map<Class<? extends Style>, StyleApplier<?>>` with the built-ins.
    - Registration: `public final registerRenderer(Class, Renderer)` and `registerStyleApplier(Class, StyleApplier)` replace any existing mapping (built-ins included), reject null arguments (`NullPointerException`) and interface classes (`IllegalArgumentException`, because lookup walks only the superclass chain). `getRenderer`/`getStyleApplier` are `final`: they walk up the superclass chain and throw `IllegalStateException` when nothing matches.
    - Textures: a per-instance cache keyed by path and the three masks, with keys normalized to class-path style (a leading `/` is an alias of the bare path). `public final loadTexture(...)` (two overloads, implementing the `RendererProvider` methods) creates a texture on a miss through `protected abstract createTexture(normalizedPath, maskedR, maskedG, maskedB)`; failed loads are not cached. `public final unloadTextures()` calls `protected abstract deleteTexture(TextureData)` once per distinct texture, always empties the cache (first failure rethrown, later ones suppressed), and throws `IllegalStateException` while the backend is drawing (`render` sets a private `drawing` flag). The concrete `renderTexture(...)` maps `ImageMode` variants to ImGui draw calls with an exhaustive pattern `switch`.
  - `backend/TextureData.java`: the `TextureData(int id, int width, int height)` record returned by `RendererProvider.loadTexture`
  - `backend/ImGuiOpenGlBackend.java`: final; `createTexture` (class-loader resource lookup, STB decode, RGB-channel color masking, GL texture upload) and `deleteTexture` (`glDeleteTextures`)
  - `backend/impl/TextureMasking.java`: the pure pixel-masking loop used by `createTexture`
  - `renderer/Renderer.java`: abstract per-component renderer base (explicit protected constructor); no texture state of its own
  - `renderer/RendererProvider.java`: renderer and style-applier lookup plus `loadTexture(path)`, `loadTexture(path, maskedR, maskedG, maskedB)` and `renderTexture(...)`; container renderers use it for their children and every renderer uses it for images
  - `renderer/impl/*Renderer.java`: one renderer per component type, all created with no-argument constructors
  - `renderer/style/StyleApplier.java` and `renderer/style/impl/*StyleApplier.java`: one applier per style type, which push and pop ImGui style vars and colors
  - `impl/ImGuiState.java`: internal, final; global state shared by the renderer, renderers and fonts (`hoveringScrollableWindow`, read by hosts only through `ImGuiOpenGlRenderer.isHoveringScrollablePanel()`, and `currentContextPtr`, compared by `ImGuiFont.useFont` without a per-frame allocation)
  - `impl/ClassPathResources.java`: internal; opens class-path resources through the class loader, with a leading `/` optional (used by the renderer's font registration and `ImGuiOpenGlBackend`)
- **Toolkit dependency**: imgui-java is a runtime dependency only (`compileOnly` plus `runtimeOnly` `[1.92.7.1,1.93)`); no ImGui type appears in an exported signature, so it is not part of the module's compile-time API. `lwjgl-stb` is an `implementation` dependency (runtime scope for consumers).

### loris-ui-jme3 (`jme3/`)
- **Purpose**: integrates the ImGui backend into jMonkeyEngine 3.
- **JPMS**: no `module-info.java` (jME3 jars split packages, so a named module can't read them). The jar is an automatic module named `lorisui.jme3` through the `Automatic-Module-Name` manifest attribute. The package has a `package-info.java`.
- **Key Files**:
  - `ImGuiJmeDisplay.java`: implements `SceneProcessor` only. It owns a private `ImGuiOpenGlBackend`, an `ImGuiOpenGlRenderer`, a `ScreenManager` and a `ResourceBundleKeyResolver`, and delegates screens (`addScreen`, `setCurrentScreen`), resource bundles (`setResourceBundle`), fonts (`registerFont*`, returning `Font`) and `registerRenderer`/`registerStyleApplier` to them. Font, renderer and style-applier registration is allowed only while the display is not attached, not while its release is pending or running (a `releasing` flag covers the teardown itself, for example registration from the `onEndScreen` it fires), and not after a failed initialization. The constructor has no Dear ImGui side effects. The display is re-attachable; see Screen Lifecycle.
  - `ImGuiInputSystem.java`: package-private, final; a jME `RawInputListener` that marks mouse and key events consumed using only the `ImGuiOpenGlRenderer` input-capture queries. jme3 has no `imgui.*` imports.

### loris-ui-lwjgl (`lwjgl/`)
- **Purpose**: hosts LorisUI in an application's own LWJGL SDL3 window and OpenGL loop, without a game engine.
- **JPMS module**: `lorisui.lwjgl`, exporting `com.ivan1pl.lorisui.lwjgl` (with `package-info.java` and a module doc comment), `requires transitive lorisui.imgui` and `requires org.lwjgl.sdl`. It compiles against `lwjgl` and `lwjgl-sdl` as `compileOnly`; at runtime they come with imgui-java.
- **Key Files**:
  - `ImGuiLwjglDisplay.java`: final, `AutoCloseable`; `ImGuiLwjglDisplay(long sdlWindow)` (`IllegalArgumentException` for `0`, no native calls). It owns the same four collaborators as the jME display and offers the same registration, screen and bundle methods. The application keeps the window, the GL context and the loop: it calls `initialize()` with the context current, forwards every SDL event to `processEvent(long)` (returns whether the UI consumes it, using the `ImGuiInputSystem` rule; `false` while not initialized), calls `render(width, height)` once per frame in logical window coordinates after clearing and before swapping, and calls `close()` before destroying the context or window. All precondition checks run before any native call.

### examples (`examples/`)
- **Purpose**: demo applications and manual test bed. It applies only the `java` plugin and registers the `runJme3Example` and `runLwjglExample` `JavaExec` tasks (group `application`), which pass `--enable-native-access=ALL-UNNAMED`.
- **Key Files**:
  - `example/shared/ExampleScreen.java`: a host-agnostic `LorisScreen` that exercises the components; its constructor takes the font and a required `hideUiAction`, wired to a "Hide UI" button (bundle key `global.hideUi`)
  - `example/shared/ExampleSettings.java`: shared constants of both examples (800×600 window, English locale, `global` bundle at `bundles.global`, the Open Sans font resource at size 20, the screen name)
  - `example/jme3/LorisJme3Example.java`: a jME `SimpleApplication` with OpenGL 3.3. F1 toggles the UI by removing and re-adding the display on the GUI viewport; "Hide UI" removes the display from inside the frame (F1 brings it back); `destroy()` removes the display if it is attached
  - `example/lwjgl/LorisLwjglExample.java`: creates an SDL3 window with a 3.3 core, sRGB-capable OpenGL context (`GL_FRAMEBUFFER_SRGB` enabled, high pixel density), runs an `ImGuiLwjglDisplay` in try-with-resources and a poll/clear/render/swap loop. "Hide UI" closes the display permanently from inside the frame, and the window keeps clearing to black until it is closed

## Data Flow

**Setup**
1. The host app creates a display (`ImGuiJmeDisplay(context, inputManager, guiViewPort)` or `ImGuiLwjglDisplay(sdlWindow)`), registers fonts, custom renderers and style appliers and resource bundles, adds `LorisScreen`s and selects the current screen. Nothing native happens yet.
2. The display is initialized: jME calls `initialize` lazily, on the first frame (or window resize, through `RenderManager.notifyReshape`) after the display is added to a viewport; the LWJGL application calls `initialize()` itself. The renderer creates its context, replays the fonts and sets up the SDL3/GL3 objects; the jME display then registers its input listeners. Finally `ScreenManager.activate()` fires `onStartScreen()` on the current screen.

**Per frame** (jME `postQueue`, LWJGL `render`):
1. `ImGuiOpenGlRenderer.render(screen, w, h, resolver)` makes its context current and starts an ImGui frame.
2. `LorisScreen.render(backend, w, h, resolver)`:
   - If the previous `layout()` call threw or returned `null`, the failure is rethrown once as an `IllegalStateException` (cause = original failure) and nothing is rendered in that call; later frames render the last successful layout. Hosts should treat it as fatal.
   - If the layout was invalidated (`setLayoutNeedsUpdate(true)`, callable from any thread; the update flag is an `AtomicBoolean`), `layout()` is scheduled on the shared single-thread daemon layout worker (`lorisui-layout`), which is created lazily and stopped by `LorisScreen.shutdownLayoutUpdates()`. The new `List<Component>` is published through a `volatile` field and replaces `content` asynchronously; in the meantime the previous content keeps rendering (an empty list before the first layout).
   - Calls `backend.render(w, h, content, resolver)`.
3. `ImGuiBackend.render` looks up the `Renderer` for each component, and each renderer emits ImGui calls. Containers (Panel, TabbedPanel, Popup) recurse through `RendererProvider`. Styles are applied through `StyleApplier`s. Text keys are resolved through `BundleKeyResolver`. Images are loaded or fetched from the backend's cache through `RendererProvider.loadTexture(...)` and drawn with `RendererProvider.renderTexture(...)` according to their `ImageMode`. A missing or unreadable image (`Image` or panel `Background`) makes the renderer throw a `RuntimeException` wrapping the `IOException`; failures are not cached, so the screen's render fails again on every draw.
4. ImGui draw data is rendered with OpenGL 3. `ImGuiOpenGlRenderer.render` ends the ImGui frame even when `LorisScreen.render` throws; the screen's exception propagates, with any frame-close failure suppressed.

**Input**: SDL events reach ImGui IO through `ImGuiOpenGlRenderer.processSdlEvent`. In jME, an SDL event listener forwards them, and in parallel `ImGuiInputSystem` marks jME raw input events consumed when `wantsMouseInput()`/`wantsKeyboardInput()` report that the UI wants them; mouse-wheel events are consumed only while `isHoveringScrollablePanel()`. In the LWJGL host the application passes each event to `processEvent`, which forwards it and applies the same rule to its return value. Component callbacks (for example button actions) run during rendering on the host's UI thread.

**Teardown**: removal (jME `cleanup`) or `close()` (LWJGL) → `ScreenManager.beginDeactivation()` → `DeferredRelease.request()`, deferred to the end of the outermost operation if requested during a frame, a screen switch or a hook → `ScreenManager.deactivate()` (`onEndScreen`) → renderer `dispose()` (textures → Gl3 → Sdl3 → context → font handles unbound) → `LorisScreen.shutdownLayoutUpdates()`. Each step runs even when an earlier one fails (`DeferredRelease.runAll`); the first failure propagates and later ones are suppressed.

## Screen Lifecycle
All display calls and screen hooks run on the host's UI thread (the jME render thread, or the thread that owns the SDL window and GL context). Neither display implements `BundleKeyResolver`; each passes its internal `ResourceBundleKeyResolver` to the renderer, and applications that need key resolution create their own resolver.

**Shared rules (`ScreenManager`)**:
- A screen receives `onEndScreen()` only if its `onStartScreen()` returned normally, and at most once per start; a screen whose `onStartScreen()` threw counts as not started. Hook exceptions propagate out of the method that fired them.
- `addScreen(name, screen)`: `NullPointerException` for null arguments, `IllegalStateException` for a name that is already registered. Fires no hooks and is allowed from inside hooks.
- `setCurrentScreen(name)`: `IllegalStateException` from inside a hook, then `NullPointerException` for null and `IllegalStateException` for an unknown name, all before any state change; switching to the current screen does nothing. While the display is not initialized it only records the name. While initialized the switch is immediate: the new screen becomes current, then `onEndScreen()` fires on the old screen and `onStartScreen()` on the new one, during the call; the new screen is drawn from the next frame. The switch always completes: if the old screen's `onEndScreen()` throws, the new screen is still started, then the end failure propagates (a different start failure is added to it as suppressed). It may be called from a component callback, in which case the old screen finishes drawing the current frame.
- **Re-entrancy guard**: `setCurrentScreen`, `activate()` and `deactivate()` called from inside `onStartScreen()`/`onEndScreen()` throw `IllegalStateException` before changing state. Screens switch later instead, for example from a component callback.
- **Two-phase deactivation**: `beginDeactivation()` makes the manager inactive without a hook (allowed inside hooks; a switch or activation already in progress still completes). From then on `setCurrentScreen` only records the choice, and `deactivate()` fires `onEndScreen()` on the screen started before, even if another screen has been selected since; it also ends a started screen while the manager is already inactive. `activate()` throws `IllegalStateException` while a begun deactivation has not been completed with `deactivate()`.

**Deferred teardown (both hosts)**: each display runs its operations that can call application code (rendering a frame, `setCurrentScreen`, and the activate step of `initialize`) through its `DeferredRelease`. A teardown request stops the display at once (the jME display removes its input listeners and `isInitialized()` returns `false`; the LWJGL display is closed and `processEvent` returns `false`), calls `ScreenManager.beginDeactivation()` and then `DeferredRelease.request()`. If an operation is running (a component callback, such as the examples' "Hide UI" button, or a screen hook), the release runs after the outermost one, once the frame has closed or the hook has returned. The renderer is therefore never disposed inside a frame and `deactivate()` never runs inside a hook. While the release is pending, `setCurrentScreen` fires no hooks and only records the choice; the recorded screen becomes current and, on the re-attachable jME display, starts on the next attach. Release failures propagate from that operation, or are added as suppressed to its exception if it is already throwing.

**jME host (`ImGuiJmeDisplay`)**:
- `initialize`: throws `IllegalStateException` if an earlier initialization failed, if the display is already initialized or its deferred release has not completed, or if no current screen is set, all before any side effect. If setting up the renderer or registering the listeners fails, it marks the display failed, removes the listeners, disposes the renderer and rethrows, so jME's per-frame retry fails fast; no hooks fire and the display is permanently unusable (registration also throws). Otherwise it ends with `ScreenManager.activate()` (`onStartScreen()`); a throwing `onStartScreen()` propagates and the display stays initialized.
- `postQueue` returns early when the display is not initialized, because jME iterates a snapshot of the viewport's processors and can still call a display removed earlier in the same frame.
- `cleanup`: jME calls it when the display is removed from its viewport (`ViewPort.removeProcessor`/`clearProcessors`). A no-op unless initialized. Otherwise it tears down (deferred if an operation run through its `DeferredRelease` is in progress).
- **Re-attach**: a cleaned-up display can be added to a viewport again. It re-creates the context, replays the fonts (the `Font` handles stay valid) and starts the current screen again; screens, bundles, renderers and style appliers stay registered, and fonts, renderers and style appliers can be registered again between removal and re-attach. Dear ImGui UI state starts fresh. Re-adding the display in the same callback that removed it is safe, because jME initializes it on a later frame, after the deferred release.
- Only one display may be attached at a time.
- **Application exit**: jME does not call `cleanup` on exit. Applications that want `onEndScreen()` and the native release at exit remove the display themselves; `LorisJme3Example` overrides `destroy()` and calls `guiViewPort.removeProcessor(imGuiJmeDisplay)` (only if attached, since `removeProcessor` calls `cleanup` even for a processor that is not attached) before `super.destroy()`.

**LWJGL host (`ImGuiLwjglDisplay`)**:
- `initialize()`: `IllegalStateException` if closed, already initialized, or no current screen is set, all before side effects. If the renderer fails to initialize, the exception propagates, the renderer has released what it set up, and the display stays uninitialized and can be retried (after a failure caused by a registered font, create a new display instead). Then it marks itself initialized and calls `ScreenManager.activate()`; a throwing `onStartScreen()` propagates and the display stays initialized.
- `render` throws `IllegalStateException` when not initialized or closed; `processEvent` returns `false` then.
- SDL text input: after each frame that returns normally (and only while still initialized), `render` compares the renderer's `wantsTextInput()` with the state it last applied and calls `SDL_StartTextInput`/`SDL_StopTextInput` for the window, because imgui-java's SDL3 backend does not port Dear ImGui's `Platform_SetImeDataFn` and SDL3 delivers no `SDL_EVENT_TEXT_INPUT` until text input is started. A refused start is not recorded, so the next frame retries; release stops text input if it was started (after `onEndScreen`, before the renderer's `dispose()`). The jME host needs no such step, as jME's `SdlKeyInput` starts text input itself.
- `close()`: idempotent and **final** (`AutoCloseable` semantics): the display is marked closed at once, so later `register*`, `initialize` and `render` throw, while `addScreen`, `setCurrentScreen` and `setResourceBundle` only record. If initialized, it releases immediately, or deferred when called during a frame, a screen switch or a hook. To show UI again, the application creates a new display. Closing before `initialize()` only marks the display closed.
- Only one display may be initialized at a time.

## Extension Points
- **New built-in component**: add a class to `api/component` (with a Builder), add a renderer in `imgui/renderer/impl`, and register it in the `ImGuiBackend` constructor.
- **New built-in style**: add a class to `api/component/style`, add an applier in `imgui/renderer/style/impl`, and register it in the `ImGuiBackend` constructor.
- **Custom components or styles (library users)**: extend `Renderer`/`StyleApplier` and register them with `registerRenderer`/`registerStyleApplier`, either on an `ImGuiBackend` or on a display (`ImGuiJmeDisplay`, `ImGuiLwjglDisplay`) before it is initialized. A registration replaces any existing mapping, including a built-in one, and subclasses without their own mapping use the nearest registered ancestor. Renderers load and draw textures through the `RendererProvider` they receive. A custom renderer calls Dear ImGui directly, so its code adds imgui-java to its own build and, on the module path, `requires imgui.binding`. The displays keep their backend private; registration is the only customization path, which also covers the former "custom backend in the jME host" need.
- **Another graphics API**: subclass `ImGuiBackend` and implement `createTexture`/`deleteTexture` (`ImGuiOpenGlBackend` is final), then drive it with a host of your own; both bundled hosts always use their own `ImGuiOpenGlBackend`.
- **New backend**: implement `Backend.render` (and its own registry mechanism) in a new module that depends only on `loris-ui-api`.
- **New host**: a module that depends only on `loris-ui-imgui`. Wrap `ImGuiOpenGlRenderer` and `ImGuiOpenGlBackend` in the target's render hook, keep screens in a `ScreenManager`, resolve text with a `ResourceBundleKeyResolver`, use the renderer's input-capture queries for input routing (starting SDL text input on `wantsTextInput()` unless the framework does), and defer teardown requested during a frame or hook with a `DeferredRelease` plus `ScreenManager.beginDeactivation()`, as the bundled hosts do.

## Known Architectural Concerns
- **jME HiDPI size gap**: the renderer expects logical window coordinates, but the jME host passes its camera size in pixels, so on HiDPI displays with a framebuffer scale above 1 the jME UI is mis-scaled. The LWJGL host passes the logical window size and is unaffected.
- **Dear ImGui asserts end the JVM**: imgui-java calls `System.exit(1)` after any failed Dear ImGui assertion, even with a custom `ImGui.setAssertCallback` handler, which can only log or pick the exit code. The renderer disables error-recovery asserts so frame exceptions reach the host, and its in-frame guard plus the hosts' deferred teardown remove the known `DestroyContext` trigger (a locked font atlas); other asserts still terminate. This is documented in the `ImGuiOpenGlRenderer` and `lorisui.imgui` Javadoc.
- **Native lifecycle verified manually only**: context creation and destruction, Impl shutdown, font replay, GL texture deletion and re-attach cannot be unit-tested (no native context in tests), and were checked by hand on Linux only. Only the native-free paths are unit-tested: the deferred-teardown state machine (`DeferredRelease`, `ScreenManager.beginDeactivation`, and their host composition mirrored in `HostLifecycleCompositionTest`), the renderer's gating, `ImGuiFont` glyph-range validation and the LWJGL display's pre-initialize paths; `jme3` and `examples` have no tests.
- **UI state on re-attach**: every re-attach creates a new Dear ImGui context, so selected tabs, scroll positions, open popups and keyboard focus reset; LorisUI-held state (bindings, `TabbedPanel`/`ComboBox` model values) is kept.
- **Global SDL hints**: imgui-java's SDL3 backend sets `SDL_HINT_MOUSE_FOCUS_CLICKTHROUGH`, `SDL_HINT_MOUSE_AUTO_CAPTURE` and `SDL_HINT_BORDERLESS_WINDOWED_STYLE` on every `initialize()`; they stay set after `dispose()`.
- **Context left current**: the renderer leaves its Dear ImGui context current after every call, so an application that uses its own Dear ImGui context must restore it.
- **Global state**: `ImGuiState` holds static flags (`hoveringScrollableWindow`, `currentContextPtr`), and `LorisScreen` shares one static layout worker across screens; only one renderer and one display may be in use at a time.
- **Texture cache**: per backend, cleared as a whole by `unloadTextures()` (and by renderer teardown); there is no per-path eviction while a backend is in use.
- **Missing images**: a texture that fails to load is retried and fails again on every draw instead of failing once.
- **Renderer robustness**: `ImGuiOpenGlRenderer` disables ImGui's error-recovery assert and tooltip, so state left open by a throwing renderer (windows, IDs, style stacks) is unwound when the frame closes and the original exception propagates to the host; the trade-off is that an imbalance that does not throw is recovered silently instead of failing fast. The input renderers pop their item width in `finally`, the combo box uses `setNextItemWidth`, and the progress bar pops its style in `finally`, but other push/pop pairs (combo style vars, per-item IDs, `beginChild`/`endChild` in the panel and combo renderers) are still not in `try/finally`. `TextInput` and `NumberInput` both use the bare `"##"` ImGui label without a per-component ID, so two inputs in the same window share an ImGui ID.

## Configuration
- Build-time: Gradle `ext` versions in the root `build.gradle`; Checkstyle rules in `config/checkstyle/`; editor settings in `.editorconfig`
- Runtime: done in code through either display (fonts, renderers and style appliers, resource bundles, screens). The examples' shared settings live in `ExampleSettings`; the jME window settings in `LorisJme3Example.createDefaultSettings()`.
- i18n: `ResourceBundle`s registered by name (for example `bundles.global`)
- Resources (fonts, textures) are class-path resource names; a leading `/` is optional. On the module path they must be outside any package of a named module, or in a package the application module opens unconditionally.

## Deployment Architecture
LorisUI is a library, so it isn't deployed as a service. It's meant to be published as Maven artifacts (`loris-ui-api`, `loris-ui-imgui`, `loris-ui-jme3`, `loris-ui-lwjgl`) and consumed by desktop game applications. imgui-java (which brings LWJGL with its SDL and OpenGL bindings and natives) is pulled in at runtime; `lwjgl-stb` is an `implementation` dependency of `loris-ui-imgui` (runtime scope for consumers) with natives for Windows, Linux, macOS and macOS arm64. On JDK 25, applications pass `--enable-native-access` (`ALL-UNNAMED` on the class path, the module names on the module path) to avoid the restricted-method warnings of imgui-java and LWJGL; the examples' run tasks pass `ALL-UNNAMED`. Running the SDL-based examples on macOS may additionally need `-XstartOnFirstThread`, which the run tasks don't pass. Consumer Javadoc states `--enable-native-access` in the `lorisui.imgui`, `lorisui.lwjgl` and jme3 package docs, and `-XstartOnFirstThread` in the LWJGL host's docs.

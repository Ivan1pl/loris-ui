# System Architecture

## Overview
LorisUI is a layered, multi-module Java library. Game code describes UI as trees of plain component objects defined in a toolkit-agnostic API. A **backend** turns those trees into draw calls each time the host renders, and a **host integration** connects the backend to an application's render loop and input. Two host modules ship with the library: one for jMonkeyEngine 3 and one for an application's own LWJGL window and loop, with a display for each supported platform/renderer pair (SDL3 with OpenGL 3, GLFW with OpenGL 3, SDL3 with SDL_GPU, SDL3 with Vulkan). The jME display draws with OpenGL 3 or OpenGL ES 3, whichever matches jME's renderer.

```
examples ──┬──▶ loris-ui-jme3  ──┬──▶ loris-ui-imgui ─────────────────────────────▶ loris-ui-api
 (demos)   │    (jME3 host:      │    (ImGui backends and renderers:          ▲    (component model,
           │     GL3 / GLES3)    │     OpenGL 3, GLES 3, SDL_GPU, Vulkan)      │     Backend port, screens;
           └──▶ loris-ui-lwjgl ──┘         │                                   │     zero dependencies)
                (LWJGL host:               ├──▶ loris-ui-imgui-vulkan ─────────┘
                 SDL3 / GLFW)              │    (MIT: Vulkan renderer port)
                                           └──▶ loris-ui-imgui-gles3
                                                (MIT: OpenGL ES 3 renderer port)
```

## Architecture Pattern
**Pattern**: Layered library with a ports-and-adapters style backend abstraction, plus registries of strategies (renderers and style appliers) inside the backend.

- **Port**: `api/.../api/backend/Backend.java` declares `render(int w, int h, List<Component> components, BundleKeyResolver bundleKeyResolver)` and the keyboard-navigation settings of the UI it draws: `getActivationKey`/`setActivationKey` (the `api` enum `ActivationKey`, `ENTER` or `SPACE`) and `isKeyboardNavigationEnabled`/`setKeyboardNavigationEnabled`. It contains nothing toolkit-specific: textures, fonts, input capture and how keys are read are backend concerns.
- **Adapters**: `imgui/.../imgui/backend/ImGuiBackend.java` (abstract: registries with the registration API, the per-instance texture cache, the per-instance canvas textures with their eviction, texture drawing, and the protected abstract hooks for texture creation and deletion and for canvas texture creation and update), `ImGuiOpenGlBackend.java` (final; OpenGL textures), `ImGuiOpenGlEsBackend.java` (final; OpenGL ES textures), `ImGuiSdlGpuBackend.java` (final; SDL_GPU textures) and `ImGuiVulkanBackend.java` (final; Vulkan textures).
- **Frame driver**: the sealed `imgui/.../imgui/ImGuiRenderer.java` owns the Dear ImGui context and runs one frame per call; its five final variants own the platform and renderer objects of one pair each: `ImGuiSdlGl3Renderer` (SDL3 + OpenGL 3, used by the jME host on desktop OpenGL and by `ImGuiLwjglSdlGl3Display`), `ImGuiGlfwGl3Renderer` (GLFW + OpenGL 3), `ImGuiSdlGles3Renderer` (SDL3 + OpenGL ES 3, used by the jME host on ANGLE), `ImGuiSdlGpuRenderer` (SDL3 + SDL_GPU) and `ImGuiSdlVulkanRenderer` (SDL3 + Vulkan 1.3).
- **Hosts**: `jme3/.../jme3/ImGuiJmeDisplay.java` drives the renderer from jMonkeyEngine, choosing the GL3 or GLES3 pair from jME's renderer setting; the four displays in `lwjgl/.../lwjgl/` (`ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay`, `ImGuiLwjglSdlVulkanDisplay`) are embedded in an application that owns its window, OpenGL context, GPU device or Vulkan device, and loop. All keep their screens in an `api` `ScreenManager`, resolve text with an `api` `ResourceBundleKeyResolver` and defer teardown with an `api` `DeferredRelease`. These host-support helpers live in `lorisui.api` because the automatic `lorisui.jme3` module can only read exported packages.

**Rule**: dependencies only point towards `api`. `loris-ui-api` must not depend on any toolkit, engine or third-party library. The two renderer-port modules sit below `loris-ui-imgui` as internal helpers: `loris-ui-imgui-vulkan` depends only on `loris-ui-api`, `loris-ui-imgui-gles3` on no LorisUI module, and nothing but `loris-ui-imgui` depends on them. They are separate subprojects only because their code is MIT-licensed (see their section under System Structure).

## System Structure

### loris-ui-api (`api/`)
- **Purpose**: the public, toolkit-agnostic contract: component model, styles, backend port, screens and their lifecycle, fonts and i18n.
- **JPMS module**: `lorisui.api`. It exports `backend`, `component`, `component.style`, `core`, `font`, `resolver` and `screen`, each with a `package-info.java`; the module descriptor has a module doc comment.
- **Packages** (`com.ivan1pl.lorisui.api.*`):
  - `component`: the `Component` marker interface and concrete components (`Panel`, `Button`, `Text`, `Image`, `TextInput`, `NumberInput`, `ComboBox`, `ProgressBar`, `TabbedPanel`, `Popup`, `ModalPopup`, `Spacer`, `Canvas`), plus `Layout`, `Background`, the sealed `ImageMode` and the `MouseButton` enum (`LEFT`, `RIGHT`, `MIDDLE`; its order is the preference among buttons pressed in the same frame)
    - `Canvas` shows an editable pixel image. Its display size (`size(w, h)`, required: `build()` throws `NullPointerException` naming `size` without it) is in logical window pixels, its resolution (`resolution(w, h)`, the size by default, at most 536,870,911 pixels) in image pixels; both are fixed at build time. Pixels are packed ARGB (`0xAARRGGBB`, like `Color.getRGBA()`), start transparent, and are read and written with `getPixel`/`setPixel` (an `int` or a `Color`) and the `BufferedImage.setRGB`-style `getPixels`/`setPixels(x, y, w, h, argb, offset, scanSize)` (caller arrays are copied; every argument is checked before any change, `NullPointerException` for `null`, `IllegalArgumentException` otherwise, in a documented order). The visible region (`getVisibleRegion()` returning the nested `Canvas.Region` record, read atomically; `setVisibleRegion(x, y, w, h)`, inside the image) is stretched over the display size without keeping the aspect ratio, and an optional background color fills the display area behind the image. All pixel, region and snapshot methods are atomic under a private lock and may be called from any thread; no supplier or callback runs while it is held. Backends take the changed pixels with `takePixelUpdate(boolean wholeImage)`, which returns a `Canvas.PixelUpdate(x, y, width, height, argb)` record with a fresh copy of the bounding rectangle of all changes since the last take (the whole image when asked), or `null` when nothing changed, and clears the pending changes. Mouse events go to the nested `@FunctionalInterface` callbacks `ClickAction`, `DragAction` and `WheelAction` (no-op defaults, one `requireNonNull` setter each) through the public triggers `click(x, y, button)`, `drag(x, y, dx, dy, button)` and `wheel(x, y, delta)`, which run them only while `isEnabled()`. The canvas takes no keyboard focus. Its class Javadoc advises keeping a canvas in a screen field (one built in `layout()` starts empty after every relayout), drawing it on one display only and keeping the resolution at or below 4096 × 4096
  - `component.style`: `Style` and its concrete styles (`ScrollbarStyle`, `ComboBoxStyle`, `ComboBoxPopupStyle`, `ComboBoxItemStyle`, `TextInputStyle`)
  - `backend`: the `Backend` interface and the `ActivationKey` enum (`ENTER`, which includes keypad Enter, and `SPACE`). `Backend`'s Javadoc describes keyboard navigation toolkit-neutrally (Tab/Shift+Tab cycling with wrap-around, disabled buttons skipped, popups and expanded combo boxes trapping the cycle, Up/Down in an expanded combo box, the activation key, Escape closing an expanded combo box or clearing the focus but never closing a popup)
  - `screen`: the abstract `LorisScreen` (template method for screens; static `shutdownLayoutUpdates()` stops the background layout work, which restarts lazily on the next requested layout), the final `ScreenManager` and the final `DeferredRelease`.
    - `ScreenManager` is the host-neutral registry of named screens. It validates registration and switching, fires matched `onStartScreen`/`onEndScreen` hooks through `activate()`/`setCurrentScreen`/`deactivate()`, and rejects `setCurrentScreen`, `activate()` and `deactivate()` called from inside a hook (`IllegalStateException`, before any state change). `beginDeactivation()` makes it inactive without firing a hook (allowed inside hooks); `deactivate()` later ends the screen that was started.
    - `DeferredRelease` is the host-neutral teardown helper: `run(operation)` tracks operations that can call application code, `request()` releases at once or after the outermost running operation (`isRunning()`, `isPending()` report the state), and the static `runAll(steps...)`/`runAfterFailure(failure, cleanup)` run multi-step releases keeping every failure.
    - Both are not thread-safe; hosts call them on their UI thread.
  - `core`: the final `Color` and `IntBiFunction<ResultType>`, the content function that receives the screen width and height
  - `font`: the `Font` marker interface
  - `resolver`: `BundleKeyResolver` (i18n; its default `containsKey(key)` resolves the key without arguments and returns `false` on a `RuntimeException`, after rejecting a `null` key) and the final `ResourceBundleKeyResolver`, which resolves `bundleName.key` keys from `ResourceBundle`s registered by name and overrides `containsKey` with `ResourceBundle.containsKey`, returning `false` for a key without a dot or of an unregistered bundle
- **Conventions**: components are immutable-ish value holders built with nested static `Builder`s and non-public constructors. The Panel family is closed to the package: `Panel`'s constructor and its self-typed `BaseBuilder<PanelType, BuilderType>` are package-private, and `Button`, `Popup` and `ModalPopup` have private constructors.

### loris-ui-imgui (`imgui/`)
- **Purpose**: renders the API component model with Dear ImGui on OpenGL 3, OpenGL ES 3, SDL_GPU or Vulkan, and drives Dear ImGui frames for the hosts.
- **JPMS module**: `lorisui.imgui`, with `requires transitive lorisui.api` so consumers of the backend read the API types; plain `requires` for imgui-java (`imgui.binding`, `imgui.lwjgl3`), LWJGL's `org.lwjgl.opengl`, `org.lwjgl.sdl` (the SDL_GPU calls and the SDL variants' text input) and `org.lwjgl.stb`, and the two renderer-port modules `lorisui.imgui.gles3` and `lorisui.imgui.vulkan` (which export their package only to `lorisui.imgui`, so on the module path both must be present at runtime for every host, and no application requires them); and plain `requires static org.lwjgl.opengles` and `requires static org.lwjgl.vulkan`, never `transitive`: only the GLES3 and Vulkan variants and their backends use them, so GL-only and SDL_GPU consumers need neither, and jME consumers need neither at compile time. A `requires static` module is not added to the module graph at runtime, so a modular application in which a variant runs resolves its binding: a Vulkan application declares `requires org.lwjgl.vulkan` itself, and a modular jME application on jME's default ANGLE renderer (the GLES3 variant) declares `requires org.lwjgl.opengles` or starts with `--add-modules org.lwjgl.opengles`, as jME itself needs under that renderer (see `standards/architecture/modules.md`). It exports `imgui`, `imgui.backend`, `imgui.renderer` and `imgui.renderer.style` (each with a `package-info.java`; the descriptor has a module doc comment). **It does not export** `imgui.impl`, `backend.impl`, `renderer.impl` or `renderer.style.impl`, which are internal. There is no `imgui.font` package.
- **Key Files** (`com.ivan1pl.lorisui.imgui.*`):
  - `ImGuiRenderer.java`: `public abstract sealed`, permitting exactly the five final variants below (`ImGuiSdlGl3Renderer`, `ImGuiGlfwGl3Renderer`, `ImGuiSdlGpuRenderer`, `ImGuiSdlGles3Renderer`, `ImGuiSdlVulkanRenderer`); the frame driver. Its constructor and its hooks (`initBackends`, `newBackendFrame`, `shutdownRendererBackend`, `shutdownPlatformBackend`, `clearBackends`, the no-op `awaitDeviceIdle`, and the no-op `updateTextInput`/`releaseTextInput`, which the four SDL variants override), the `isRendering()` query and `divertTab(TabKeyFilter.Result)` (the variants pass every key event's Tab classification; it returns whether the event is withheld from Dear ImGui and queues a move of +1 or -1 only while keyboard navigation is enabled, in one exhaustive switch shared by all five variants) are package-private, so the hierarchy is closed to the package; the base has no public `render`, because the variants' signatures differ. Lifecycle:
    - The variant constructors take a backend and the window handle and make no native calls: `ImGuiSdlGl3Renderer(ImGuiBackend, sdlWindow)` (any handle accepted, as before the rename), `ImGuiGlfwGl3Renderer(ImGuiBackend, glfwWindow)`, `ImGuiSdlGles3Renderer(ImGuiBackend, sdlWindow)` and `ImGuiSdlGpuRenderer(ImGuiSdlGpuBackend, sdlWindow)` (`IllegalArgumentException` for a `0` window; the typed backend prevents pairing a GL backend with the GPU renderer). A null backend throws `NullPointerException`, checked first. `ImGuiSdlVulkanRenderer(ImGuiVulkanBackend, sdlWindow, colorAttachmentFormat, framesInFlight)` checks its primitives first, before the null backend (`IllegalArgumentException` for a `0` window, a non-positive format or fewer than one frame in flight, in that order), because no Vulkan object can exist in a unit test; it then takes the device, queue family and queue from the backend. The colour-attachment format is baked into the pipeline and fixed for the renderer's lifetime; `dispose()` and `initialize()` keep it, and another format needs a new renderer.
    - `registerFontFromFile`/`registerFontFromResources` (each with an optional glyph-range overload) read the font bytes eagerly (`IOException` naming the path, also for data of 100 bytes or less, on which Dear ImGui would fail a JVM-ending assertion; the `registerFont*` Javadoc asks for fonts from trusted sources only, because Dear ImGui's font loader is not hardened against malicious data), are allowed only while not initialized, and return a stable `ImGuiFont` handle. Glyph ranges are validated (`IllegalArgumentException` for no range, no terminating `0`, a missing last code point or a reversed range) and built as unsigned 16-bit code points, so ranges above `U+7FFF` (CJK) work; the font bytes stay in memory for the renderer's lifetime.
    - `initialize()` creates a fresh Dear ImGui context and makes it current, applies the IO configuration (no ini/log files, error-recovery assert and tooltip disabled), replays the registered fonts in registration order (a font Dear ImGui cannot load throws `IllegalStateException` naming its source) and builds the atlas, creates the variant's fresh platform and renderer Impl objects (`ImGuiImplSdl3`/`ImGuiImplGl3`, `ImGuiImplGlfw`/`ImGuiImplGl3`, `ImGuiImplSdl3`/`ImGuiImplGles3`, `ImGuiImplSdl3`/`ImGuiImplSdlGpu3` or `ImGuiImplSdl3` (`initForVulkan`)/`ImGuiImplVulkan`; each kept only after its `init` succeeded, except that a failed `ImGuiImplSdlGpu3.init`, `ImGuiImplGles3.init` or `ImGuiImplVulkan.init` is shut down on the spot because it may already own GPU, GL or Vulkan objects; the SDL3 backend sets three global SDL hints that stay set after `dispose()`, and the GLFW backend replaces GLFW's global monitor callback; the SDL_GPU variant first reads the window's swapchain format and throws `IllegalStateException` when the window is not claimed for the device; the Vulkan variant first throws `IllegalStateException` when the device does not expose Vulkan 1.3 functions, and its `ImGuiImplVulkan.init` uploads the font atlas on the backend's queue and waits for it), and applies the LorisUI style overrides. A failed `initialize()` releases whatever it had set up (`DeferredRelease.runAfterFailure`) and leaves the renderer uninitialized, so it can be retried (a failure caused by a registered font recurs, because fonts cannot be unregistered).
    - `dispose()` releases, in order and running every step even after a failure: makes the context current, stops SDL text input if an SDL variant started it, waits for the device to go idle (`SDL_WaitForGPUIdle` for SDL_GPU, `vkDeviceWaitIdle` for Vulkan, whose failure throws `IllegalStateException("vkDeviceWaitIdle failed with VkResult <n>")`; a no-op for the GL variants), the backend's textures (`unloadTextures()`), the renderer Impl (`ImGuiImplGl3`, `ImGuiImplGles3`, `ImGuiImplSdlGpu3` or `ImGuiImplVulkan`), the platform Impl (`ImGuiImplSdl3` or `ImGuiImplGlfw`), the context; then, even after a failure, it unbinds the font handles and drops the variant's Impl references (`clearBackends`). It is a no-op when not initialized, and the renderer can be initialized again afterwards (fonts are replayed, handles stay valid).
    - A private `rendering` flag (read through the package-private `isRendering()`) covers each `render` call: `initialize()`, `dispose()` and a re-entrant `render` throw `IllegalStateException` while a frame is open, before any state change. Hosts therefore defer teardown requested from inside a frame (see Screen Lifecycle).
    - Every entry point makes the renderer's context current and records its pointer in `ImGuiState.currentContextPtr`; the renderer leaves its context current afterwards, so an application with its own Dear ImGui context must make that context current again. Only one renderer may be in use at a time.
    - The variants' `render` methods take the screen size in **logical window coordinates**: `SDL_GetWindowSize` for the SDL variants, `glfwGetWindowSize` for the GLFW variant (on Windows and X11 GLFW measures windows in pixels, so the UI is not scaled up on HiDPI monitors); Dear ImGui's platform backend applies the framebuffer scale. `ImGuiSdlGl3Renderer`, `ImGuiGlfwGl3Renderer` and `ImGuiSdlGles3Renderer` have `render(screen, w, h, resolver)` and draw into the current OpenGL or OpenGL ES framebuffer. `ImGuiSdlGpuRenderer` has `render(screen, w, h, resolver, commandBuffer, targetTexture)`: a `0` command buffer throws `IllegalArgumentException` before any state check; a `0` target builds the frame but draws nothing; otherwise it runs `prepareDrawData` outside any pass, then draws in its own `LOADOP_LOAD`/`STOREOP_STORE` render pass on the application's command buffer, which the application has cleared before and submits after the call. `ImGuiSdlVulkanRenderer` has `render(screen, w, h, resolver, commandBuffer, targetImageView)`: before any state check it throws `NullPointerException` for a `null` `VkCommandBuffer`, then `IllegalArgumentException` for a command buffer of another device than the backend's. No render pass or dynamic rendering instance may be active on the command buffer, because the renderer records a barrier and a rendering instance of its own; the application ends the one it cleared the image with before the call. It records nothing when the target view is `0`, when `skipFrameDraw()` was called during the frame, when the framebuffer is empty or when there are no draw lists; otherwise it records one global colour-attachment write-after-write barrier and draws in its own `vkCmdBeginRendering` (`LOAD`/`STORE`, dynamic rendering) on the application's image view, which must be in `COLOR_ATTACHMENT_OPTIMAL`, have the format given at construction and be at least the window's pixel size. The render area is the draw data's framebuffer size (`SDL_GetWindowSizeInPixels`), since `render` has no extent parameter. It keeps one host-visible vertex/index buffer pair per frame in flight and moves to the next only on a frame that records draws, so the application keeps at most `framesInFlight` frames in flight. The public `skipFrameDraw()` (`IllegalStateException` when no frame is being rendered, idempotent within the frame, cleared at the start of every frame) makes the current frame record nothing, so the renderer may be disposed as soon as `render` returns, before the application submits. The frame is always closed; if the screen threw, its exception propagates and a frame-close failure is added to it as suppressed.
    - Input: `processSdlEvent(long)` on the four SDL variants; seven `processGlfw*` methods (window focus, cursor enter, cursor position, mouse button, scroll, key, char) on the GLFW variant, which installs no window callbacks itself. Each throws `IllegalStateException` before `initialize()`. **Tab diversion**: no Tab key event (press, repeat or release, with any modifiers) ever reaches Dear ImGui, whatever the navigation switch, so Dear ImGui's Ctrl+Tab window switching never runs; `NavEnableKeyboard` stays off. A Tab press or repeat without Ctrl, Alt or Super (GUI on SDL) queues a focus move through `divertTab` (back with Shift). The SDL variants classify through `SdlKeyEvents`, the GLFW variant through a private `classifyTab` on GLFW constants mirrored as private constants (`lorisui.imgui` does not require `org.lwjgl.glfw`); both classify with `TabKeyFilter`. All other events are forwarded unchanged.
    - Input-capture queries for hosts: `wantsMouseInput()`, `wantsKeyboardInput()` and `isHoveringScrollablePanel()`, each describing the most recently rendered frame and returning `false` while not initialized. `wantsKeyboardInput()` is Dear ImGui's `WantCaptureKeyboard` (a text or number input is being edited) ORed, while keyboard navigation is enabled, with the capture state that `KeyboardFocus` committed for the last completed frame: an enabled button or combo box with keyboard focus, an input with keyboard focus (pending activation or active), or an expanded combo box (also one expanded with the mouse). The switch is read on every call, so turning navigation off ends that extra capture at once.
    - Keyboard-navigation setters: `setActivationKey(ActivationKey)` and `setKeyboardNavigationEnabled(boolean)` delegate to the backend; they are not gated by the renderer's state (allowed in any state, also before `initialize()` and after `dispose()`), and a `null` key throws `NullPointerException` (from the backend). The renderer owns one `KeyboardFocus` (a private final field), so focus state is per renderer; each frame begins and ends it around `screen.render` (see Data Flow, per frame).
    - SDL text input: the four SDL variants own SDL text input on their window through `SdlTextInput`, updated from Dear ImGui's `WantTextInput` after each frame that closed without an exception (started while a LorisUI text or number input is active, stopped once none is; a refused start is retried after the next frame) and stopped in `dispose()` if started, because imgui-java's SDL3 platform backend does not port Dear ImGui's `Platform_SetImeDataFn` and SDL3 sends no `SDL_EVENT_TEXT_INPUT` until text input is started. Hosts and applications must not start or stop it for the same window. The GLFW variant needs nothing, because GLFW always delivers characters.
    - Dear ImGui UI state (selected tabs, scroll positions, open popups, keyboard focus) starts fresh after `dispose()` + `initialize()`, and `dispose()` also resets the LorisUI keyboard focus (`KeyboardFocus.reset()`) and clears the `ImGuiState.keyboardFocus` slot; state held by LorisUI components and their bindings is unaffected.
  - `SdlTextInput.java`: package-private, final and native-free; the start/stop state machine of SDL text input, built from a `BooleanSupplier` start and a `Runnable` stop, with `update(boolean wanted)` and `release()`. The static `forWindow(long)` binds `SDLKeyboard.SDL_StartTextInput`/`SDL_StopTextInput` to a window through lambdas that touch SDL only when they run. Each SDL variant creates one as the last step of its constructor, after its argument checks, and delegates its `updateTextInput`/`releaseTextInput` hooks to it. `update` starts text input once while it is wanted (a refused start is not recorded, so the next `update` retries) and stops it when it no longer is; `release` stops it only if it was started, after which `update(true)` starts it again (re-initialization, jME re-attach).
  - `TabKeyFilter.java`: package-private, final and native-free; `classify(tab, pressOrRepeat, shift, ctrl, alt, superKey)` returns a nested `Result` (`PASS`, `WITHHOLD`, `MOVE_FORWARD`, `MOVE_BACK`). Every Tab event is withheld (only `PASS` reaches Dear ImGui); a press or repeat without Ctrl, Alt or Super is a move, back with Shift; a release or a modified Tab is withheld without a move. Callers pass the result to `ImGuiRenderer.divertTab`, which checks the navigation switch, and map a foreign window's Tab to `WITHHOLD`.
  - `SdlKeyEvents.java`: package-private and final; `divertTab(renderer, eventPtr)`, used by the four SDL variants' `processSdlEvent` (as `SdlTextInput` is used only by them). It reads `SDL_EVENT_KEY_DOWN`/`KEY_UP` events, identifies Tab with `ImGuiImplSdl3.keyEventToImGuiKey` (exactly the events Dear ImGui would treat as Tab), treats a Tab event of another window (`windowID` other than the renderer's window) like a release (withheld, no move), classifies with `TabKeyFilter` and hands the result to `ImGuiRenderer.divertTab`, which queues the move and returns whether the event must not reach Dear ImGui. It reads native event memory, so it is not unit-tested; the rule is covered through `TabKeyFilter`.
  - `ImGuiFont.java`: final; the ImGui implementation of `Font`, in the `imgui` package so `ImGuiRenderer` can bind it through package-private members. Instances are created only by the renderer's registration methods; there are no static loaders. A handle keeps the font bytes and built glyph ranges for replay (imgui-java passes the glyph-range pointer from a JNI critical array, so keeping the array reachable does not guarantee Dear ImGui a stable address; a known binding limitation), is re-bound on each `initialize()`, and `useFont(Runnable)` throws `IllegalStateException` (without running the code) while its renderer is not initialized or another renderer's context is current.
  - `backend/ImGuiBackend.java`: implements `Backend` and `RendererProvider`; protected constructor that fills the registries `Map<Class<? extends Component>, Renderer<?>>` and `Map<Class<? extends Style>, StyleApplier<?>>` with the built-ins.
    - Keyboard-navigation settings: `public final` `getActivationKey`/`setActivationKey` (default `ENTER`; `requireNonNull`, so `null` throws `NullPointerException` with the message `activationKey`) and `isKeyboardNavigationEnabled`/`setKeyboardNavigationEnabled` (default `true`), stored in plain fields and read by the renderer at every key event and frame. `ENTER` matches Dear ImGui's `Enter` and `KeypadEnter` keys, `SPACE` its `Space` key.
    - Registration: `public final registerRenderer(Class, Renderer)` and `registerStyleApplier(Class, StyleApplier)` replace any existing mapping (built-ins included), reject null arguments (`NullPointerException`) and interface classes (`IllegalArgumentException`, because lookup walks only the superclass chain). `getRenderer`/`getStyleApplier` are `final`: they walk up the superclass chain and throw `IllegalStateException` when nothing matches.
    - Textures: a per-instance cache keyed by path and the three masks, with keys normalized to class-path style (a leading `/` is an alias of the bare path). `public final loadTexture(...)` (two overloads, implementing the `RendererProvider` methods) creates a texture on a miss through `protected abstract createTexture(normalizedPath, maskedR, maskedG, maskedB)`; failed loads are not cached. `public final unloadTextures()` calls `protected abstract deleteTexture(TextureData)` once per distinct texture, image and canvas textures alike, always empties the cache, the canvas map and the drawn set and drops the scratch buffer (every deletion runs through `DeferredRelease.runAll` in a private `deleteTextures` helper shared with eviction: first failure rethrown, later ones suppressed), and throws `IllegalStateException` while the backend is drawing (`render` sets a private `drawing` flag). The concrete `renderTexture(long id, ...)` maps `ImageMode` variants to ImGui draw calls with an exhaustive pattern `switch`; `Repeat` is drawn as a grid of `ImGui.image` tiles placed with `sameLine` (spans from `TextureTiling`, partial UVs on edge tiles), like the *Resize modes, so it does not depend on the texture's wrap mode. The class is abstract with a protected constructor, and all four concrete backends are final: `ImGuiOpenGlBackend` pairs with the two GL3 renderers, `ImGuiOpenGlEsBackend` with `ImGuiSdlGles3Renderer`, `ImGuiSdlGpuBackend` with `ImGuiSdlGpuRenderer` and `ImGuiVulkanBackend` with `ImGuiSdlVulkanRenderer`.
    - Canvas textures: `public final loadTexture(Canvas)` (implementing `RendererProvider.loadTexture(Canvas)`; `NullPointerException` naming `canvas`) records the canvas in an identity set of drawn canvases and keeps one texture per canvas in an `IdentityHashMap`. Without an entry it takes the whole image (`takePixelUpdate(true)`), converts it with `RgbaPixels` into a reusable direct scratch `ByteBuffer` (`ByteBuffer.allocateDirect`, grown to the largest upload, never shrunk, position 0 and limit `w * h * 4`) and calls `protected abstract createCanvasTexture(width, height, rgbaPixels)`; a failed create stores nothing, so the next load creates again. With an entry it takes the changed rectangle (`takePixelUpdate(false)`) and, if there is one, calls `protected abstract updateCanvasTexture(texture, x, y, width, height, rgbaPixels)`; any `Throwable` on that path marks the entry "whole image due" and is rethrown, and the flag is cleared only after a successful update, so taken but unuploaded pixels are never lost. Both hooks receive tightly packed RGBA rows, top row first, must not keep the buffer, create non-sRGB (UNORM) textures sampled nearest-neighbor where the renderer variant allows it, clamped to the edge, and may run during a frame. **Eviction**: an outermost `render` (one entered while `drawing` was `false`) first deletes, before setting `drawing`, the textures of canvases not drawn since the previous outermost `render` and clears the drawn set (also when a deletion fails; the failure propagates before anything is drawn); nested renders never evict. A canvas drawn in render N and not in render N+1 keeps its texture through N+1, loses it at the start of N+2, and is re-created from the whole image when drawn again. Eviction assumes one outermost `render` per frame, and a subclass overriding `render` must call `super.render` (both in the class Javadoc).

A frame change drops entries not updated in the previous frame (a gesture never survives a skipped frame), and a second update in the same frame does nothing. A disabled canvas ends its gesture and reports nothing. A gesture ends without an event when its button's released bit is set or its down bit is clear. With no gesture, a hovered press of the lowest-ordinal clicked button starts one and runs `click()`; other buttons are ignored until it ends.   - `impl/ImGuiState.java`: internal, final; global state shared by the renderer, renderers and fonts (`hoveringScrollableWindow`, set by scrollable top-level panels and by interactive canvases while hovered and read by hosts only through `ImGuiRenderer.isHoveringScrollablePanel()`, whose Javadoc and that of the four LWJGL displays name "a scrollable panel or an enabled canvas", `currentContextPtr`, compared by `ImGuiFont.useFont` without a per-frame allocation, and the `volatile` `keyboardFocus` slot: the rendering renderer's `KeyboardFocus`, set only inside `screen.render` of a frame with keyboard navigation enabled and `null` otherwise, so renderers that find it `null` behave exactly as without navigation; the slot is JVM-global, so it is valid only for the renderer whose frame is running, one frame at a time)
  - `impl/KeyboardFocus.java`: internal (public in the non-exported `imgui.impl`, so the renderers in `renderer.impl` reach it), final and native-free; the LorisUI keyboard-focus model, one per `ImGuiRenderer`, fed only plain ints and booleans. It keeps the committed state of the last completed frame (draw order of the registered elements with their kind, enabled state and scope, the scopes, the active scope, the anchor, whether the anchor has keyboard focus, a pending input activation, the capture flag), the net count of queued moves (`queueMove(±1)` per Tab event, collapsed) and the working state of the current frame. Focus has two levels: the **anchor** only decides where the next Tab continues (a left click on a registered element sets it, also on a disabled button; a click on nothing clears it), and **keyboard focus** (from Tab, Up/Down in a combo, or a return to a combo) adds the look, activation and capture. `beginFrame(activationPressed, escapePressed, upPressed, downPressed, mouseClicked)` restores the committed state and applies, in order, the net Tab moves (cycling the enabled members of the active scope with wrap-around; from an anchor outside it, or on the scope's owner, Tab starts at the first and Shift+Tab at the last; nothing happens with an empty order, such as before the first completed frame), Up/Down (only while a combo scope is active), then Escape (close the active combo scope and return focus to its owner, otherwise clear focus and anchor), else the activation key (only on a keyboard-focused element of the active scope). Renderers call `register(id, Kind, enabled)` (`BUTTON`, `INPUT`, `COMBO`) or `registerComboItem(id, selected)`, which return result bits (`FOCUS_LOOK`, `KEYBOARD_FOCUS_STARTED`, `ACTIVATE`, `CLOSE_COMBO_SCOPE`, `TAKE_INPUT_FOCUS`, `RELEASE_INPUT`), `reportClick(id)` (the last report in the frame wins, so the innermost element), `reportInput(id, active)`, and `pushPopupScope()`/`pushComboScope(ownerId)`/`popScope()`. `endFrame()` applies the end rules in a fixed order: clicks; an anchor not drawn this frame is cleared; input activation (an input keeps keyboard focus while pending activation, which lasts the request frame and the frame after it, or while active; otherwise only the anchor); a combo opened from the keyboard focuses its selected item, or its first; and last, a focus or anchor outside the active scope (the deepest open scope, among equals the one drawn last; a combo scope whose close was requested counts as closed from the request frame) is cleared, except the scope's owner. It then commits the frame, including the capture flag. `discardFrame()` keeps the last completed state (the moves the frame consumed stay dropped), `reset()` clears everything including queued moves, and `wantsCapture()` reports the committed capture. A Tab move emits `RELEASE_INPUT` to the input it takes the anchor from; Escape and clicks never do. An input gets neither the look nor the activation key (Dear ImGui draws its caret and handles Enter). A button that is disabled while focused keeps the anchor but loses the look, activation and capture, and its re-enable while still focused is a new focus start.
  - `impl/ClassPathResources.java`: internal; opens class-path resources through the class loader, with a leading `/` optional (used by the renderer's font registration and `DecodedImage`)

- **Purpose**: integrates the ImGui backend into jMonkeyEngine 3.

It owns a private backend and renderer variant chosen at construction from `context.getSettings().getRenderer()`: `ImGuiOpenGlBackend` + `ImGuiSdlGl3Renderer` for `OPENGL`, `ImGuiOpenGlEsBackend` + `ImGuiSdlGles3Renderer` for `OPENGL_ES`. A private static factory builds the pair with an exhaustive `switch` expression and returns a private record that also carries the variant's `render` (captured as a private functional interface, because the variants share no `render` method) and the SDL event listener for the variant's `processSdlEvent`. The constructor checks a null context, a null viewport, the `LwjglWindow` cast (`ClassCastException`) and an unsupported renderer (`IllegalStateException`), in that order, before anything is created; the public API is unchanged. It also owns a `ScreenManager` and a `ResourceBundleKeyResolver`, and delegates screens (`addScreen`, `setCurrentScreen`), resource bundles (`setResourceBundle`), fonts (`registerFont*`, returning `Font`) and `registerRenderer`/`registerStyleApplier` to them. Font, renderer and style-applier registration is allowed only while the display is not attached, not while its release is pending or running (a `releasing` flag covers the teardown itself, for example registration from the `onEndScreen` it fires), and not after a failed initialization. The keyboard-navigation setters `setActivationKey`/`setKeyboardNavigationEnabled` delegate to the private backend without that gate (any state, also after a failed initialization; the settings persist across re-attach); its class Javadoc has a "Keyboard navigation" section and lists the extra key capture. The constructor has no Dear ImGui side effects. Each frame, `postQueue` reads the window size in logical window coordinates with `SDL_GetWindowSize` (an `IllegalStateException` with the SDL error if that fails) and passes it to the renderer; jME's camera and `reshape` sizes are not used. The display's viewport must therefore render to the window; offscreen viewports (render-to-texture, or a `FilterPostProcessor` on the same viewport) are documented as unsupported, as are jME's emulated display-scale modes (an `AppSettings` display-scale mode above 1). The sRGB framebuffer that the sRGB textures need comes from jME's gamma correction, which is on by default, for both renderers. The display has no text-input code of its own: its SDL variant starts and stops SDL text input on the jME window (jME 3.10.0-beta3 does not start it), as the class Javadoc states together with the interference caveat. The display is re-attachable; see Screen Lifecycle.
  - `ImGuiInputSystem.java`: package-private, final; a jME `RawInputListener` that marks mouse and key events consumed using only the input-capture queries of `ImGuiRenderer`, so it works with either variant. Key events go through its `DeliveredKeys` (keyed by the jME key code), which the display clears when it removes its listeners. jme3 has no `imgui.*` imports.
  - `DeliveredKeys.java`: package-private, final and native-free; records for each held key whether a key-down of its current hold (the press or a repeat) reached the application, and decides the key's release by that record alone: the release reaches the application exactly when such a key-down did, whatever the capture at the moment of release, and the record is removed. Only the release of a key with no recorded key-down follows the current capture; key-downs always follow it. `clear()` forgets every held key. `lorisui.lwjgl` keeps a copy (without `clear()`, because its displays cannot be reused after `close()`), since jme3 cannot depend on it; the duplication is the explicit exception for tiny host input helpers in `standards/architecture/modules.md` (both copies unit-tested, each copy's Javadoc names the other).

### loris-ui-lwjgl (`lwjgl/`)
- **Purpose**: hosts LorisUI in an application's own LWJGL window and loop, without a game engine: SDL3 with OpenGL 3, SDL_GPU or Vulkan, or GLFW with OpenGL 3.
- **JPMS module**: `lorisui.lwjgl`, exporting `com.ivan1pl.lorisui.lwjgl` (with `package-info.java` and a module doc comment, both with a "which display to use" table, the typical setup per display, the sRGB requirement and the Vulkan notes), `requires transitive lorisui.imgui`, `requires org.lwjgl.glfw`, `requires org.lwjgl.sdl` and a plain `requires static org.lwjgl.vulkan` (never `transitive`; a modular Vulkan application `requires org.lwjgl.vulkan` itself). It compiles against `lwjgl`, `lwjgl-sdl`, `lwjgl-glfw` and `lwjgl-vulkan` as `compileOnly`; at runtime the first three come with imgui-java (GLFW and SDL natives only for linux, macos, macos-arm64 and windows), and a Vulkan application adds `lwjgl-vulkan` itself (the system Vulkan loader on Linux and Windows, LWJGL's MoltenVK natives on macOS). There is no `impl` package; shared host logic is package-private in the exported package.
- **Key Files**:
  - `ImGuiLwjglDisplayBase.java`: package-private, abstract, `<RendererType extends ImGuiRenderer>`. It owns the same four collaborators as the jME display (the backend, the renderer variant, a `ScreenManager`, a `ResourceBundleKeyResolver`) plus a `DeferredRelease`, all in private fields with package-private accessors, and declares the public registration, screen and bundle methods the four displays inherit, plus the keyboard-navigation setters `setActivationKey`/`setKeyboardNavigationEnabled`, which delegate to the backend without the registration gate (any state, also before `initialize()` and after `close()`). Each display's class Javadoc has a "Keyboard navigation" section, and the SDL displays' `processEvent` and the GLFW display's input list name the extra key capture. Package-private template methods (`initializeDisplay`, `renderFrame`, `runDeferred`, `closeDisplay`) implement the shared `initialize`/`close` state machine; the subclasses supply `setUp()`, and the GLFW display overrides the no-op `releaseInput()`. The release runs `DeferredRelease.runAll(deactivate, releaseInput, renderer::dispose, LorisScreen::shutdownLayoutUpdates)`.
  - `ImGuiLwjglSdlInput.java`: package-private, final; the SDL event consumption rule shared by the three SDL displays. Key events go through its `DeliveredKeys` keyed by the SDL scancode.
  - `DeliveredKeys.java`: package-private, final and native-free; the symmetric key-release rule shared by `ImGuiLwjglSdlInput` and the GLFW display; the same as jme3's copy apart from `clear()` (a per-host duplicate under the exception in `standards/architecture/modules.md`). The GLFW display keys it by the key token, or by the complemented scancode (`~scancode`, never equal to a token) for a key without one, because GLFW may synthesize a release with another scancode (the Windows dual-Shift workaround, releases on focus loss).
  - `ImGuiLwjglSdlGl3Display.java`: final, `AutoCloseable`; `ImGuiLwjglSdlGl3Display(long sdlWindow)` (`IllegalArgumentException` for `0`, no native calls), with an `ImGuiOpenGlBackend` and an `ImGuiSdlGl3Renderer`. The application keeps the window, the GL context and the loop: it calls `initialize()` with the context current, forwards every SDL event to `processEvent(long)` (returns whether the UI consumes it, using the `ImGuiInputSystem` rule; `false` while not initialized), calls `render(width, height)` once per frame in logical window coordinates (`SDL_GetWindowSize`) after clearing and before swapping, and calls `close()` before destroying the context or window. All precondition checks run before any native call.
  - `ImGuiLwjglGlfwGl3Display.java`: final, `AutoCloseable`; `ImGuiLwjglGlfwGl3Display(long glfwWindow)` (`IllegalArgumentException` for `0`; no GLFW call and no callback object until `initialize()`), with an `ImGuiOpenGlBackend` and an `ImGuiGlfwGl3Renderer`. Input is chained, not forwarded by the application: `initialize()` sets GLFW's global monitor callback to `null` around the renderer's `initialize()`, then gives the application's monitor callback back and frees Dear ImGui's stub, and installs seven own window callbacks (window focus, cursor enter, cursor position, mouse button, scroll, key, char) in front of the application's, which must be set before `initialize()`. Each event goes to Dear ImGui first and to the application's previous callback only when the UI does not consume it (the `ImGuiInputSystem` rule; focus and cursor enter are never consumed). Release restores the application's callbacks, keeping any newer callback the application set after `initialize()`, never frees the application's wrappers, and frees the display's own seven. `close()` called during one of the display's callback dispatches throws `IllegalStateException` before any state change; a failure thrown during a dispatch (by LorisUI or the application's chained callback) is caught, later events are dropped, and the next `render()` or `close()` rethrows it (`RuntimeException`/`Error` as-is, others wrapped in `RuntimeException`). The package-private `dispatch(Runnable)` seam carries these rules. `render(width, height)` takes the `glfwGetWindowSize` size; there is no text-input toggling, because GLFW always delivers characters.
  - `ImGuiLwjglSdlGpuDisplay.java`: final, `AutoCloseable`; `ImGuiLwjglSdlGpuDisplay(long sdlWindow, long gpuDevice)` (`IllegalArgumentException` for a `0` window, checked first, or a `0` device; it never destroys either), with an `ImGuiSdlGpuBackend` and an `ImGuiSdlGpuRenderer`. `processEvent` works as in the SDL3 + OpenGL 3 display; SDL text input is handled by the renderer variant. `render(width, height, commandBuffer, targetTexture)` throws `IllegalArgumentException` for a `0` command buffer before any state check; a `0` target (minimized window) still processes input and builds the frame. The application claims the window for the device and sets an `SDR_LINEAR` swapchain before `initialize()`, acquires the command buffer and swapchain texture, clears and submits around each `render`, and calls `close()` before releasing the window from the device or destroying the device.
  - `ImGuiLwjglSdlVulkanDisplay.java`: final, `AutoCloseable`; `ImGuiLwjglSdlVulkanDisplay(long sdlWindow, VkDevice device, int queueFamilyIndex, VkQueue queue, int colorAttachmentFormat, int framesInFlight)` checks the `0` window first, then lets `ImGuiVulkanBackend` and `ImGuiSdlVulkanRenderer` check the rest (family, device, queue and their mismatch, then format and frame count), makes no native calls and never destroys the window or any Vulkan object. `processEvent` works as in the SDL3 + OpenGL 3 display; SDL text input is handled by the renderer variant. `render(width, height, commandBuffer, targetImageView)` runs its own state checks first (`IllegalStateException` when closed or not initialized) and leaves the command-buffer checks to the renderer (`NullPointerException` for `null`, then `IllegalArgumentException` for another device) instead of repeating them, so the display keeps no device reference of its own. It marks the frame in progress around the renderer's `render` and restores the previous value afterwards instead of clearing it, so a nested `render` from a component callback, which the renderer rejects, cannot clear the flag of the frame still running (a `close()` after it would otherwise let that frame draw). `close()` called during that frame (a component callback such as "Hide UI", or a screen hook) first calls `skipFrameDraw()`, so the frame records no LorisUI commands, and the release (`onEndScreen`, stopping text input, `vkDeviceWaitIdle`, destroying every LorisUI Vulkan object) runs when `render` returns; the application submits the command buffer as usual. A close between `render` and that frame's submit is unsupported. The colour-attachment format is fixed for the display's lifetime, and because closing is final, an application whose swapchain format changes creates a new display and registers everything again. The application creates the instance and device for Vulkan 1.3 with `dynamicRendering`, an sRGB swapchain and its frames, transitions and clears the image before each `render`, transitions, ends, submits and presents after it, passes target `0` while the swapchain extent is smaller than the window's pixel size, and calls `close()` before destroying the device, the image views passed to `render` or the window.

## Data Flow

**Setup**
1. The host app creates a display (`ImGuiJmeDisplay(context, inputManager, guiViewPort)`, `ImGuiLwjglSdlGl3Display(sdlWindow)`, `ImGuiLwjglGlfwGl3Display(glfwWindow)`, `ImGuiLwjglSdlGpuDisplay(sdlWindow, gpuDevice)` or `ImGuiLwjglSdlVulkanDisplay(sdlWindow, device, queueFamilyIndex, queue, colorAttachmentFormat, framesInFlight)`), registers fonts, custom renderers and style appliers and resource bundles, adds `LorisScreen`s and selects the current screen. Nothing native happens yet; the jME display has already chosen its GL3 or GLES3 pair from jME's renderer setting. The GLFW application also sets its own input callbacks; the SDL_GPU application creates the device, claims the window for it and sets an `SDR_LINEAR` swapchain; the Vulkan application loads one Vulkan library for SDL and LWJGL, creates the window with `SDL_WINDOW_VULKAN`, an instance and device for Vulkan 1.3 with `dynamicRendering`, and an sRGB swapchain with its per-frame resources.
2. The display is initialized: jME calls `initialize` lazily, on the first frame (or window resize, through `RenderManager.notifyReshape`) after the display is added to a viewport; the LWJGL application calls `initialize()` itself. The renderer creates its context, replays the fonts and sets up its variant's platform and renderer Impl objects (the GLES3 port creates its GL objects eagerly here, and the Vulkan port builds its pipeline and uploads the font atlas on the queue); the jME display then registers its input listeners, and the GLFW display gives the application's monitor callback back and chains its seven input callbacks. Finally `ScreenManager.activate()` fires `onStartScreen()` on the current screen.

**Per frame** (jME `postQueue`, LWJGL `render`):
1. The host passes the screen size in logical window coordinates: the jME display queries `SDL_GetWindowSize` each frame, and the LWJGL application passes the size to the display's `render` (`SDL_GetWindowSize` for the SDL displays, `glfwGetWindowSize` for the GLFW display). The SDL_GPU application first acquires a command buffer and the swapchain texture and clears the texture in its own pass, then passes both to `render(width, height, commandBuffer, targetTexture)`. The Vulkan application recreates the swapchain if its desired extent changed or it is out of date, waits on the frame slot's fence, acquires an image, begins the slot's command buffer, transitions the image to `COLOR_ATTACHMENT_OPTIMAL` and clears it (synchronized in the colour-attachment-output stage), then passes the command buffer and the image view to `render(width, height, commandBuffer, targetImageView)`, or `0` as the view while the swapchain extent is smaller than `SDL_GetWindowSizeInPixels`. The renderer variant's `render` makes its context current and starts an ImGui frame. **Keyboard-focus begin step**: if keyboard navigation is off, the renderer resets its `KeyboardFocus` (so turning navigation off clears the focus at the next rendered frame) and leaves `ImGuiState.keyboardFocus` `null`; otherwise it calls `KeyboardFocus.beginFrame` with the activation key (`Enter`/`KeypadEnter` or `Space`, pressed without repeat), Escape (without repeat), Up and Down (with repeat), each only without Ctrl, Alt or Super, and the left mouse click, then publishes the helper in `ImGuiState.keyboardFocus`.
2. `LorisScreen.render(backend, w, h, resolver)`:
   - If the previous `layout()` call threw or returned `null`, the failure is rethrown once as an `IllegalStateException` (cause = original failure) and nothing is rendered in that call; later frames render the last successful layout. Hosts should treat it as fatal.
   - If the layout was invalidated (`setLayoutNeedsUpdate(true)`, callable from any thread; the update flag is an `AtomicBoolean`), `layout()` is scheduled on the shared single-thread daemon layout worker (`lorisui-layout`), which is created lazily and stopped by `LorisScreen.shutdownLayoutUpdates()`. The new `List<Component>` is published through a `volatile` field and replaces `content` asynchronously; in the meantime the previous content keeps rendering (an empty list before the first layout).
   - Calls `backend.render(w, h, content, resolver)`.
3. `ImGuiBackend.render` looks up the `Renderer` for each component, and each renderer emits ImGui calls. Containers (Panel, TabbedPanel, Popup) recurse through `RendererProvider`, passing the screen size unchanged, so size and content functions receive the screen's width and height at every nesting level, not the parent's size, and so do the position functions of top-level panels and popups (a nested panel is placed by its parent's layout; `TabbedPanel` tab-label functions, called once at build, receive the tab button's size). A panel with padding draws its content in an inner child window inset from each edge by that side's padding (top, bottom, left, right), after its background and Button hit area; the screen size is still passed down unchanged. Styles are applied through `StyleApplier`s. Text keys are resolved through `BundleKeyResolver`. Images are loaded or fetched from the backend's cache through `RendererProvider.loadTexture(...)` and drawn with `RendererProvider.renderTexture(...)` according to their `ImageMode` (`Repeat` as a tile grid). On SDL_GPU, a texture loaded during the build is uploaded with its own command buffer, submitted at once, so it executes before the frame's buffer; on Vulkan, it is uploaded with its own command buffer submitted to the application's queue and waited for. The GL backends restore the texture binding and unpack state they change, so jME's GL state cache stays valid when an image loads mid-frame. A missing or unreadable image (`Image` or panel `Background`) makes the renderer throw a `RuntimeException` wrapping the `IOException`; failures are not cached, so the screen's render fails again on every draw. **Canvas upload**: an outermost `ImGuiBackend.render` first releases the textures of canvases not drawn since the previous one (before anything is drawn). A `Canvas` is drawn by `CanvasRenderer`, which first reads the mouse state and runs the canvas's click, drag and wheel callbacks through `CanvasInputTracker`, then calls `RendererProvider.loadTexture(canvas)`: the backend takes the changed rectangle from the canvas (or the whole image for a new or repaired texture), packs it into RGBA and uploads it synchronously (GL and GLES with `glTexSubImage2D` inside the restored upload state, SDL_GPU with its own submitted command buffer, Vulkan with `VulkanTextures.update` on the application's queue, waited for), so the image drawn this frame includes every change made before the call, from any thread or from the callbacks. While the slot is set, the focusable renderers register their elements in draw order, push and pop popup and combo scopes, report clicks and input activity, and act on the result bits (focus look, `hover()`/`click()` through `ButtonInputTracker`, opening or closing a combo, `setKeyboardFocusHere`/`clearActiveID` on inputs).
   - **Keyboard-focus end step**: right after `screen.render` returns, before `ImGui.render` and the draw callback, the renderer calls `KeyboardFocus.endFrame()`, which commits the frame's focus state and capture flag. If `screen.render` throws, `discardFrame()` keeps the last completed state (queued moves the frame consumed stay dropped; callbacks that already ran are not undone) before the frame is closed and the exception propagates. A failure while drawing or updating text input after the end step does not roll the committed state back, and a Vulkan frame with `skipFrameDraw()` is a normal completed frame. The slot is cleared in the frame's `finally`.
4. ImGui draw data is rendered by the variant: the GL3 variants draw into the current OpenGL framebuffer and the GLES3 variant into the current OpenGL ES framebuffer (restoring the GL state it touched), and the application (or jME) swaps afterwards; the SDL_GPU variant runs `prepareDrawData` outside any pass and then draws in its own `LOADOP_LOAD`/`STOREOP_STORE` pass into the target texture on the application's command buffer (nothing when the target is `0`), and the application submits the buffer afterwards; the Vulkan variant records a colour-attachment barrier and its own `LOAD`/`STORE` dynamic rendering into the image view on the application's command buffer (nothing when the view is `0`, when `skipFrameDraw()` was called, or when the framebuffer is empty), and the application transitions the image for presenting, ends, submits (resetting the buffer instead if `render` threw) and presents. The renderer ends the ImGui frame even when `LorisScreen.render` throws; the screen's exception propagates, with any frame-close failure suppressed.
5. After a frame that closed without an exception, the renderer reads Dear ImGui's `WantTextInput` and passes it to its `updateTextInput` hook: the SDL variants hand it to their `SdlTextInput`, which starts SDL text input for the window while a text or number input is active and stops it once none is; the GLFW variant does nothing. A frame whose screen or draw step threw skips this step, and a later frame catches up.

**Input**: SDL events reach ImGui IO through the SDL variants' `processSdlEvent`. In jME, an SDL event listener (bound to the chosen variant at construction) forwards them, and in parallel `ImGuiInputSystem` marks jME raw input events consumed when `wantsMouseInput()`/`wantsKeyboardInput()` report that the UI wants them; mouse-wheel events are consumed only while `isHoveringScrollablePanel()`, which is also true while the pointer is over an enabled canvas that takes input (no host code changed for canvases). With the three SDL displays the application passes each event to `processEvent`, which forwards it and applies the same rule to its return value. The GLFW display's chained callbacks forward each event to the matching `ImGuiGlfwGl3Renderer.processGlfw*` method and call the application's previous callback only when the same rule says the UI does not consume it. SDL text input, without which SDL3 delivers no typed characters, is started and stopped by the SDL variants for every SDL host, including jME (step 5 of the frame); no host toggles it. **Tab diversion**: the variants' input entry points (`processSdlEvent` through `SdlKeyEvents`, `processGlfwKey` through the private `classifyTab`, both through `ImGuiRenderer.divertTab`) withhold every Tab key event from Dear ImGui and, while keyboard navigation is enabled, turn a Tab press or repeat without Ctrl, Alt or Super (of the renderer's own window, for SDL) into a queued focus move that the next frame's begin step applies; the activation key, Escape and Up/Down reach Dear ImGui as usual and are read from its key state in the begin step. **Host capture**: hosts keep using `wantsKeyboardInput()` unchanged; it now also covers keyboard focus (an enabled button or combo box with keyboard focus, an input with keyboard focus, an expanded combo box) while navigation is enabled, so the jME `ImGuiInputSystem`, the SDL displays' `processEvent` and the GLFW display's key and char callbacks consume all key events then, and pass them to the game once the focus is cleared (Escape, a click on nothing). **Key releases**: every host decides a key's release by the key's own key-downs, not by the capture at the moment of release: the release reaches the game exactly when the key's press or a repeat during the same hold reached it (tracked per physical key by the package-private `DeliveredKeys` in `jme3` and `lwjgl`). So a key held while the capture switches on (the first Tab, a movement key held while Tab lands on a button) never stays down in the game, and a key pressed while the UI captured (Escape that clears the focus, a key typed into an input) never sends the game a release it never saw pressed, which matters to games acting on key-up. Only the release of a key with no recorded key-down follows the capture; key-downs and character or text events follow the capture alone. Component callbacks (for example button actions and hover actions) run during rendering on the host's UI thread.

**Teardown**: removal (jME `cleanup`) or `close()` (LWJGL) → `ScreenManager.beginDeactivation()` → `DeferredRelease.request()`, deferred to the end of the outermost operation if requested during a frame, a screen switch or a hook → `ScreenManager.deactivate()` (`onEndScreen`) → GLFW display's callbacks restored and freed → renderer `dispose()` (context current → SDL text input stopped (SDL variants, if started) → device idle (`SDL_WaitForGPUIdle` for SDL_GPU, `vkDeviceWaitIdle` for Vulkan) → textures, image and canvas (for Vulkan, each texture waits for the queue to go idle and is destroyed, and the two shared samplers and the descriptor-set layout go with the last one) → renderer Impl (Gl3, Gles3, SdlGpu3 or Vulkan) → platform Impl (Sdl3 or Glfw) → context → font handles unbound) → `LorisScreen.shutdownLayoutUpdates()`. Each step runs even when an earlier one fails (`DeferredRelease.runAll`); the first failure propagates and later ones are suppressed. A Vulkan display closed during its own frame first calls `skipFrameDraw()`, so that frame records no LorisUI commands and the deferred release can destroy the Vulkan objects as soon as `render` returns, before the application submits. The SDL_GPU application then waits for the GPU to go idle, releases the window from the device and destroys the device, the window and SDL; the Vulkan application waits for the device to go idle and destroys its frame resources, swapchain, device, surface and instance, then the window; the GLFW application frees its own callbacks after `close()`.

## Screen Lifecycle
All display calls and screen hooks run on the host's UI thread (the jME render thread, or the thread that owns the window and its GL context, GPU device or Vulkan device; for GLFW, the main thread). The Vulkan display and backend submit uploads to the application's queue from that thread, so an application that submits to the same queue from other threads serializes those submissions with LorisUI calls. No display implements `BundleKeyResolver`; each passes its internal `ResourceBundleKeyResolver` to the renderer, and applications that need key resolution create their own resolver.

**Shared rules (`ScreenManager`)**:
- A screen receives `onEndScreen()` only if its `onStartScreen()` returned normally, and at most once per start; a screen whose `onStartScreen()` threw counts as not started. Hook exceptions propagate out of the method that fired them.
- `addScreen(name, screen)`: `NullPointerException` for null arguments, `IllegalStateException` for a name that is already registered. Fires no hooks and is allowed from inside hooks.
- `setCurrentScreen(name)`: `IllegalStateException` from inside a hook, then `NullPointerException` for null and `IllegalStateException` for an unknown name, all before any state change; switching to the current screen does nothing. While the display is not initialized it only records the name. While initialized the switch is immediate: the new screen becomes current, then `onEndScreen()` fires on the old screen and `onStartScreen()` on the new one, during the call; the new screen is drawn from the next frame. The switch always completes: if the old screen's `onEndScreen()` throws, the new screen is still started, then the end failure propagates (a different start failure is added to it as suppressed). It may be called from a component callback, in which case the old screen finishes drawing the current frame.
- **Re-entrancy guard**: `setCurrentScreen`, `activate()` and `deactivate()` called from inside `onStartScreen()`/`onEndScreen()` throw `IllegalStateException` before changing state. Screens switch later instead, for example from a component callback.
- **Two-phase deactivation**: `beginDeactivation()` makes the manager inactive without a hook (allowed inside hooks; a switch or activation already in progress still completes). From then on `setCurrentScreen` only records the choice, and `deactivate()` fires `onEndScreen()` on the screen started before, even if another screen has been selected since; it also ends a started screen while the manager is already inactive. `activate()` throws `IllegalStateException` while a begun deactivation has not been completed with `deactivate()`.

**Deferred teardown (all hosts)**: each display runs its operations that can call application code (rendering a frame, `setCurrentScreen`, and the activate step of `initialize`) through its `DeferredRelease`. A teardown request stops the display at once (the jME display removes its input listeners and `isInitialized()` returns `false`; an LWJGL display is closed, the SDL displays' `processEvent` returns `false` and the GLFW display passes every event to the application's callbacks), calls `ScreenManager.beginDeactivation()` and then `DeferredRelease.request()`. If an operation is running (a component callback, such as the examples' "Hide UI" button, or a screen hook), the release runs after the outermost one, once the frame has closed or the hook has returned. The renderer is therefore never disposed inside a frame and `deactivate()` never runs inside a hook. While the release is pending, `setCurrentScreen` fires no hooks and only records the choice; the recorded screen becomes current and, on the re-attachable jME display, starts on the next attach. Release failures propagate from that operation, or are added as suppressed to its exception if it is already throwing.

**jME host (`ImGuiJmeDisplay`)**:
- `initialize`: throws `IllegalStateException` if an earlier initialization failed, if the display is already initialized or its deferred release has not completed, or if no current screen is set, all before any side effect. If setting up the renderer or registering the listeners fails, it marks the display failed, removes the listeners, disposes the renderer and rethrows, so jME's per-frame retry fails fast; no hooks fire and the display is permanently unusable (registration also throws). Otherwise it ends with `ScreenManager.activate()` (`onStartScreen()`); a throwing `onStartScreen()` propagates and the display stays initialized.
- `postQueue` returns early when the display is not initialized, because jME iterates a snapshot of the viewport's processors and can still call a display removed earlier in the same frame.
- `cleanup`: jME calls it when the display is removed from its viewport (`ViewPort.removeProcessor`/`clearProcessors`). A no-op unless initialized. Otherwise it tears down (deferred if an operation run through its `DeferredRelease` is in progress).
- **Re-attach**: a cleaned-up display can be added to a viewport again. It re-creates the context, replays the fonts (the `Font` handles stay valid) and starts the current screen again; screens, bundles, renderers and style appliers stay registered, and fonts, renderers and style appliers can be registered again between removal and re-attach. Dear ImGui UI state starts fresh. Re-adding the display in the same callback that removed it is safe, because jME initializes it on a later frame, after the deferred release.
- Only one display may be attached at a time.
- **Application exit**: jME does not call `cleanup` on exit. Applications that want `onEndScreen()` and the native release at exit remove the display themselves; `LorisJme3Example` overrides `destroy()` and calls `guiViewPort.removeProcessor(imGuiJmeDisplay)` (only if attached, since `removeProcessor` calls `cleanup` even for a processor that is not attached) before `super.destroy()`.

**LWJGL host (`ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay`, `ImGuiLwjglSdlVulkanDisplay`)**: the rules below come from the shared base and apply to all four displays unless noted.
- `initialize()`: `IllegalStateException` if closed, already initialized, or no current screen is set, all before side effects. If the renderer fails to initialize, the exception propagates, the renderer has released what it set up, and the display stays uninitialized and can be retried (after a failure caused by a registered font, create a new display instead). Then it marks itself initialized and calls `ScreenManager.activate()`; a throwing `onStartScreen()` propagates and the display stays initialized.
- `render` throws `IllegalStateException` when not initialized or closed; the SDL displays' `processEvent` returns `false` then. The SDL_GPU display's `render` checks for a `0` command buffer first (`IllegalArgumentException`); the Vulkan display's `render` checks its own state first and then lets the renderer check the command buffer (`NullPointerException` for `null`, then `IllegalArgumentException` for another device).
- Text input: the three SDL displays (like the jME display) have no text-input step, because the SDL variants own SDL text input (see `loris-ui-imgui`); the GLFW display needs none, because GLFW always delivers characters.
- `close()`: idempotent and **final** (`AutoCloseable` semantics): the display is marked closed at once, so later `register*`, `initialize` and `render` throw, while `addScreen`, `setCurrentScreen` and `setResourceBundle` only record. If initialized, it releases immediately, or deferred when called during a frame, a screen switch or a hook. To show UI again, the application creates a new display. Closing before `initialize()` only marks the display closed.
- GLFW display only: `close()` called during one of its GLFW callback dispatches (from the application's chained callback, or from a hook or component code that callback runs) throws `IllegalStateException` before any state change, because the release would destroy cursors and free the executing callback stub inside a GLFW callback; the application requests the close there and calls `close()` after `glfwPollEvents` returns. A failure thrown during a dispatch is kept, later events reach neither the UI nor the application, and the next `render()` (before drawing) or `close()` (after closing, with a release failure suppressed) rethrows it once. Closing from a component callback during `render()` ("Hide UI") is deferred as usual. `render()` must not be called from a GLFW callback.
- Vulkan display only: `close()` during one of its frames (from a component callback or a screen hook; the display tracks a frame-in-progress flag around the renderer's `render`) calls the renderer's `skipFrameDraw()` before closing, so that frame records no LorisUI commands and the deferred release (`vkDeviceWaitIdle`, then destroying the Vulkan objects) runs when `render` returns; the application submits the command buffer as usual. Closing between `render` and that frame's submit is unsupported, because the recorded commands use the display's resources. Its `initialize()` fails with `IllegalStateException` when the device does not expose Vulkan 1.3 functions.
- Only one display may be initialized at a time.

## Extension Points
- **New built-in component**: add a class to `api/component` (with a Builder), add a renderer in `imgui/renderer/impl`, and register it in the `ImGuiBackend` constructor.
- **New built-in style**: add a class to `api/component/style`, add an applier in `imgui/renderer/style/impl`, and register it in the `ImGuiBackend` constructor.
- **Custom components or styles (library users)**: extend `Renderer`/`StyleApplier` and register them with `registerRenderer`/`registerStyleApplier`, either on an `ImGuiBackend` or on a display (`ImGuiJmeDisplay`, `ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay`, `ImGuiLwjglSdlVulkanDisplay`) before it is initialized. A registration replaces any existing mapping, including a built-in one, and subclasses without their own mapping use the nearest registered ancestor. Renderers load and draw textures through the `RendererProvider` they receive. A custom renderer calls Dear ImGui directly, so its code adds imgui-java to its own build and, on the module path, `requires imgui.binding`. The displays keep their backend private; registration is the only customization path, which also covers the former "custom backend in the jME host" need. Custom components cannot take part in keyboard focus: `KeyboardFocus` is internal and there is no focus SPI, so a custom renderer's widgets are skipped by Tab (built-in components it renders as children through `RendererProvider` still register).
- **Custom texture backend / another graphics API**: a custom `ImGuiBackend` subclass (implementing the four hooks `createTexture`, `deleteTexture`, `createCanvasTexture` and `updateCanvasTexture`, the canvas pair creating UNORM textures, for example to load textures differently on OpenGL; a pre-1.0 SPI break without shims, and an override of `render` must call `super.render` so canvas textures are still evicted) pairs only with the GL3 or GLES3 renderers (`ImGuiSdlGl3Renderer`, `ImGuiGlfwGl3Renderer`, `ImGuiSdlGles3Renderer`), because its textures must be texture names of the renderer's OpenGL or OpenGL ES context; the SDL_GPU and Vulkan renderers take their own typed backends. All four concrete backends are final, and each bundled display uses its own backend (`ImGuiOpenGlBackend` or `ImGuiOpenGlEsBackend` for jME, matching jME's renderer; `ImGuiOpenGlBackend` for the two GL3 displays; `ImGuiSdlGpuBackend` for the SDL_GPU display; `ImGuiVulkanBackend` for the Vulkan display). A new graphics API needs a new variant of the sealed `ImGuiRenderer` inside `lorisui.imgui`, so it is not an extension point.
- **New backend**: implement `Backend.render` and the keyboard-navigation settings (`get`/`setActivationKey` with `requireNonNull`, `is`/`setKeyboardNavigationEnabled`, with the behavior `Backend`'s Javadoc describes), plus its own registry mechanism, in a new module that depends only on `loris-ui-api`.
- **New host**: a module that depends only on `loris-ui-imgui`. Wrap an `ImGuiRenderer` variant and its matching backend (`ImGuiOpenGlBackend` for the GL3 variants, `ImGuiOpenGlEsBackend` for `ImGuiSdlGles3Renderer`, `ImGuiSdlGpuBackend` for `ImGuiSdlGpuRenderer`, `ImGuiVulkanBackend` for `ImGuiSdlVulkanRenderer`) in the target's render hook, keep screens in a `ScreenManager`, resolve text with a `ResourceBundleKeyResolver`, use the renderer's input-capture queries for input routing (they include the keyboard-focus capture, so no host code is needed for it; with the GLFW variant, forwarding the window's callbacks and restoring the global monitor callback after `initialize()`; the SDL variants start and stop SDL text input themselves, so the host must not toggle it for the same window), provide an sRGB framebuffer, and defer teardown requested during a frame or hook with a `DeferredRelease` plus `ScreenManager.beginDeactivation()`, as the bundled hosts do (a Vulkan host also calls `skipFrameDraw()` when it is closed during a frame).

## Known Architectural Concerns
- **Emulated jME display-scale modes (> 1) unsupported**: with an `AppSettings` display-scale mode above 1, jME renders the GUI into a framebuffer sized framebuffer × mode, while Dear ImGui sizes its viewport from the logical window size times the framebuffer scale, so the UI covers only part of the window. The jME Javadoc documents this; there is no runtime detection.
- **jME viewport must render to the window**: the jME display sizes the UI from the window's logical size, so its viewport must render to the window. Offscreen viewports (render-to-texture, or a `FilterPostProcessor` on the same viewport) are unsupported; the jME Javadoc documents this, and there is no runtime detection.
- **jME `restart()` with an attached display unsupported**: jME's `restart()` (`LwjglWindow.restartContext()`) destroys and recreates the SDL window and GL context, while `ImGuiJmeDisplay` passes the window handle to its renderer variant only once, in its constructor. That handle goes stale, so the renderer's SDL3 platform backend (which filters events by the old window) and its SDL text-input toggling would target a destroyed window. The per-frame window-size query in `drawCurrentScreen` reads the live `window.getWindowHandle()` and is not affected. Not detected, not verified at runtime, no fix.
- **Dear ImGui asserts end the JVM**: imgui-java calls `System.exit(1)` after any failed Dear ImGui assertion, even with a custom `ImGui.setAssertCallback` handler, which can only log or pick the exit code. The renderer disables error-recovery asserts so frame exceptions reach the host, and its in-frame guard plus the hosts' deferred teardown remove the known `DestroyContext` trigger (a locked font atlas); other asserts still terminate. This is documented in the `ImGuiRenderer` and `lorisui.imgui` Javadoc. An SDL_GPU validation failure in debug mode can also end the process.
- **Native lifecycle verified manually only**: context creation and destruction, Impl shutdown, font replay, GL and GLES texture upload and deletion, GPU texture upload and release, the SDL_GPU frame, the GLES draw path under ANGLE, the Vulkan pipeline, uploads, synchronization, swapchain recreation and teardown, SDL text-input delivery, native GLFW callback chaining and re-attach cannot be unit-tested (no native context or `VkDevice` in tests), and are checked by hand with the six examples, one at a time or all at once with `runAllExamples`. The same holds for the keyboard-navigation integration: the focusable renderers (registration, focus looks, popup and combo scopes, the internal combo popup ID, the one-frame input activation and `clearActiveID` after the widget), the Tab diversion in the five variants (`SdlKeyEvents` reads native event memory; foreign-window Tab) and the host capture. The same holds for the canvas: `CanvasRenderer` (hit-testing, `itemHoverable`, the wheel-consuming child), the native canvas texture paths of the four backends (create, partial update, GL state restore, SDL_GPU and Vulkan uploads, eviction and release) and the wheel withholding in the hosts. Its manual pass, on all six examples (also with `runAllExamples`, and the Vulkan one with `-Dlorisui.example.gpuDebug=true` without validation errors), on `ExampleScreen`'s "Canvas" tab: the tab shows the canvas with its background; painted pixels match the swatch exactly; paint, erase, pan and zoom work; a left, right or middle drag that leaves the canvas keeps painting, erasing or panning until release, and another button pressed mid-gesture changes nothing; in both jME examples F1 pressed during a left, right and middle canvas drag toggles the UI (no keyboard capture); a drag passing over "Clear" may show its hover look but never clears on release; zoomed pixels are sharp, except blurred on SDL_GPU; the wheel over the canvas zooms without scrolling the tab content, while the wheel elsewhere in the tab scrolls it, also right after the content was scrolled (wheel lock) and on the first frames after the tab opens; switching tabs away and back keeps the drawing (eviction and re-upload); Clear works; "Hide UI" and showing it again, and jME re-attach, keep the drawing; no GL state corruption in either jME example. The keyboard-navigation manual pass on both example screens: Tab and Shift+Tab through `ExampleScreen` (the disabled `progress_minus` skipped; inputs get a caret and keep their edit when tabbed off; Enter opens the combo, Tab and Up/Down move through its items, Enter selects and returns to the combo, Escape closes and returns; the selected tab keeps its anchor; a button re-enabled while focused runs its hover action again); held Tab across inputs at a low frame rate (no stray caret, focus matches the active input); Ctrl+Tab does nothing; on `ExampleFocusScreen`, the two inputs in one panel keep separate edits, the modal traps Tab and Escape does not close it, and a click only sets the anchor; host keys (while a button is focused Escape is consumed, so no jME exit and no GLFW close; after the focus is cleared F1 and Escape reach the game). Only the native-free paths are unit-tested: the deferred-teardown state machine (`DeferredRelease`, `ScreenManager.beginDeactivation`, and their host composition mirrored in `HostLifecycleCompositionTest`), the gating of the five renderer variants and of `ImGuiSdlGpuBackend` and `ImGuiVulkanBackend`, the GL backends' decode-before-GL order, `ImGuiFont` glyph-range validation, `TextureTiling`, `ButtonInputTracker` (press identity, hover start and the keyboard focus-start and activation inputs), `CanvasInputTracker` (gesture ownership, drag accumulation, wheel, disabled gate, frame bookkeeping), `ImGuiBackend`'s canvas texture cache and eviction (through a recording backend), `RgbaPixels`, `Canvas` itself (`CanvasTest` in `api`, with Mockito), `KeyboardFocus` (cycling, scopes and combos, input activation, mouse anchoring, failed frames, reset and capture), `TabKeyFilter`, the navigation settings on `ImGuiBackend` and their passthrough from the renderer, `SdlTextInput` (the SDL text-input start/stop state machine), `DecodedImage`'s missing-resource path, the SPIR-V words of `ImGuiImplVulkanShaders` and `VulkanTextures`' size guard of `upload` and `update` (both in `loris-ui-imgui-vulkan`), the pre-initialize paths of the four LWJGL displays (including the ungated navigation setters on an uninitialized and a closed display and the `null`-key `NullPointerException`, through the SDL3 + OpenGL 3 display), the GLFW display's dispatch rules (through its package-private `dispatch` seam), the hosts' key-release rule (`DeliveredKeys` in `lwjgl` and `jme3`) and the jME renderer choice (`ImGuiJmeGraphicsApi`); `examples` has no tests. The Vulkan classes can be tested only for the argument checks reachable with `null` Vulkan objects, so the Vulkan backend's, renderer's and display's paths behind a successful construction are an accepted gap covered only by the manual checklist: the display's close-during-frame logic (`skipFrameDraw`, the restored frame flag and the deferred release), its render check order (its own state checks, then the renderer's command-buffer checks), calls before `initialize()`, `close()` and registration after `close()`; the shared base behavior stays covered by the SDL3 + OpenGL 3 tests. That a display's navigation setter reaches its private backend is not observable without natives or a test-only accessor, and `ImGuiJmeDisplay` cannot be constructed in tests (jME is `compileOnly`), so the display setters' delegation is an accepted gap, verified by review and with the examples; the navigation switch and the `SPACE` key have no example control, so their end-to-end paths are covered only by the unit tests and review. No example contains a non-modal `Popup`, so its Tab trap (R3) is covered only by `KeyboardFocusTest` and review (accepted).
- **UI state on re-attach**: every re-attach creates a new Dear ImGui context, so selected tabs, scroll positions, open popups and keyboard focus reset; LorisUI-held state (bindings, `TabbedPanel`/`ComboBox` model values) is kept.
- **Global SDL hints**: imgui-java's SDL3 backend (all four SDL variants) sets `SDL_HINT_MOUSE_FOCUS_CLICKTHROUGH`, `SDL_HINT_MOUSE_AUTO_CAPTURE` and `SDL_HINT_BORDERLESS_WINDOWED_STYLE` on every `initialize()`; they stay set after `dispose()`.
- **SDL text input owned by the SDL variants**: the four SDL variants start SDL text input on their window while a LorisUI text or number input is active, and stop it once none is and on `dispose()`, keeping track of their own calls only. An application or framework (including a future jME version) that starts or stops SDL text input for the same window interferes with typing into the UI: a stop while a field is active cuts off typed characters until the field is left and entered again, and the variant's own stop can end text input that the application started. There is no opt-out; the Javadoc of the four SDL variants, of `ImGuiJmeDisplay` and of the three LWJGL SDL displays' `render()` documents it, and it is not detected. A host closed or removed during a frame while a field is active (an LWJGL SDL display, or the jME display) may start text input at the end of that frame and stop it again in the deferred release: the net effect is none on desktop, though an on-screen keyboard could flash briefly.
- **GLFW monitor callback**: Dear ImGui's GLFW backend replaces GLFW's global monitor callback on every `initialize()` and never restores it. `ImGuiLwjglGlfwGl3Display` gives the application's callback back; a host using `ImGuiGlfwGl3Renderer` directly must do so itself.
- **GLFW close and callback failures**: `close()` is rejected inside the GLFW display's callbacks, and must not be called from any other GLFW callback either (such as a window-close callback; not detected), so integrators request the close there and call `close()` after `glfwPollEvents` returns. A failure in a callback dispatch surfaces from the next `render()`/`close()`, and events arriving in between (usually the rest of that poll) reach neither the UI nor the application. Calling `render()` from a GLFW callback the display does not own, such as a window-refresh callback, is unsupported.
- **GLFW HiDPI on Windows and X11**: GLFW measures windows in pixels there (no `GLFW_SCALE_TO_MONITOR`), so the UI is not scaled up on HiDPI monitors. Documented, not fixed.
- **sRGB framebuffer required**: image textures are sRGB on every variant (`GL_SRGB_ALPHA` / `GL_SRGB8_ALPHA8` / `R8G8B8A8_UNORM_SRGB` / `R8G8B8A8_SRGB`) and the Dear ImGui font atlas is UNORM, so every host must write through an sRGB framebuffer: `GL_FRAMEBUFFER_SRGB` on an sRGB-capable default framebuffer for the GL3 hosts, jME's gamma correction (on by default) for both jME renderers, the `SDR_LINEAR` swapchain composition for SDL_GPU, and an sRGB swapchain format (such as `B8G8R8A8_SRGB`) for Vulkan. A host without it shows different colors. Canvas textures are the exception: they are UNORM on every backend (`GL_RGBA8`, `R8G8B8A8_UNORM`), so canvas pixels are stored like Dear ImGui vertex colors and match widget colors through the same sRGB framebuffer.
- **`SDR_LINEAR` support**: the `SDR_LINEAR` swapchain composition depends on the driver. The SDL_GPU example checks `SDL_WindowSupportsGPUSwapchainComposition` and fails with a clear message; a host that cannot get it sees darker images than the GL path. The swapchain parameters must not change while the renderer is initialized.
- **GPU release before submit**: closing the SDL_GPU display inside a frame releases GPU resources at the end of `render`, before the application submits that frame's command buffer; this relies on SDL_GPU deferring the release of resources already recorded in a command buffer, and is checked by hand ("Hide UI" in the SDL_GPU example, ideally with `-Dlorisui.example.gpuDebug=true`).
- **No Vulkan close between `render` and submit**: Vulkan does not defer destruction, so the Vulkan display handles only a close during its own frame (`skipFrameDraw`, then the release after `render` returns). A `close()`, or a screen hook that closes the display, after `render` has recorded but before the application submits destroys objects the command buffer uses; this is documented as unsupported, not detected.
- **Vulkan render area from SDL**: `render` has no extent parameter, so the renderer draws over the draw data's framebuffer size (`SDL_GetWindowSizeInPixels`, cached by SDL while events are pumped). If the swapchain is smaller, for example while the window shrinks between the event pump and the swapchain recreation, the render area would exceed the image (a validation error); the application passes `targetImageView = 0` on such a frame (the UI updates, nothing is drawn), as the example does. The example recreates the swapchain only when the desired extent changes or after `OUT_OF_DATE`; a `SUBOPTIMAL` result keeps presenting with the current swapchain, so a surface that stays suboptimal does not cause a recreation and a device-idle wait every frame.
- **Vulkan queue requirements and synchronization**: the backend's queue must be graphics-capable (from `queueFamilyIndex`) and must be the queue the application submits its frames on, because uploads, their layout transitions and `deleteTexture`'s `vkQueueWaitIdle` rely on submission order on that one queue; neither is checked. Uploads submit from the UI thread and wait for completion, so applications that submit to the queue from other threads must serialize those submissions with LorisUI calls.
- **Vulkan colour-attachment format fixed per instance**: the format is a constructor argument baked into the pipeline. Rendering into another format needs a new renderer or, because closing is final, a new display with its fonts, renderers, style appliers, bundles and screens registered again. The example keeps its swapchain format across recreations, so this does not arise there.
- **Modular Vulkan applications `requires org.lwjgl.vulkan` themselves**: `lorisui.imgui` and `lorisui.lwjgl` use a plain `requires static org.lwjgl.vulkan` (and `lorisui.imgui` `requires static org.lwjgl.opengles`; the port modules `lorisui.imgui.vulkan` and `lorisui.imgui.gles3` do the same, and no application requires them), so GL-only and jME consumers need no Vulkan binding; a modular jME application on the ANGLE renderer must still have `org.lwjgl.opengles` resolved at runtime (`requires` or `--add-modules`). The cost is a `javac -Xlint:exports` warning about Vulkan types in exported signatures, which the build does not enable; do not add `-Xlint:all` with `-Werror` to `javac` without suppressing `exports` for these modules.
- **Vulkan loader sharing on macOS**: SDL and LWJGL must load the same Vulkan library; the example passes LWJGL's loaded library path to `SDL_Vulkan_LoadLibrary`, which needs a manual check on macOS.
- **MoltenVK and Vulkan 1.3**: Vulkan 1.3 support (dynamic rendering) in the MoltenVK build that ships with LWJGL 3.4.3 is unverified; the example fails with a clear message naming the missing requirement when no suitable device is found, and the renderer's `initialize()` throws when the device does not expose Vulkan 1.3 functions.
- **OpenGL ES 3.0 vertex limit**: the GLES3 port has no base-vertex draw and imgui-java uses 16-bit indices, so a single Dear ImGui window above 65,535 vertices fails a Dear ImGui assertion, which ends the JVM. Accepted and documented in the `ImGuiSdlGles3Renderer` and `lorisui.imgui` Javadoc; typical menus and HUDs stay far below it.
- **ANGLE checked manually only**: the GLES3 draw path under jME's ANGLE renderer (and the ANGLE drivers per platform) is verified only by running `runJme3Example`, side by side with `runJme3Gl3Example` and the LWJGL examples. It is checked with jME 3.10.0-beta3.
- **Unsupported jME renderers rejected**: `ImGuiJmeDisplay`'s constructor throws `IllegalStateException` for any jME renderer other than `ANGLE_GLES3` and `LWJGL-OpenGL*` (for example `JOGL_*` or a `null` renderer), before anything is created.
- **Repeat item count**: a `Repeat` image creates one Dear ImGui item per tile, so a small texture over a large area costs many items. Like the *Resize modes, it assumes it is drawn from the left edge of the current window, which holds for the built-in renderers.
- **Wrap mode**: GL and GLES textures use `GL_CLAMP_TO_EDGE` (and both Vulkan samplers `CLAMP_TO_EDGE`), so sprite cells at a texture border no longer blend with the opposite edge when filtered linearly.
- **Context left current**: the renderer leaves its Dear ImGui context current after every call, so an application that uses its own Dear ImGui context must restore it.
- **One backend per renderer**: `PanelRenderer` keeps the button press and hover state (`ButtonInputTracker`) in its instance, which belongs to one backend, so a backend shared between renderers or Dear ImGui contexts loses button presses and mixes hover state (`CanvasRenderer`'s `CanvasInputTracker` likewise keeps canvas gestures per backend). The `ImGuiBackend` Javadoc and the five renderer variants' `@param backend` require a backend used by one renderer only (re-initializing the same renderer is fine), as the bundled hosts do; it is documented, not enforced, and there is no per-context state. **Two backends sharing a canvas**: a `Canvas` must be drawn by one backend only (documented on `Canvas`, `RendererProvider.loadTexture(Canvas)` and `ImGuiBackend`), because `takePixelUpdate` hands the changed pixels to whichever backend takes them first, so another backend drawing the same canvas misses those changes until its texture is re-created; drawing one canvas on several backends correctly is out of scope.
- **Button input (accepted behaviors)**: the hover check stays `isWindowHovered(ChildWindows)` without `AllowWhenBlockedByActiveItem`, so there is no hover start and no click while another control holds the mouse (a scrollbar, a press in another window, a drag-selection in a text field). A text field that is merely being edited does not block buttons: Dear ImGui lets other widgets hover while the mouse is up (`ActiveIdAllowOverlap`), so hover starts and clicks work as usual. Nested buttons each get their own hover start and only the innermost one clicks, but the outer one may draw its active background on the press frame. A press and a release in the same frame click both nested buttons; this needs Dear ImGui's input trickling (`ConfigInputTrickleEventQueue`, on by default, unchanged by LorisUI) turned off. A disabled button still claims the press, so a disabled inner button swallows its enabled outer button's click, and a press on a disabled button that becomes enabled before the release clicks; a button that becomes enabled while hovered does not run its hover action, while one whose input is re-enabled while hovered does. The click that closes a popup or the ComboBox dropdown does not click the button underneath, as in native Dear ImGui.
- **Keyboard navigation behavior changes (accepted)**: Tab never reaches Dear ImGui, even with navigation off, so Ctrl+Tab windowing is gone for every application. While navigation is enabled, all key events are captured while an enabled button or combo box has keyboard focus or a combo box is expanded, also one expanded with the mouse (which now also traps Tab). The capture also covers an input with keyboard focus while it is active, not only while its activation is pending (a superset of the spec's rule), because Dear ImGui computes `WantCaptureKeyboard` in `NewFrame` and would report the input one frame late. Escape never closes a `Popup` or `ModalPopup`; on an active input it is left to Dear ImGui (revert and end edit) and clears the LorisUI focus. Turning navigation off resets the focus at the next rendered frame; turning it off and on again with no frame in between keeps the focus (invisible, and the capture follows the switch at once). Navigation is on by default, so on a gameplay or HUD screen with buttons a stray Tab focuses a button and every key is then captured until Escape or a click; applications turn navigation off (`setKeyboardNavigationEnabled(false)`) on screens where Tab or other keys belong to the game (documented on `Backend.setKeyboardNavigationEnabled`).
- **Capture lags one frame**: capture uses the state committed by the last completed frame, so the first Tab press while nothing is focused also reaches the game. This does not apply while a `ModalPopup` is open, because Dear ImGui then already captures the keyboard.
- **Capture and Tab moves need rendered frames**: `wantsKeyboardInput()` reflects the last rendered frame, and Tab moves are queued between frames and applied by the next frame's begin step. A host that keeps forwarding events but stops rendering (for example while the UI is hidden without closing the display) keeps consuming every key while a button was focused, and queued Tab presses apply as one jump on the next frame. Hosts render every frame while forwarding events, or turn navigation off or close (jME: remove) the display while the UI is hidden; documented on `ImGuiRenderer.wantsKeyboardInput()` and the displays. Not fixed in code.
- **Key presses before the display attaches**: hosts track only the key-downs they saw, so a key held down when the display is initialized (jME: attached) has its release decided by the current capture alone and can be consumed if the UI captures at that moment. The jME display also clears its `DeliveredKeys` on detach (removing its listeners), so the release of a key held across a detach and re-attach likewise follows the capture at the moment of release. Both are narrow; accepted.
- **Empty popup scope**: an open `Popup` or `ModalPopup` with no enabled focusable element is still the active scope, so Tab does nothing and all focus outside it is cleared, and because Escape never closes popups, a keyboard-only user cannot leave it through LorisUI navigation (only a click or the application closing the popup does). This follows the spec (a popup traps the cycle); accepted and documented.
- **One-frame input activation**: `setKeyboardFocusHere` only requests navigation, and Dear ImGui activates the input in the next frame's `NewFrame`, so the caret appears one frame after focus lands (visible only at very low frame rates); `KeyboardFocus` keeps the input pending for the request frame and the one after it. An input overtaken by another Tab while pending is still activated by Dear ImGui for one frame before LorisUI deactivates it, so SDL text input may start and stop again one frame later (harmless, visible in logs). Only Tab moves deactivate inputs (`clearActiveID` after the widget); Escape and clicks leave deactivation to Dear ImGui. A click in the frame in which a tabbed-to input is activated moves the LorisUI anchor to the clicked element (or clears it), while Dear ImGui still activates the input (its pending focus request wins over the click), so the input shows its caret while the LorisUI anchor is elsewhere; accepted.
- **Combo item ID collision**: combo items are scoped by `pushID(item.toString())`, so items whose `toString()` values are equal share one ImGui ID and act as one focus target (the collision existed before keyboard navigation; not fixed). Combo boxes and text and number inputs use `"##" + component` as their ImGui label and ID, and components do not override `toString()`, so the ID comes from the class name and the identity hash: two components of one class with equal identity hashes in one ID scope would share an ID. Identity hashes are not unique, so this is possible but rare; accepted.
- **Focused elements not scrolled into view**: keyboard-focused buttons, combo boxes and combo items inside scrolled regions are not scrolled into view.
- **Dear ImGui internals**: opening a combo from the keyboard uses Dear ImGui's internal popup ID derivation (`getIDWithSeed("##ComboPopup", null, comboId)`, as in `BeginCombo`), releasing an input uses `imgui.internal.ImGui.clearActiveID()`, and a hovered canvas registers itself as Dear ImGui's hovered item with `imgui.internal.ImGui.itemHoverable(min, max, id, 0)`, so a left press on it skips Dear ImGui's empty-space window-move path (`UpdateMouseMovingWindowEndFrame` returns early while `HoveredId != 0`), which would otherwise set `ActiveId` to the window's move ID, even with `NoMove`, and capture the keyboard. All three are verified against Dear ImGui 1.92.7, but the runtime range `[1.92.7.1,1.93)` admits any later 1.92.x, and a changed seed would open a popup that is never begun (keyboard opening of combos would fail silently), while a changed empty-space path would make left canvas drags capture the keyboard. **Checklist on every imgui-java upgrade** (also within the range): re-check `BeginCombo`'s `"##ComboPopup"` popup-ID seed, the `itemHoverable` signature and the early return of the empty-space move path on a hovered item (F1 must still reach the jME example during a left canvas drag), the canvas wheel take-over (the wheeling window chosen from the hovered window, `ScrollMax` from the previous frame's content size, `SetNextWindowScroll` overriding the wheel's scroll target), the `clearActiveID` and `SetKeyboardFocusHere` semantics (the request is activated in the next `NewFrame`, and an input requested by navigation is not re-activated while it is active), re-run the manual canvas checks for the wheel take-over (the wheel over a canvas in a scrollable panel runs `wheel()` without scrolling the panel) and for no keyboard capture during canvas drags (F1 pressed during a left, right or middle canvas drag still toggles the jME examples' UI), and re-run the manual keyboard checks for inputs (Tab into a text or number input shows the caret, typing and Tab off keep the edit and deactivate it; holding Tab across inputs at a low frame rate leaves no stray caret) and for combo boxes (a focused combo opens on Enter at its selected item, Tab, Shift+Tab, Up and Down move with the highlight, Enter selects, closes and returns the focus).
- **Global state**: `ImGuiState` holds static fields (`hoveringScrollableWindow`, `currentContextPtr`, and the `keyboardFocus` slot, set only during `screen.render`), and `LorisScreen` shares one static layout worker across screens; only one renderer and one display may be in use at a time. The button press and hover state and the canvas gesture state are not global: they are per backend (`ButtonInputTracker` in `PanelRenderer`, `CanvasInputTracker` in `CanvasRenderer`). The keyboard-focus state is per renderer (`KeyboardFocus` in `ImGuiRenderer`); the slot only publishes it to the renderers during a frame, so it is valid only for the renderer whose frame is running (driving one renderer's frame from inside another's is unsupported, as it already is for the Dear ImGui context).
- **Texture cache**: per backend, cleared as a whole by `unloadTextures()` (and by renderer teardown); there is no per-path eviction of image textures while a backend is in use. Canvas textures are the exception: they are evicted when their canvas was not drawn since the previous outermost `render`.
- **Canvas wheel take-over is best effort**: an interactive canvas consumes the wheel through its one-pixel-overflow child (see `CanvasRenderer`), so its parent should not scroll while the wheel turns over it. This depends on Dear ImGui 1.92.7's wheeling-window choice; it was verified manually with Dear ImGui 1.92.7 on all six examples (2026-11-19) and is re-checked on every imgui-java upgrade (see Dear ImGui internals). Residual cases, accepted and documented: Dear ImGui keeps sending the wheel to a recently scrolled window for about 0.7 s, so while the parent is that locked wheeling window the parent scrolls and the canvas's `wheel()` also fires for the same notch; on the first frame a canvas child exists its scroll range is still 0 (`ScrollMax` uses the previous frame's content size), so a wheel event in that frame goes to the parent; Ctrl+wheel never scrolls Dear ImGui windows but still fires `wheel()`, because modifiers are not filtered (Shift+wheel is covered by the horizontal overflow). If the mechanism fails on a later Dear ImGui, the fallback is documented behavior: a scrollable parent also scrolls (the `Canvas` Javadoc and this concern then say so).
- **Canvas hit-testing without an active item (accepted)**: `CanvasRenderer` hit-tests with a `dummy` plus raw mouse state, like `PanelRenderer`'s buttons, and never makes a Dear ImGui item active, so a canvas gesture never captures the keyboard (`wantsKeyboardInput()` is unchanged; `WantCaptureMouse` stays true for the whole gesture, because Dear ImGui owns a button pressed over its windows until release). The consequence: while a canvas drag passes over other widgets they may show their hover look, and LorisUI buttons run their hover actions; releasing over a button does not click it, because its press was not recorded. Documented in the `Canvas` Javadoc. A left press on any LorisUI panel or button area (not a canvas) still goes through Dear ImGui's empty-space move path and captures the keyboard while held; that is existing behavior, not changed.
- **Canvas textures assume one outermost `render` per frame**: eviction treats each outermost `ImGuiBackend.render` as a frame, as `Backend.render`'s Javadoc implies. A screen that calls `backend.render` twice per frame evicts, at the second call, every canvas the first call drew and re-creates it every frame; a subclass that overrides `render` without calling `super.render` never evicts canvas textures before `unloadTextures()`. Documented in the `ImGuiBackend` Javadoc, not enforced.
- **Canvas upload costs**: uploads are synchronous and happen while the canvas is drawn. Scattered edits merge into one bounding rectangle, so an edit in two opposite corners uploads almost the whole image; each upload also allocates its snapshot `int[]` (the RGBA scratch buffer is reused). On SDL_GPU each create and update submits its own command buffer. On Vulkan each edited canvas costs one staging allocation (buffer, memory, command pool, fence), one submission and one fence wait per frame. A fence signaled by `vkQueueSubmit` also covers all work submitted earlier on that queue, so the wait blocks the CPU until every earlier frame in flight has finished on the GPU: frames with canvas edits lose the pipelining of several frames in flight and run with one, while frames without edits keep it. Each released canvas texture (evicted or unloaded) costs one `vkQueueWaitIdle`, labeled `releasing canvas texture <w>x<h>`. Documented in the `ImGuiVulkanBackend` Javadoc; deferred uploads on the frame command buffer are a roadmap item.
- **SDL_GPU canvas filtering**: `ImGuiImplSdlGpu3` binds one linear sampler for every texture, so canvas textures on SDL_GPU are sampled `LINEAR` and zoomed canvas pixels are blurred, while the GL, GLES and Vulkan backends draw them as sharp squares (`NEAREST`). Documented in the `ImGuiSdlGpuBackend` Javadoc and, toolkit-neutrally, in the `Canvas` Javadoc ("smoothed by some" backends); a per-texture sampler needs an `ImGuiImplSdlGpu3` port (roadmap item).
- **Canvas colors versus `Image`**: canvas textures are UNORM, so a canvas pixel looks like the same `Color` in widgets (vertex colors), while the same bytes in an image file shown with `Image` (an sRGB texture) look different. Documented in the `Canvas` Javadoc.
- **Canvas size**: the resolution is checked only against the 536,870,911-pixel limit (so the RGBA byte count fits an `int`), not against GPU limits; the `Canvas` Javadoc recommends at most 4096 × 4096, and a larger texture may fail at the backend: SDL_GPU and Vulkan report a failed creation or upload as an `IllegalStateException`, while on OpenGL and OpenGL ES an oversized or out-of-memory canvas texture is not detected and the canvas may be drawn blank.
- **Canvas placement (accepted edge cases)**: a canvas inside a `Button` also presses the button (as an `Image` or a nested button does), and a canvas used as a top-level screen component is unsupported (`CanvasRenderer` ignores `topLevel`; place it inside a panel).
- **Wheel withholding from the game not observable in the examples**: hosts withhold the wheel over an enabled canvas through the unchanged `isHoveringScrollablePanel()` path, but the jME examples disable the fly camera and no LWJGL example reads the wheel, so this is verified only by review (accepted gap).
- **Missing images**: a texture that fails to load is retried and fails again on every draw instead of failing once.
- **Renderer robustness**: `ImGuiRenderer` disables ImGui's error-recovery assert and tooltip, so state left open by a throwing renderer (windows, IDs, style stacks) is unwound when the frame closes and the original exception propagates to the host; the trade-off is that an imbalance that does not throw is recovered silently instead of failing fast. The input renderers pop their item width in `finally`, the combo box uses `setNextItemWidth` and pops its styles, style var and focus-look color in `finally` around `beginCombo`, the panel and combo renderers pop their keyboard-focus scopes in `finally`, the progress bar pops its style in `finally`, and the canvas renderer ends its child and pops its background color in `finally`, but other push/pop pairs (per-item IDs, `beginChild`/`endChild` in the panel and combo renderers) are still not in `try/finally`.

- jMonkeyEngine 3.10.0-beta3 (jME host and examples only), with its default `ANGLE_GLES3` renderer or an `LWJGL_OPENGL*` renderer (jME itself accepts only the OpenGL 3.2 and later ones)

## Configuration
- Build-time: Gradle `ext` versions in the root `build.gradle`; Checkstyle rules in `config/checkstyle/`; editor settings in `.editorconfig`
- Runtime: done in code through any display (fonts, renderers and style appliers, resource bundles, screens). The examples' shared settings live in `ExampleSettings`; the jME window settings in `LorisJme3Example.createDefaultSettings()` (which keeps jME's default renderer; `LorisJme3Gl3Example` sets `LWJGL_OPENGL33`).
- i18n: `ResourceBundle`s registered by name (for example `bundles.global`)
- Resources (fonts, textures) are class-path resource names; a leading `/` is optional. On the module path they must be outside any package of a named module, or in a package the application module opens unconditionally.

## Deployment Architecture
LorisUI is a library, so it isn't deployed as a service. It's published as Maven artifacts (`loris-ui-api`, `loris-ui-imgui`, `loris-ui-imgui-gles3`, `loris-ui-imgui-vulkan`, `loris-ui-jme3`, `loris-ui-lwjgl`), each with sources and Javadoc jars and a POM with name, description, url, exactly one license (Apache-2.0, or MIT for the two port artifacts, which `loris-ui-imgui` brings as runtime-scope dependencies), developer and scm, and consumed by desktop game applications. Publishing goes only to the local Maven repository (`./gradlew publishToMavenLocal`); no remote repository is configured, and `examples` is not published. `loris-ui-jme3` does not bring jMonkeyEngine: its consumers declare `jme3-core` and `jme3-lwjgl3` (plus any other jME modules they use) themselves. imgui-java (which brings LWJGL with its SDL, GLFW and OpenGL bindings and natives, the GLFW and SDL natives only for Linux, macOS, macOS arm64 and Windows) is pulled in at runtime; `lwjgl-stb` is an `implementation` dependency of `loris-ui-imgui` (runtime scope for consumers) with natives for Windows, Linux, macOS and macOS arm64. LWJGL's OpenGL ES and Vulkan bindings are not brought: jME supplies the OpenGL ES binding for its ANGLE renderer, and a Vulkan application declares `lwjgl-vulkan` itself (plus its `natives-macos`/`natives-macos-arm64` classifiers for MoltenVK on macOS). Every library jar and sources jar contains `META-INF/LICENSE`: the root Apache-2.0 `LICENSE`, or the port subproject's own MIT `LICENSE` in `loris-ui-imgui-gles3` and `loris-ui-imgui-vulkan`. On JDK 25, applications pass `--enable-native-access` (`ALL-UNNAMED` on the class path, the module names on the module path) to avoid the restricted-method warnings of imgui-java and LWJGL; the examples' run tasks pass `ALL-UNNAMED`. Running the SDL- and GLFW-based examples on macOS may additionally need `-XstartOnFirstThread`, which the run tasks don't pass. Consumer Javadoc states `--enable-native-access` in the `lorisui.imgui`, `lorisui.lwjgl` and jme3 package docs, and `-XstartOnFirstThread` in the LWJGL host's docs.

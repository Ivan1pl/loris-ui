# System Architecture

## Overview
LorisUI is a layered, multi-module Java library. Game code describes UI as trees of plain component objects defined in a toolkit-agnostic API. A **backend** turns those trees into draw calls each time the host renders, and a **host integration** connects the backend to an application's render loop and input. Two host modules ship with the library: one for jMonkeyEngine 3 and one for an application's own LWJGL window and loop, with a display for each supported platform/renderer pair (SDL3 with OpenGL 3, GLFW with OpenGL 3, SDL3 with SDL_GPU).

```
examples ──┬──▶ loris-ui-jme3  ──┬──▶ loris-ui-imgui ──▶ loris-ui-api
 (demos)   │    (jME3 host)      │    (ImGui backends     (component model,
           └──▶ loris-ui-lwjgl ──┘     and renderers:      Backend port, screens;
                (LWJGL host:           OpenGL 3 /          zero dependencies)
                 SDL3 / GLFW)          SDL_GPU)
```

## Architecture Pattern
**Pattern**: Layered library with a ports-and-adapters style backend abstraction, plus registries of strategies (renderers and style appliers) inside the backend.

- **Port**: `api/.../api/backend/Backend.java` declares a single method, `render(int w, int h, List<Component> components, BundleKeyResolver bundleKeyResolver)`. It contains nothing toolkit-specific: textures, fonts and input capture are backend concerns.
- **Adapters**: `imgui/.../imgui/backend/ImGuiBackend.java` (abstract: registries with the registration API, the per-instance texture cache, texture drawing, and the protected abstract texture creation and deletion), `ImGuiOpenGlBackend.java` (final; OpenGL textures) and `ImGuiSdlGpuBackend.java` (final; SDL_GPU textures).
- **Frame driver**: the sealed `imgui/.../imgui/ImGuiRenderer.java` owns the Dear ImGui context and runs one frame per call; its three final variants own the platform and renderer objects of one pair each: `ImGuiSdlGl3Renderer` (SDL3 + OpenGL 3, used by the jME host and `ImGuiLwjglSdlGl3Display`), `ImGuiGlfwGl3Renderer` (GLFW + OpenGL 3) and `ImGuiSdlGpuRenderer` (SDL3 + SDL_GPU).
- **Hosts**: `jme3/.../jme3/ImGuiJmeDisplay.java` drives the renderer from jMonkeyEngine; the three displays in `lwjgl/.../lwjgl/` (`ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay`) are embedded in an application that owns its window, OpenGL context or GPU device, and loop. All keep their screens in an `api` `ScreenManager`, resolve text with an `api` `ResourceBundleKeyResolver` and defer teardown with an `api` `DeferredRelease`. These host-support helpers live in `lorisui.api` because the automatic `lorisui.jme3` module can only read exported packages.

**Rule**: dependencies only point towards `api`. `loris-ui-api` must not depend on any toolkit, engine or third-party library.

## System Structure

### loris-ui-api (`api/`)
- **Purpose**: the public, toolkit-agnostic contract: component model, styles, backend port, screens and their lifecycle, fonts and i18n.
- **JPMS module**: `lorisui.api`. It exports `backend`, `component`, `component.style`, `core`, `font`, `resolver` and `screen`, each with a `package-info.java`; the module descriptor has a module doc comment.
- **Packages** (`com.ivan1pl.lorisui.api.*`):
  - `component`: the `Component` marker interface and concrete components (`Panel`, `Button`, `Text`, `Image`, `TextInput`, `NumberInput`, `ComboBox`, `ProgressBar`, `TabbedPanel`, `Popup`, `ModalPopup`, `Spacer`), plus `Layout`, `Background` and the sealed `ImageMode`
  - `component.style`: `Style` and its concrete styles (`ScrollbarStyle`, `ComboBoxStyle`, `ComboBoxPopupStyle`, `ComboBoxItemStyle`, `TextInputStyle`)
  - `backend`: the `Backend` interface (only)
  - `screen`: the abstract `LorisScreen` (template method for screens; static `shutdownLayoutUpdates()` stops the background layout work, which restarts lazily on the next requested layout), the final `ScreenManager` and the final `DeferredRelease`.
    - `ScreenManager` is the host-neutral registry of named screens. It validates registration and switching, fires matched `onStartScreen`/`onEndScreen` hooks through `activate()`/`setCurrentScreen`/`deactivate()`, and rejects `setCurrentScreen`, `activate()` and `deactivate()` called from inside a hook (`IllegalStateException`, before any state change). `beginDeactivation()` makes it inactive without firing a hook (allowed inside hooks); `deactivate()` later ends the screen that was started.
    - `DeferredRelease` is the host-neutral teardown helper: `run(operation)` tracks operations that can call application code, `request()` releases at once or after the outermost running operation (`isRunning()`, `isPending()` report the state), and the static `runAll(steps...)`/`runAfterFailure(failure, cleanup)` run multi-step releases keeping every failure.
    - Both are not thread-safe; hosts call them on their UI thread.
  - `core`: the final `Color` and `IntBiFunction<ResultType>`, the content function that receives the screen width and height
  - `font`: the `Font` marker interface
  - `resolver`: `BundleKeyResolver` (i18n) and the final `ResourceBundleKeyResolver`, which resolves `bundleName.key` keys from `ResourceBundle`s registered by name
- **Conventions**: components are immutable-ish value holders built with nested static `Builder`s and non-public constructors. The Panel family is closed to the package: `Panel`'s constructor and its self-typed `BaseBuilder<PanelType, BuilderType>` are package-private, and `Button`, `Popup` and `ModalPopup` have private constructors.

### loris-ui-imgui (`imgui/`)
- **Purpose**: renders the API component model with Dear ImGui on OpenGL 3 or SDL_GPU, and drives Dear ImGui frames for the hosts.
- **JPMS module**: `lorisui.imgui`, with `requires transitive lorisui.api` so consumers of the backend read the API types, and `requires org.lwjgl.sdl` for the SDL_GPU calls. It exports `imgui`, `imgui.backend`, `imgui.renderer` and `imgui.renderer.style` (each with a `package-info.java`; the descriptor has a module doc comment). **It does not export** `imgui.impl`, `backend.impl`, `renderer.impl` or `renderer.style.impl`, which are internal. There is no `imgui.font` package.
- **Key Files** (`com.ivan1pl.lorisui.imgui.*`):
  - `ImGuiRenderer.java`: `public abstract sealed`, permitting exactly the three final variants below; the frame driver. Its constructor and its hooks (`initBackends`, `newBackendFrame`, `shutdownRendererBackend`, `shutdownPlatformBackend`, `clearBackends`, the no-op `awaitDeviceIdle`) are package-private, so the hierarchy is closed to the package; the base has no public `render`, because the variants' signatures differ. Lifecycle:
    - The variant constructors take a backend and the window handle and make no native calls: `ImGuiSdlGl3Renderer(ImGuiBackend, sdlWindow)` (any handle accepted, as before the rename), `ImGuiGlfwGl3Renderer(ImGuiBackend, glfwWindow)` and `ImGuiSdlGpuRenderer(ImGuiSdlGpuBackend, sdlWindow)` (`IllegalArgumentException` for a `0` window; the typed backend prevents pairing a GL backend with the GPU renderer). A null backend throws `NullPointerException`.
    - `registerFontFromFile`/`registerFontFromResources` (each with an optional glyph-range overload) read the font bytes eagerly (`IOException` naming the path, also for data of 100 bytes or less, on which Dear ImGui would fail a JVM-ending assertion; the `registerFont*` Javadoc asks for fonts from trusted sources only, because Dear ImGui's font loader is not hardened against malicious data), are allowed only while not initialized, and return a stable `ImGuiFont` handle. Glyph ranges are validated (`IllegalArgumentException` for no range, no terminating `0`, a missing last code point or a reversed range) and built as unsigned 16-bit code points, so ranges above `U+7FFF` (CJK) work; the font bytes stay in memory for the renderer's lifetime.
    - `initialize()` creates a fresh Dear ImGui context and makes it current, applies the IO configuration (no ini/log files, error-recovery assert and tooltip disabled), replays the registered fonts in registration order (a font Dear ImGui cannot load throws `IllegalStateException` naming its source) and builds the atlas, creates the variant's fresh platform and renderer Impl objects (`ImGuiImplSdl3`/`ImGuiImplGl3`, `ImGuiImplGlfw`/`ImGuiImplGl3` or `ImGuiImplSdl3`/`ImGuiImplSdlGpu3`; each kept only after its `init` succeeded, except that a failed `ImGuiImplSdlGpu3.init` is shut down on the spot because it may already own GPU objects; the SDL3 backend sets three global SDL hints that stay set after `dispose()`, and the GLFW backend replaces GLFW's global monitor callback; the SDL_GPU variant first reads the window's swapchain format and throws `IllegalStateException` when the window is not claimed for the device), and applies the LorisUI style overrides. A failed `initialize()` releases whatever it had set up (`DeferredRelease.runAfterFailure`) and leaves the renderer uninitialized, so it can be retried (a failure caused by a registered font recurs, because fonts cannot be unregistered).
    - `dispose()` releases, in order and running every step even after a failure: makes the context current, waits for the GPU to go idle (`SDL_WaitForGPUIdle`, SDL_GPU variant only), the backend's textures (`unloadTextures()`), the renderer Impl (`ImGuiImplGl3` or `ImGuiImplSdlGpu3`), the platform Impl (`ImGuiImplSdl3` or `ImGuiImplGlfw`), the context; then, even after a failure, it unbinds the font handles and drops the variant's Impl references (`clearBackends`). It is a no-op when not initialized, and the renderer can be initialized again afterwards (fonts are replayed, handles stay valid).
    - A private `rendering` flag covers each `render` call: `initialize()`, `dispose()` and a re-entrant `render` throw `IllegalStateException` while a frame is open, before any state change. Hosts therefore defer teardown requested from inside a frame (see Screen Lifecycle).
    - Every entry point makes the renderer's context current and records its pointer in `ImGuiState.currentContextPtr`; the renderer leaves its context current afterwards, so an application with its own Dear ImGui context must make that context current again. Only one renderer may be in use at a time.
    - The variants' `render` methods take the screen size in **logical window coordinates**: `SDL_GetWindowSize` for the SDL variants, `glfwGetWindowSize` for the GLFW variant (on Windows and X11 GLFW measures windows in pixels, so the UI is not scaled up on HiDPI monitors); Dear ImGui's platform backend applies the framebuffer scale. `ImGuiSdlGl3Renderer` and `ImGuiGlfwGl3Renderer` have `render(screen, w, h, resolver)` and draw into the current OpenGL framebuffer. `ImGuiSdlGpuRenderer` has `render(screen, w, h, resolver, commandBuffer, targetTexture)`: a `0` command buffer throws `IllegalArgumentException` before any state check; a `0` target builds the frame but draws nothing; otherwise it runs `prepareDrawData` outside any pass, then draws in its own `LOADOP_LOAD`/`STOREOP_STORE` render pass on the application's command buffer, which the application has cleared before and submits after the call. The frame is always closed; if the screen threw, its exception propagates and a frame-close failure is added to it as suppressed.
    - Input: `processSdlEvent(long)` on both SDL variants; seven `processGlfw*` methods (window focus, cursor enter, cursor position, mouse button, scroll, key, char) on the GLFW variant, which installs no window callbacks itself. Each throws `IllegalStateException` before `initialize()`.
    - Input-capture queries for hosts: `wantsMouseInput()`, `wantsKeyboardInput()`, `wantsTextInput()` and `isHoveringScrollablePanel()`, each describing the most recently rendered frame and returning `false` while not initialized.
    - Dear ImGui UI state (selected tabs, scroll positions, open popups, keyboard focus) starts fresh after `dispose()` + `initialize()`; state held by LorisUI components and their bindings is unaffected.
  - `ImGuiFont.java`: final; the ImGui implementation of `Font`, in the `imgui` package so `ImGuiRenderer` can bind it through package-private members. Instances are created only by the renderer's registration methods; there are no static loaders. A handle keeps the font bytes and built glyph ranges for replay (imgui-java passes the glyph-range pointer from a JNI critical array, so keeping the array reachable does not guarantee Dear ImGui a stable address; a known binding limitation), is re-bound on each `initialize()`, and `useFont(Runnable)` throws `IllegalStateException` (without running the code) while its renderer is not initialized or another renderer's context is current.
  - `backend/ImGuiBackend.java`: implements `Backend` and `RendererProvider`; protected constructor that fills the registries `Map<Class<? extends Component>, Renderer<?>>` and `Map<Class<? extends Style>, StyleApplier<?>>` with the built-ins.
    - Registration: `public final registerRenderer(Class, Renderer)` and `registerStyleApplier(Class, StyleApplier)` replace any existing mapping (built-ins included), reject null arguments (`NullPointerException`) and interface classes (`IllegalArgumentException`, because lookup walks only the superclass chain). `getRenderer`/`getStyleApplier` are `final`: they walk up the superclass chain and throw `IllegalStateException` when nothing matches.
    - Textures: a per-instance cache keyed by path and the three masks, with keys normalized to class-path style (a leading `/` is an alias of the bare path). `public final loadTexture(...)` (two overloads, implementing the `RendererProvider` methods) creates a texture on a miss through `protected abstract createTexture(normalizedPath, maskedR, maskedG, maskedB)`; failed loads are not cached. `public final unloadTextures()` calls `protected abstract deleteTexture(TextureData)` once per distinct texture, always empties the cache (first failure rethrown, later ones suppressed), and throws `IllegalStateException` while the backend is drawing (`render` sets a private `drawing` flag). The concrete `renderTexture(long id, ...)` maps `ImageMode` variants to ImGui draw calls with an exhaustive pattern `switch`; `Repeat` is drawn as a grid of `ImGui.image` tiles placed with `sameLine` (spans from `TextureTiling`, partial UVs on edge tiles), like the *Resize modes, so it does not depend on the texture's wrap mode. The class is abstract with a protected constructor, and both concrete backends are final: `ImGuiOpenGlBackend` pairs with the two GL3 renderers, `ImGuiSdlGpuBackend` with `ImGuiSdlGpuRenderer`.
  - `backend/TextureData.java`: the `TextureData(long id, int width, int height)` record returned by `RendererProvider.loadTexture`; `id` is a backend-specific handle (an OpenGL texture name or an `SDL_GPUTexture*`)
  - `backend/ImGuiOpenGlBackend.java`: final; `createTexture` (`DecodedImage`, then a `GL_SRGB_ALPHA` texture upload with `GL_CLAMP_TO_EDGE` wrapping) and `deleteTexture` (`glDeleteTextures`)
  - `backend/ImGuiSdlGpuBackend.java`: final; holds the SDL_GPU device (`ImGuiSdlGpuBackend(long gpuDevice)`, `IllegalArgumentException` for `0`, no native calls; `getGpuDevice()`). `createTexture` decodes with `DecodedImage` and uploads an `R8G8B8A8_UNORM_SRGB` texture through a transfer buffer and a copy pass on its own command buffer, submitted at once (so a load needs no frame command buffer, and the upload executes before the frame's buffer); any SDL failure throws `IllegalStateException` naming the resource and `SDL_GetError()` after releasing what it created. `deleteTexture` calls `SDL_ReleaseGPUTexture`
  - `backend/impl/DecodedImage.java`: internal, `AutoCloseable`; reads a class-path resource (`IOException` naming a missing path), decodes it with STB to RGBA8 and applies the masks; shared by both texture backends
  - `backend/impl/TextureMasking.java`: the pure pixel-masking loop used by `DecodedImage`
  - `backend/impl/TextureTiling.java`: the pure `spans(length, tileLength)` function behind the Repeat tile grid
  - `renderer/Renderer.java`: abstract per-component renderer base (explicit protected constructor); no texture state of its own
  - `renderer/RendererProvider.java`: renderer and style-applier lookup plus `loadTexture(path)`, `loadTexture(path, maskedR, maskedG, maskedB)` and `renderTexture(long id, ...)`; container renderers use it for their children and every renderer uses it for images
  - `renderer/impl/*Renderer.java`: one renderer per component type, all created with no-argument constructors
  - `renderer/style/StyleApplier.java` and `renderer/style/impl/*StyleApplier.java`: one applier per style type, which push and pop ImGui style vars and colors
  - `impl/ImGuiState.java`: internal, final; global state shared by the renderer, renderers and fonts (`hoveringScrollableWindow`, read by hosts only through `ImGuiRenderer.isHoveringScrollablePanel()`, and `currentContextPtr`, compared by `ImGuiFont.useFont` without a per-frame allocation)
  - `impl/ClassPathResources.java`: internal; opens class-path resources through the class loader, with a leading `/` optional (used by the renderer's font registration and `DecodedImage`)
- **Toolkit dependency**: imgui-java is a runtime dependency only (`compileOnly` plus `runtimeOnly` `[1.92.7.1,1.93)`); no ImGui type appears in an exported signature, so it is not part of the module's compile-time API. `lwjgl-stb` is an `implementation` dependency (runtime scope for consumers). `lwjgl-sdl` is `compileOnly`, for the SDL_GPU calls; at runtime it comes with imgui-java.

### loris-ui-jme3 (`jme3/`)
- **Purpose**: integrates the ImGui backend into jMonkeyEngine 3.
- **JPMS**: no `module-info.java` (jME3 jars split packages, so a named module can't read them). The jar is an automatic module named `lorisui.jme3` through the `Automatic-Module-Name` manifest attribute. The package has a `package-info.java`.
- **Dependencies**: compiles against `jme3-core`, `jme3-lwjgl3`, `lwjgl` and `lwjgl-sdl` as `compileOnly`, so its published metadata lists only `loris-ui-imgui`; the application declares the jME modules it uses (the `package-info.java` states this runtime requirement), and LWJGL comes with jME's LWJGL3 renderer.
- **Key Files**:
  - `ImGuiJmeDisplay.java`: implements `SceneProcessor` only. It owns a private `ImGuiOpenGlBackend`, an `ImGuiSdlGl3Renderer`, a `ScreenManager` and a `ResourceBundleKeyResolver`, and delegates screens (`addScreen`, `setCurrentScreen`), resource bundles (`setResourceBundle`), fonts (`registerFont*`, returning `Font`) and `registerRenderer`/`registerStyleApplier` to them. Font, renderer and style-applier registration is allowed only while the display is not attached, not while its release is pending or running (a `releasing` flag covers the teardown itself, for example registration from the `onEndScreen` it fires), and not after a failed initialization. The constructor has no Dear ImGui side effects. Each frame, `postQueue` reads the window size in logical window coordinates with `SDL_GetWindowSize` (an `IllegalStateException` with the SDL error if that fails) and passes it to the renderer; jME's camera and `reshape` sizes are not used. The display's viewport must therefore render to the window; offscreen viewports (render-to-texture, or a `FilterPostProcessor` on the same viewport) are documented as unsupported, as are jME's emulated display-scale modes (an `AppSettings` display-scale mode above 1). The sRGB framebuffer that the sRGB textures need comes from jME's gamma correction, which is on by default. The display is re-attachable; see Screen Lifecycle.
  - `ImGuiInputSystem.java`: package-private, final; a jME `RawInputListener` that marks mouse and key events consumed using only the `ImGuiSdlGl3Renderer` input-capture queries. jme3 has no `imgui.*` imports.

### loris-ui-lwjgl (`lwjgl/`)
- **Purpose**: hosts LorisUI in an application's own LWJGL window and loop, without a game engine: SDL3 with OpenGL 3 or SDL_GPU, or GLFW with OpenGL 3.
- **JPMS module**: `lorisui.lwjgl`, exporting `com.ivan1pl.lorisui.lwjgl` (with `package-info.java` and a module doc comment, both with a "which display to use" table, the typical setup per display and the sRGB requirement), `requires transitive lorisui.imgui`, `requires org.lwjgl.glfw` and `requires org.lwjgl.sdl`. It compiles against `lwjgl`, `lwjgl-sdl` and `lwjgl-glfw` as `compileOnly`; at runtime they come with imgui-java (GLFW and SDL natives only for linux, macos, macos-arm64 and windows). There is no `impl` package; shared host logic is package-private in the exported package.
- **Key Files**:
  - `ImGuiLwjglDisplayBase.java`: package-private, abstract, `<RendererType extends ImGuiRenderer>`. It owns the same four collaborators as the jME display (the backend, the renderer variant, a `ScreenManager`, a `ResourceBundleKeyResolver`) plus a `DeferredRelease`, all in private fields with package-private accessors, and declares the public registration, screen and bundle methods the three displays inherit. Package-private template methods (`initializeDisplay`, `renderFrame`, `runDeferred`, `closeDisplay`) implement the shared `initialize`/`close` state machine; the subclasses supply `setUp()` and `releaseInput()`. The release runs `DeferredRelease.runAll(deactivate, releaseInput, renderer::dispose, LorisScreen::shutdownLayoutUpdates)`.
  - `ImGuiLwjglSdlInput.java`: package-private, final; the SDL event consumption rule and the SDL text-input toggling shared by both SDL displays.
  - `ImGuiLwjglSdlGl3Display.java`: final, `AutoCloseable`; `ImGuiLwjglSdlGl3Display(long sdlWindow)` (`IllegalArgumentException` for `0`, no native calls), with an `ImGuiOpenGlBackend` and an `ImGuiSdlGl3Renderer`. The application keeps the window, the GL context and the loop: it calls `initialize()` with the context current, forwards every SDL event to `processEvent(long)` (returns whether the UI consumes it, using the `ImGuiInputSystem` rule; `false` while not initialized), calls `render(width, height)` once per frame in logical window coordinates (`SDL_GetWindowSize`) after clearing and before swapping, and calls `close()` before destroying the context or window. All precondition checks run before any native call.
  - `ImGuiLwjglGlfwGl3Display.java`: final, `AutoCloseable`; `ImGuiLwjglGlfwGl3Display(long glfwWindow)` (`IllegalArgumentException` for `0`; no GLFW call and no callback object until `initialize()`), with an `ImGuiOpenGlBackend` and an `ImGuiGlfwGl3Renderer`. Input is chained, not forwarded by the application: `initialize()` sets GLFW's global monitor callback to `null` around the renderer's `initialize()`, then gives the application's monitor callback back and frees Dear ImGui's stub, and installs seven own window callbacks (window focus, cursor enter, cursor position, mouse button, scroll, key, char) in front of the application's, which must be set before `initialize()`. Each event goes to Dear ImGui first and to the application's previous callback only when the UI does not consume it (the `ImGuiInputSystem` rule; focus and cursor enter are never consumed). Release restores the application's callbacks, keeping any newer callback the application set after `initialize()`, never frees the application's wrappers, and frees the display's own seven. `close()` called during one of the display's callback dispatches throws `IllegalStateException` before any state change; a failure thrown during a dispatch (by LorisUI or the application's chained callback) is caught, later events are dropped, and the next `render()` or `close()` rethrows it (`RuntimeException`/`Error` as-is, others wrapped in `RuntimeException`). The package-private `dispatch(Runnable)` seam carries these rules. `render(width, height)` takes the `glfwGetWindowSize` size; there is no text-input toggling, because GLFW always delivers characters.
  - `ImGuiLwjglSdlGpuDisplay.java`: final, `AutoCloseable`; `ImGuiLwjglSdlGpuDisplay(long sdlWindow, long gpuDevice)` (`IllegalArgumentException` for a `0` window, checked first, or a `0` device; it never destroys either), with an `ImGuiSdlGpuBackend` and an `ImGuiSdlGpuRenderer`. `processEvent` and SDL text input work as in the SDL3 + OpenGL 3 display. `render(width, height, commandBuffer, targetTexture)` throws `IllegalArgumentException` for a `0` command buffer before any state check; a `0` target (minimized window) still processes input and builds the frame. The application claims the window for the device and sets an `SDR_LINEAR` swapchain before `initialize()`, acquires the command buffer and swapchain texture, clears and submits around each `render`, and calls `close()` before releasing the window from the device or destroying the device.

### examples (`examples/`)
- **Purpose**: demo applications and manual test bed. It applies only the `java` plugin and registers the `runJme3Example`, `runLwjglSdlGl3Example`, `runLwjglGlfwGl3Example` and `runLwjglSdlGpuExample` `JavaExec` tasks (group `application`), which pass `--enable-native-access=ALL-UNNAMED`; `runLwjglSdlGpuExample` also passes the `lorisui.example.gpuDebug` system property through (`-Dlorisui.example.gpuDebug=true` creates the SDL_GPU device in debug mode, with validation).
- **Key Files**:
  - `example/shared/ExampleScreen.java`: a host-agnostic `LorisScreen` that exercises the components; its constructor takes the font and a required `hideUiAction`, wired to a "Hide UI" button (bundle key `global.hideUi`); "Tab 3" shows a 540×100 `ImageMode.repeat()` image of `/textures/textures.png` above its text, so every example shows Repeat tiling with partial edge tiles
  - `example/shared/ExampleSettings.java`: shared constants of all examples (800×600 window, English locale, `global` bundle at `bundles.global`, the Open Sans font resource at size 20, the screen name)
  - `example/jme3/LorisJme3Example.java`: a jME `SimpleApplication` with OpenGL 3.3. F1 toggles the UI by removing and re-adding the display on the GUI viewport; "Hide UI" removes the display from inside the frame (F1 brings it back); `destroy()` removes the display if it is attached
  - `example/lwjgl/LorisLwjglSdlGl3Example.java`: creates an SDL3 window with a 3.3 core, sRGB-capable OpenGL context (`GL_FRAMEBUFFER_SRGB` enabled, high pixel density), runs an `ImGuiLwjglSdlGl3Display` in try-with-resources and a poll/clear/render/swap loop. "Hide UI" closes the display permanently from inside the frame, and the window keeps clearing to black until it is closed
  - `example/lwjgl/LorisLwjglGlfwGl3Example.java`: the same for a GLFW window (3.3 core, forward-compatible, `GLFW_SRGB_CAPABLE`, `GL_FRAMEBUFFER_SRGB` enabled) and an `ImGuiLwjglGlfwGl3Display`. Its key callback only requests the close on Escape (reached only when the UI does not consume the key), and the loop calls `close()` after `glfwPollEvents` returns; a mouse-button callback prints the clicks the UI does not consume. It frees its callbacks with `Callbacks.glfwFreeCallbacks` after the display is closed
  - `example/lwjgl/LorisLwjglSdlGpuExample.java`: creates an SDL3 window without OpenGL, an SDL_GPU device (debug mode from `lorisui.example.gpuDebug`) and claims the window, fails with a clear message when the `SDR_LINEAR` swapchain composition is unsupported, then runs an `ImGuiLwjglSdlGpuDisplay` with an acquire/clear/render/submit loop and waits for the GPU to go idle before releasing the window and destroying the device

## Data Flow

**Setup**
1. The host app creates a display (`ImGuiJmeDisplay(context, inputManager, guiViewPort)`, `ImGuiLwjglSdlGl3Display(sdlWindow)`, `ImGuiLwjglGlfwGl3Display(glfwWindow)` or `ImGuiLwjglSdlGpuDisplay(sdlWindow, gpuDevice)`), registers fonts, custom renderers and style appliers and resource bundles, adds `LorisScreen`s and selects the current screen. Nothing native happens yet. The GLFW application also sets its own input callbacks; the SDL_GPU application creates the device, claims the window for it and sets an `SDR_LINEAR` swapchain.
2. The display is initialized: jME calls `initialize` lazily, on the first frame (or window resize, through `RenderManager.notifyReshape`) after the display is added to a viewport; the LWJGL application calls `initialize()` itself. The renderer creates its context, replays the fonts and sets up its variant's platform and renderer Impl objects; the jME display then registers its input listeners, and the GLFW display gives the application's monitor callback back and chains its seven input callbacks. Finally `ScreenManager.activate()` fires `onStartScreen()` on the current screen.

**Per frame** (jME `postQueue`, LWJGL `render`):
1. The host passes the screen size in logical window coordinates: the jME display queries `SDL_GetWindowSize` each frame, and the LWJGL application passes the size to the display's `render` (`SDL_GetWindowSize` for the SDL displays, `glfwGetWindowSize` for the GLFW display). The SDL_GPU application first acquires a command buffer and the swapchain texture and clears the texture in its own pass, then passes both to `render(width, height, commandBuffer, targetTexture)`. The renderer variant's `render` makes its context current and starts an ImGui frame.
2. `LorisScreen.render(backend, w, h, resolver)`:
   - If the previous `layout()` call threw or returned `null`, the failure is rethrown once as an `IllegalStateException` (cause = original failure) and nothing is rendered in that call; later frames render the last successful layout. Hosts should treat it as fatal.
   - If the layout was invalidated (`setLayoutNeedsUpdate(true)`, callable from any thread; the update flag is an `AtomicBoolean`), `layout()` is scheduled on the shared single-thread daemon layout worker (`lorisui-layout`), which is created lazily and stopped by `LorisScreen.shutdownLayoutUpdates()`. The new `List<Component>` is published through a `volatile` field and replaces `content` asynchronously; in the meantime the previous content keeps rendering (an empty list before the first layout).
   - Calls `backend.render(w, h, content, resolver)`.
3. `ImGuiBackend.render` looks up the `Renderer` for each component, and each renderer emits ImGui calls. Containers (Panel, TabbedPanel, Popup) recurse through `RendererProvider`, passing the screen size unchanged, so size and content functions receive the screen's width and height at every nesting level, not the parent's size, and so do the position functions of top-level panels and popups (a nested panel is placed by its parent's layout; `TabbedPanel` tab-label functions, called once at build, receive the tab button's size). Styles are applied through `StyleApplier`s. Text keys are resolved through `BundleKeyResolver`. Images are loaded or fetched from the backend's cache through `RendererProvider.loadTexture(...)` and drawn with `RendererProvider.renderTexture(...)` according to their `ImageMode` (`Repeat` as a tile grid). On SDL_GPU, a texture loaded during the build is uploaded with its own command buffer, submitted at once, so it executes before the frame's buffer. A missing or unreadable image (`Image` or panel `Background`) makes the renderer throw a `RuntimeException` wrapping the `IOException`; failures are not cached, so the screen's render fails again on every draw.
4. ImGui draw data is rendered by the variant: the GL3 variants draw into the current OpenGL framebuffer, and the application swaps afterwards; the SDL_GPU variant runs `prepareDrawData` outside any pass and then draws in its own `LOADOP_LOAD`/`STOREOP_STORE` pass into the target texture on the application's command buffer (nothing when the target is `0`), and the application submits the buffer afterwards. The renderer ends the ImGui frame even when `LorisScreen.render` throws; the screen's exception propagates, with any frame-close failure suppressed.

**Input**: SDL events reach ImGui IO through the SDL variants' `processSdlEvent`. In jME, an SDL event listener forwards them, and in parallel `ImGuiInputSystem` marks jME raw input events consumed when `wantsMouseInput()`/`wantsKeyboardInput()` report that the UI wants them; mouse-wheel events are consumed only while `isHoveringScrollablePanel()`. With the two SDL displays the application passes each event to `processEvent`, which forwards it and applies the same rule to its return value. The GLFW display's chained callbacks forward each event to the matching `ImGuiGlfwGl3Renderer.processGlfw*` method and call the application's previous callback only when the same rule says the UI does not consume it. Component callbacks (for example button actions) run during rendering on the host's UI thread.

**Teardown**: removal (jME `cleanup`) or `close()` (LWJGL) → `ScreenManager.beginDeactivation()` → `DeferredRelease.request()`, deferred to the end of the outermost operation if requested during a frame, a screen switch or a hook → `ScreenManager.deactivate()` (`onEndScreen`) → LWJGL host input released (SDL text input stopped, or the GLFW callbacks restored and freed) → renderer `dispose()` (context current → GPU idle, SDL_GPU only → textures → renderer Impl (Gl3 or SdlGpu3) → platform Impl (Sdl3 or Glfw) → context → font handles unbound) → `LorisScreen.shutdownLayoutUpdates()`. Each step runs even when an earlier one fails (`DeferredRelease.runAll`); the first failure propagates and later ones are suppressed. The SDL_GPU application then waits for the GPU to go idle, releases the window from the device and destroys the device, the window and SDL; the GLFW application frees its own callbacks after `close()`.

## Screen Lifecycle
All display calls and screen hooks run on the host's UI thread (the jME render thread, or the thread that owns the window and its GL context or GPU device; for GLFW, the main thread). No display implements `BundleKeyResolver`; each passes its internal `ResourceBundleKeyResolver` to the renderer, and applications that need key resolution create their own resolver.

**Shared rules (`ScreenManager`)**:
- A screen receives `onEndScreen()` only if its `onStartScreen()` returned normally, and at most once per start; a screen whose `onStartScreen()` threw counts as not started. Hook exceptions propagate out of the method that fired them.
- `addScreen(name, screen)`: `NullPointerException` for null arguments, `IllegalStateException` for a name that is already registered. Fires no hooks and is allowed from inside hooks.
- `setCurrentScreen(name)`: `IllegalStateException` from inside a hook, then `NullPointerException` for null and `IllegalStateException` for an unknown name, all before any state change; switching to the current screen does nothing. While the display is not initialized it only records the name. While initialized the switch is immediate: the new screen becomes current, then `onEndScreen()` fires on the old screen and `onStartScreen()` on the new one, during the call; the new screen is drawn from the next frame. The switch always completes: if the old screen's `onEndScreen()` throws, the new screen is still started, then the end failure propagates (a different start failure is added to it as suppressed). It may be called from a component callback, in which case the old screen finishes drawing the current frame.
- **Re-entrancy guard**: `setCurrentScreen`, `activate()` and `deactivate()` called from inside `onStartScreen()`/`onEndScreen()` throw `IllegalStateException` before changing state. Screens switch later instead, for example from a component callback.
- **Two-phase deactivation**: `beginDeactivation()` makes the manager inactive without a hook (allowed inside hooks; a switch or activation already in progress still completes). From then on `setCurrentScreen` only records the choice, and `deactivate()` fires `onEndScreen()` on the screen started before, even if another screen has been selected since; it also ends a started screen while the manager is already inactive. `activate()` throws `IllegalStateException` while a begun deactivation has not been completed with `deactivate()`.

**Deferred teardown (all hosts)**: each display runs its operations that can call application code (rendering a frame, `setCurrentScreen`, and the activate step of `initialize`) through its `DeferredRelease`. A teardown request stops the display at once (the jME display removes its input listeners and `isInitialized()` returns `false`; an LWJGL display is closed, the SDL displays' `processEvent` returns `false` and the GLFW display passes every event to the application's callbacks), calls `ScreenManager.beginDeactivation()` and then `DeferredRelease.request()`. If an operation is running (a component callback, such as the examples' "Hide UI" button, or a screen hook), the release runs after the outermost one, once the frame has closed or the hook has returned. The renderer is therefore never disposed inside a frame and `deactivate()` never runs inside a hook. While the release is pending, `setCurrentScreen` fires no hooks and only records the choice; the recorded screen becomes current and, on the re-attachable jME display, starts on the next attach. Release failures propagate from that operation, or are added as suppressed to its exception if it is already throwing.

**jME host (`ImGuiJmeDisplay`)**:
- `initialize`: throws `IllegalStateException` if an earlier initialization failed, if the display is already initialized or its deferred release has not completed, or if no current screen is set, all before any side effect. If setting up the renderer or registering the listeners fails, it marks the display failed, removes the listeners, disposes the renderer and rethrows, so jME's per-frame retry fails fast; no hooks fire and the display is permanently unusable (registration also throws). Otherwise it ends with `ScreenManager.activate()` (`onStartScreen()`); a throwing `onStartScreen()` propagates and the display stays initialized.
- `postQueue` returns early when the display is not initialized, because jME iterates a snapshot of the viewport's processors and can still call a display removed earlier in the same frame.
- `cleanup`: jME calls it when the display is removed from its viewport (`ViewPort.removeProcessor`/`clearProcessors`). A no-op unless initialized. Otherwise it tears down (deferred if an operation run through its `DeferredRelease` is in progress).
- **Re-attach**: a cleaned-up display can be added to a viewport again. It re-creates the context, replays the fonts (the `Font` handles stay valid) and starts the current screen again; screens, bundles, renderers and style appliers stay registered, and fonts, renderers and style appliers can be registered again between removal and re-attach. Dear ImGui UI state starts fresh. Re-adding the display in the same callback that removed it is safe, because jME initializes it on a later frame, after the deferred release.
- Only one display may be attached at a time.
- **Application exit**: jME does not call `cleanup` on exit. Applications that want `onEndScreen()` and the native release at exit remove the display themselves; `LorisJme3Example` overrides `destroy()` and calls `guiViewPort.removeProcessor(imGuiJmeDisplay)` (only if attached, since `removeProcessor` calls `cleanup` even for a processor that is not attached) before `super.destroy()`.

**LWJGL host (`ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay`)**: the rules below come from the shared base and apply to all three displays unless noted.
- `initialize()`: `IllegalStateException` if closed, already initialized, or no current screen is set, all before side effects. If the renderer fails to initialize, the exception propagates, the renderer has released what it set up, and the display stays uninitialized and can be retried (after a failure caused by a registered font, create a new display instead). Then it marks itself initialized and calls `ScreenManager.activate()`; a throwing `onStartScreen()` propagates and the display stays initialized.
- `render` throws `IllegalStateException` when not initialized or closed; the SDL displays' `processEvent` returns `false` then. The SDL_GPU display's `render` checks for a `0` command buffer first (`IllegalArgumentException`).
- SDL text input (both SDL displays, through `ImGuiLwjglSdlInput`): after each frame that returns normally (and only while still initialized), `render` compares the renderer's `wantsTextInput()` with the state it last applied and calls `SDL_StartTextInput`/`SDL_StopTextInput` for the window, because imgui-java's SDL3 backend does not port Dear ImGui's `Platform_SetImeDataFn` and SDL3 delivers no `SDL_EVENT_TEXT_INPUT` until text input is started. A refused start is not recorded, so the next frame retries; release stops text input if it was started (after `onEndScreen`, before the renderer's `dispose()`). The jME host needs no such step, as jME's `SdlKeyInput` starts text input itself, and neither does the GLFW display, as GLFW always delivers characters.
- `close()`: idempotent and **final** (`AutoCloseable` semantics): the display is marked closed at once, so later `register*`, `initialize` and `render` throw, while `addScreen`, `setCurrentScreen` and `setResourceBundle` only record. If initialized, it releases immediately, or deferred when called during a frame, a screen switch or a hook. To show UI again, the application creates a new display. Closing before `initialize()` only marks the display closed.
- GLFW display only: `close()` called during one of its GLFW callback dispatches (from the application's chained callback, or from a hook or component code that callback runs) throws `IllegalStateException` before any state change, because the release would destroy cursors and free the executing callback stub inside a GLFW callback; the application requests the close there and calls `close()` after `glfwPollEvents` returns. A failure thrown during a dispatch is kept, later events reach neither the UI nor the application, and the next `render()` (before drawing) or `close()` (after closing, with a release failure suppressed) rethrows it once. Closing from a component callback during `render()` ("Hide UI") is deferred as usual. `render()` must not be called from a GLFW callback.
- Only one display may be initialized at a time.

## Extension Points
- **New built-in component**: add a class to `api/component` (with a Builder), add a renderer in `imgui/renderer/impl`, and register it in the `ImGuiBackend` constructor.
- **New built-in style**: add a class to `api/component/style`, add an applier in `imgui/renderer/style/impl`, and register it in the `ImGuiBackend` constructor.
- **Custom components or styles (library users)**: extend `Renderer`/`StyleApplier` and register them with `registerRenderer`/`registerStyleApplier`, either on an `ImGuiBackend` or on a display (`ImGuiJmeDisplay`, `ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay`) before it is initialized. A registration replaces any existing mapping, including a built-in one, and subclasses without their own mapping use the nearest registered ancestor. Renderers load and draw textures through the `RendererProvider` they receive. A custom renderer calls Dear ImGui directly, so its code adds imgui-java to its own build and, on the module path, `requires imgui.binding`. The displays keep their backend private; registration is the only customization path, which also covers the former "custom backend in the jME host" need.
- **Custom texture backend / another graphics API**: a custom `ImGuiBackend` subclass (implementing `createTexture`/`deleteTexture`, for example to load textures differently on OpenGL) pairs only with the GL3 renderers, because its textures must be OpenGL texture names; both concrete backends are final, and each bundled display uses its own backend (`ImGuiOpenGlBackend` for jME and the two GL3 displays, `ImGuiSdlGpuBackend` for the SDL_GPU display). A new graphics API needs a new variant of the sealed `ImGuiRenderer` inside `lorisui.imgui`, so it is not an extension point.
- **New backend**: implement `Backend.render` (and its own registry mechanism) in a new module that depends only on `loris-ui-api`.
- **New host**: a module that depends only on `loris-ui-imgui`. Wrap an `ImGuiRenderer` variant and its matching backend (`ImGuiOpenGlBackend` for the GL3 variants, `ImGuiSdlGpuBackend` for `ImGuiSdlGpuRenderer`) in the target's render hook, keep screens in a `ScreenManager`, resolve text with a `ResourceBundleKeyResolver`, use the renderer's input-capture queries for input routing (starting SDL text input on `wantsTextInput()` unless the framework does; with the GLFW variant, forwarding the window's callbacks and restoring the global monitor callback after `initialize()`), provide an sRGB framebuffer, and defer teardown requested during a frame or hook with a `DeferredRelease` plus `ScreenManager.beginDeactivation()`, as the bundled hosts do.

## Known Architectural Concerns
- **Emulated jME display-scale modes (> 1) unsupported**: with an `AppSettings` display-scale mode above 1, jME renders the GUI into a framebuffer sized framebuffer × mode, while Dear ImGui sizes its viewport from the logical window size times the framebuffer scale, so the UI covers only part of the window. The jME Javadoc documents this; there is no runtime detection.
- **jME viewport must render to the window**: the jME display sizes the UI from the window's logical size, so its viewport must render to the window. Offscreen viewports (render-to-texture, or a `FilterPostProcessor` on the same viewport) are unsupported; the jME Javadoc documents this, and there is no runtime detection.
- **Dear ImGui asserts end the JVM**: imgui-java calls `System.exit(1)` after any failed Dear ImGui assertion, even with a custom `ImGui.setAssertCallback` handler, which can only log or pick the exit code. The renderer disables error-recovery asserts so frame exceptions reach the host, and its in-frame guard plus the hosts' deferred teardown remove the known `DestroyContext` trigger (a locked font atlas); other asserts still terminate. This is documented in the `ImGuiRenderer` and `lorisui.imgui` Javadoc. An SDL_GPU validation failure in debug mode can also end the process.
- **Native lifecycle verified manually only**: context creation and destruction, Impl shutdown, font replay, GL texture deletion, GPU texture upload and release, the SDL_GPU frame, native GLFW callback chaining and re-attach cannot be unit-tested (no native context in tests), and are checked by hand with the four examples. Only the native-free paths are unit-tested: the deferred-teardown state machine (`DeferredRelease`, `ScreenManager.beginDeactivation`, and their host composition mirrored in `HostLifecycleCompositionTest`), the gating of the three renderer variants and `ImGuiSdlGpuBackend`, `ImGuiFont` glyph-range validation, `TextureTiling`, `DecodedImage`'s missing-resource path, the pre-initialize paths of the three LWJGL displays and the GLFW display's dispatch rules (through its package-private `dispatch` seam); `jme3` and `examples` have no tests.
- **UI state on re-attach**: every re-attach creates a new Dear ImGui context, so selected tabs, scroll positions, open popups and keyboard focus reset; LorisUI-held state (bindings, `TabbedPanel`/`ComboBox` model values) is kept.
- **Global SDL hints**: imgui-java's SDL3 backend (both SDL variants) sets `SDL_HINT_MOUSE_FOCUS_CLICKTHROUGH`, `SDL_HINT_MOUSE_AUTO_CAPTURE` and `SDL_HINT_BORDERLESS_WINDOWED_STYLE` on every `initialize()`; they stay set after `dispose()`.
- **GLFW monitor callback**: Dear ImGui's GLFW backend replaces GLFW's global monitor callback on every `initialize()` and never restores it. `ImGuiLwjglGlfwGl3Display` gives the application's callback back; a host using `ImGuiGlfwGl3Renderer` directly must do so itself.
- **GLFW close and callback failures**: `close()` is rejected inside the GLFW display's callbacks, and must not be called from any other GLFW callback either (such as a window-close callback; not detected), so integrators request the close there and call `close()` after `glfwPollEvents` returns. A failure in a callback dispatch surfaces from the next `render()`/`close()`, and events arriving in between (usually the rest of that poll) reach neither the UI nor the application. Calling `render()` from a GLFW callback the display does not own, such as a window-refresh callback, is unsupported.
- **GLFW HiDPI on Windows and X11**: GLFW measures windows in pixels there (no `GLFW_SCALE_TO_MONITOR`), so the UI is not scaled up on HiDPI monitors. Documented, not fixed.
- **sRGB framebuffer required**: textures are sRGB on every variant (`GL_SRGB_ALPHA` / `R8G8B8A8_UNORM_SRGB`) and the Dear ImGui font atlas is UNORM, so every host must write through an sRGB framebuffer: `GL_FRAMEBUFFER_SRGB` on an sRGB-capable default framebuffer for the GL3 hosts, jME's gamma correction (on by default), and the `SDR_LINEAR` swapchain composition for SDL_GPU. A host without it shows different colors.
- **`SDR_LINEAR` support**: the `SDR_LINEAR` swapchain composition depends on the driver. The SDL_GPU example checks `SDL_WindowSupportsGPUSwapchainComposition` and fails with a clear message; a host that cannot get it sees darker images than the GL path. The swapchain parameters must not change while the renderer is initialized.
- **GPU release before submit**: closing the SDL_GPU display inside a frame releases GPU resources at the end of `render`, before the application submits that frame's command buffer; this relies on SDL_GPU deferring the release of resources already recorded in a command buffer, and is checked by hand ("Hide UI" in the SDL_GPU example, ideally with `-Dlorisui.example.gpuDebug=true`).
- **Repeat item count**: a `Repeat` image creates one Dear ImGui item per tile, so a small texture over a large area costs many items. Like the *Resize modes, it assumes it is drawn from the left edge of the current window, which holds for the built-in renderers.
- **Wrap mode**: GL textures use `GL_CLAMP_TO_EDGE`, so sprite cells at a texture border no longer blend with the opposite edge when filtered linearly.
- **Context left current**: the renderer leaves its Dear ImGui context current after every call, so an application that uses its own Dear ImGui context must restore it.
- **Global state**: `ImGuiState` holds static flags (`hoveringScrollableWindow`, `currentContextPtr`), and `LorisScreen` shares one static layout worker across screens; only one renderer and one display may be in use at a time.
- **Texture cache**: per backend, cleared as a whole by `unloadTextures()` (and by renderer teardown); there is no per-path eviction while a backend is in use.
- **Missing images**: a texture that fails to load is retried and fails again on every draw instead of failing once.
- **Renderer robustness**: `ImGuiRenderer` disables ImGui's error-recovery assert and tooltip, so state left open by a throwing renderer (windows, IDs, style stacks) is unwound when the frame closes and the original exception propagates to the host; the trade-off is that an imbalance that does not throw is recovered silently instead of failing fast. The input renderers pop their item width in `finally`, the combo box uses `setNextItemWidth`, and the progress bar pops its style in `finally`, but other push/pop pairs (combo style vars, per-item IDs, `beginChild`/`endChild` in the panel and combo renderers) are still not in `try/finally`. `TextInput` and `NumberInput` both use the bare `"##"` ImGui label without a per-component ID, so two inputs in the same window share an ImGui ID.

## Configuration
- Build-time: Gradle `ext` versions in the root `build.gradle`; Checkstyle rules in `config/checkstyle/`; editor settings in `.editorconfig`
- Runtime: done in code through any display (fonts, renderers and style appliers, resource bundles, screens). The examples' shared settings live in `ExampleSettings`; the jME window settings in `LorisJme3Example.createDefaultSettings()`.
- i18n: `ResourceBundle`s registered by name (for example `bundles.global`)
- Resources (fonts, textures) are class-path resource names; a leading `/` is optional. On the module path they must be outside any package of a named module, or in a package the application module opens unconditionally.

## Deployment Architecture
LorisUI is a library, so it isn't deployed as a service. It's published as Maven artifacts (`loris-ui-api`, `loris-ui-imgui`, `loris-ui-jme3`, `loris-ui-lwjgl`), each with sources and Javadoc jars and a POM with name, description, url, license, developer and scm, and consumed by desktop game applications. Publishing goes only to the local Maven repository (`./gradlew publishToMavenLocal`); no remote repository is configured, and `examples` is not published. `loris-ui-jme3` does not bring jMonkeyEngine: its consumers declare `jme3-core` and `jme3-lwjgl3` (plus any other jME modules they use) themselves. imgui-java (which brings LWJGL with its SDL, GLFW and OpenGL bindings and natives, the GLFW and SDL natives only for Linux, macOS, macOS arm64 and Windows) is pulled in at runtime; `lwjgl-stb` is an `implementation` dependency of `loris-ui-imgui` (runtime scope for consumers) with natives for Windows, Linux, macOS and macOS arm64. On JDK 25, applications pass `--enable-native-access` (`ALL-UNNAMED` on the class path, the module names on the module path) to avoid the restricted-method warnings of imgui-java and LWJGL; the examples' run tasks pass `ALL-UNNAMED`. Running the SDL- and GLFW-based examples on macOS may additionally need `-XstartOnFirstThread`, which the run tasks don't pass. Consumer Javadoc states `--enable-native-access` in the `lorisui.imgui`, `lorisui.lwjgl` and jme3 package docs, and `-XstartOnFirstThread` in the LWJGL host's docs.

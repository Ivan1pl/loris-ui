# System Architecture

## Overview
LorisUI is a layered, multi-module Java library. Game code describes UI as trees of plain component objects defined in a toolkit-agnostic API. A **backend** turns those trees into draw calls each time the host renders, and a **host integration** connects the backend to an application's render loop and input. Two host modules ship with the library: one for jMonkeyEngine 3 and one for an application's own LWJGL window and loop, with a display for each supported platform/renderer pair (SDL3 with OpenGL 3, GLFW with OpenGL 3, SDL3 with SDL_GPU, SDL3 with Vulkan). The jME display draws with OpenGL 3 or OpenGL ES 3, whichever matches jME's renderer.

```
examples ──┬──▶ loris-ui-jme3  ──┬──▶ loris-ui-imgui ─────────────────────────────▶ loris-ui-api
 (demos)   │    (jME3 host:      │    (ImGui backends and renderers:          ▲    (component model,
           │     GL3 / GLES3)    │     OpenGL 3, GLES 3, SDL_GPU, Vulkan)      │     Backend port, screens;
           └──▶ loris-ui-lwjgl ──┘         │                                   │     zero dependencies)
                (LWJGL host:               ├──▶ loris-ui-imgui-vulkan ─────────┘
                 SDL3 / GLFW)              │    (MIT: Vulkan renderer port)
                                           └──▶ loris-ui-imgui-gles3
                                                (MIT: OpenGL ES 3 renderer port)
```

## Architecture Pattern
**Pattern**: Layered library with a ports-and-adapters style backend abstraction, plus registries of strategies (renderers and style appliers) inside the backend.

- **Port**: `api/.../api/backend/Backend.java` declares a single method, `render(int w, int h, List<Component> components, BundleKeyResolver bundleKeyResolver)`. It contains nothing toolkit-specific: textures, fonts and input capture are backend concerns.
- **Adapters**: `imgui/.../imgui/backend/ImGuiBackend.java` (abstract: registries with the registration API, the per-instance texture cache, texture drawing, and the protected abstract texture creation and deletion), `ImGuiOpenGlBackend.java` (final; OpenGL textures), `ImGuiOpenGlEsBackend.java` (final; OpenGL ES textures), `ImGuiSdlGpuBackend.java` (final; SDL_GPU textures) and `ImGuiVulkanBackend.java` (final; Vulkan textures).
- **Frame driver**: the sealed `imgui/.../imgui/ImGuiRenderer.java` owns the Dear ImGui context and runs one frame per call; its five final variants own the platform and renderer objects of one pair each: `ImGuiSdlGl3Renderer` (SDL3 + OpenGL 3, used by the jME host on desktop OpenGL and by `ImGuiLwjglSdlGl3Display`), `ImGuiGlfwGl3Renderer` (GLFW + OpenGL 3), `ImGuiSdlGles3Renderer` (SDL3 + OpenGL ES 3, used by the jME host on ANGLE), `ImGuiSdlGpuRenderer` (SDL3 + SDL_GPU) and `ImGuiSdlVulkanRenderer` (SDL3 + Vulkan 1.3).
- **Hosts**: `jme3/.../jme3/ImGuiJmeDisplay.java` drives the renderer from jMonkeyEngine, choosing the GL3 or GLES3 pair from jME's renderer setting; the four displays in `lwjgl/.../lwjgl/` (`ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay`, `ImGuiLwjglSdlVulkanDisplay`) are embedded in an application that owns its window, OpenGL context, GPU device or Vulkan device, and loop. All keep their screens in an `api` `ScreenManager`, resolve text with an `api` `ResourceBundleKeyResolver` and defer teardown with an `api` `DeferredRelease`. These host-support helpers live in `lorisui.api` because the automatic `lorisui.jme3` module can only read exported packages.

**Rule**: dependencies only point towards `api`. `loris-ui-api` must not depend on any toolkit, engine or third-party library. The two renderer-port modules sit below `loris-ui-imgui` as internal helpers: `loris-ui-imgui-vulkan` depends only on `loris-ui-api`, `loris-ui-imgui-gles3` on no LorisUI module, and nothing but `loris-ui-imgui` depends on them. They are separate subprojects only because their code is MIT-licensed (see their section under System Structure).

## System Structure

### loris-ui-api (`api/`)
- **Purpose**: the public, toolkit-agnostic contract: component model, styles, backend port, screens and their lifecycle, fonts and i18n.
- **JPMS module**: `lorisui.api`. It exports `backend`, `component`, `component.style`, `core`, `font`, `resolver` and `screen`, each with a `package-info.java`; the module descriptor has a module doc comment.
- **Packages** (`com.ivan1pl.lorisui.api.*`):
  - `component`: the `Component` marker interface and concrete components (`Panel`, `Button`, `Text`, `Image`, `TextInput`, `NumberInput`, `ComboBox`, `ProgressBar`, `TabbedPanel`, `Popup`, `ModalPopup`, `Spacer`), plus `Layout`, `Background` and the sealed `ImageMode`
  - `component.style`: `Style` and its concrete styles (`ScrollbarStyle`, `ComboBoxStyle`, `ComboBoxPopupStyle`, `ComboBoxItemStyle`, `TextInputStyle`)
  - `backend`: the `Backend` interface (only)
  - `screen`: the abstract `LorisScreen` (template method for screens; static `shutdownLayoutUpdates()` stops the background layout work, which restarts lazily on the next requested layout), the final `ScreenManager` and the final `DeferredRelease`.
    - `ScreenManager` is the host-neutral registry of named screens. It validates registration and switching, fires matched `onStartScreen`/`onEndScreen` hooks through `activate()`/`setCurrentScreen`/`deactivate()`, and rejects `setCurrentScreen`, `activate()` and `deactivate()` called from inside a hook (`IllegalStateException`, before any state change). `beginDeactivation()` makes it inactive without firing a hook (allowed inside hooks); `deactivate()` later ends the screen that was started.
    - `DeferredRelease` is the host-neutral teardown helper: `run(operation)` tracks operations that can call application code, `request()` releases at once or after the outermost running operation (`isRunning()`, `isPending()` report the state), and the static `runAll(steps...)`/`runAfterFailure(failure, cleanup)` run multi-step releases keeping every failure.
    - Both are not thread-safe; hosts call them on their UI thread.
  - `core`: the final `Color` and `IntBiFunction<ResultType>`, the content function that receives the screen width and height
  - `font`: the `Font` marker interface
  - `resolver`: `BundleKeyResolver` (i18n) and the final `ResourceBundleKeyResolver`, which resolves `bundleName.key` keys from `ResourceBundle`s registered by name
- **Conventions**: components are immutable-ish value holders built with nested static `Builder`s and non-public constructors. The Panel family is closed to the package: `Panel`'s constructor and its self-typed `BaseBuilder<PanelType, BuilderType>` are package-private, and `Button`, `Popup` and `ModalPopup` have private constructors.

### loris-ui-imgui (`imgui/`)
- **Purpose**: renders the API component model with Dear ImGui on OpenGL 3, OpenGL ES 3, SDL_GPU or Vulkan, and drives Dear ImGui frames for the hosts.
- **JPMS module**: `lorisui.imgui`, with `requires transitive lorisui.api` so consumers of the backend read the API types; plain `requires` for imgui-java (`imgui.binding`, `imgui.lwjgl3`), LWJGL's `org.lwjgl.opengl`, `org.lwjgl.sdl` (the SDL_GPU calls) and `org.lwjgl.stb`, and the two renderer-port modules `lorisui.imgui.gles3` and `lorisui.imgui.vulkan` (which export their package only to `lorisui.imgui`, so on the module path both must be present at runtime for every host, and no application requires them); and plain `requires static org.lwjgl.opengles` and `requires static org.lwjgl.vulkan`, never `transitive`: only the GLES3 and Vulkan variants and their backends use them, so GL-only and SDL_GPU consumers need neither, and jME consumers need neither at compile time. A `requires static` module is not added to the module graph at runtime, so a modular application in which a variant runs resolves its binding: a Vulkan application declares `requires org.lwjgl.vulkan` itself, and a modular jME application on jME's default ANGLE renderer (the GLES3 variant) declares `requires org.lwjgl.opengles` or starts with `--add-modules org.lwjgl.opengles`, as jME itself needs under that renderer (see `standards/architecture/modules.md`). It exports `imgui`, `imgui.backend`, `imgui.renderer` and `imgui.renderer.style` (each with a `package-info.java`; the descriptor has a module doc comment). **It does not export** `imgui.impl`, `backend.impl`, `renderer.impl` or `renderer.style.impl`, which are internal. There is no `imgui.font` package.
- **Key Files** (`com.ivan1pl.lorisui.imgui.*`):
  - `ImGuiRenderer.java`: `public abstract sealed`, permitting exactly the five final variants below (`ImGuiSdlGl3Renderer`, `ImGuiGlfwGl3Renderer`, `ImGuiSdlGpuRenderer`, `ImGuiSdlGles3Renderer`, `ImGuiSdlVulkanRenderer`); the frame driver. Its constructor and its hooks (`initBackends`, `newBackendFrame`, `shutdownRendererBackend`, `shutdownPlatformBackend`, `clearBackends`, the no-op `awaitDeviceIdle`) and the `isRendering()` query are package-private, so the hierarchy is closed to the package; the base has no public `render`, because the variants' signatures differ. Lifecycle:
    - The variant constructors take a backend and the window handle and make no native calls: `ImGuiSdlGl3Renderer(ImGuiBackend, sdlWindow)` (any handle accepted, as before the rename), `ImGuiGlfwGl3Renderer(ImGuiBackend, glfwWindow)`, `ImGuiSdlGles3Renderer(ImGuiBackend, sdlWindow)` and `ImGuiSdlGpuRenderer(ImGuiSdlGpuBackend, sdlWindow)` (`IllegalArgumentException` for a `0` window; the typed backend prevents pairing a GL backend with the GPU renderer). A null backend throws `NullPointerException`, checked first. `ImGuiSdlVulkanRenderer(ImGuiVulkanBackend, sdlWindow, colorAttachmentFormat, framesInFlight)` checks its primitives first, before the null backend (`IllegalArgumentException` for a `0` window, a non-positive format or fewer than one frame in flight, in that order), because no Vulkan object can exist in a unit test; it then takes the device, queue family and queue from the backend. The colour-attachment format is baked into the pipeline and fixed for the renderer's lifetime; `dispose()` and `initialize()` keep it, and another format needs a new renderer.
    - `registerFontFromFile`/`registerFontFromResources` (each with an optional glyph-range overload) read the font bytes eagerly (`IOException` naming the path, also for data of 100 bytes or less, on which Dear ImGui would fail a JVM-ending assertion; the `registerFont*` Javadoc asks for fonts from trusted sources only, because Dear ImGui's font loader is not hardened against malicious data), are allowed only while not initialized, and return a stable `ImGuiFont` handle. Glyph ranges are validated (`IllegalArgumentException` for no range, no terminating `0`, a missing last code point or a reversed range) and built as unsigned 16-bit code points, so ranges above `U+7FFF` (CJK) work; the font bytes stay in memory for the renderer's lifetime.
    - `initialize()` creates a fresh Dear ImGui context and makes it current, applies the IO configuration (no ini/log files, error-recovery assert and tooltip disabled), replays the registered fonts in registration order (a font Dear ImGui cannot load throws `IllegalStateException` naming its source) and builds the atlas, creates the variant's fresh platform and renderer Impl objects (`ImGuiImplSdl3`/`ImGuiImplGl3`, `ImGuiImplGlfw`/`ImGuiImplGl3`, `ImGuiImplSdl3`/`ImGuiImplGles3`, `ImGuiImplSdl3`/`ImGuiImplSdlGpu3` or `ImGuiImplSdl3` (`initForVulkan`)/`ImGuiImplVulkan`; each kept only after its `init` succeeded, except that a failed `ImGuiImplSdlGpu3.init`, `ImGuiImplGles3.init` or `ImGuiImplVulkan.init` is shut down on the spot because it may already own GPU, GL or Vulkan objects; the SDL3 backend sets three global SDL hints that stay set after `dispose()`, and the GLFW backend replaces GLFW's global monitor callback; the SDL_GPU variant first reads the window's swapchain format and throws `IllegalStateException` when the window is not claimed for the device; the Vulkan variant first throws `IllegalStateException` when the device does not expose Vulkan 1.3 functions, and its `ImGuiImplVulkan.init` uploads the font atlas on the backend's queue and waits for it), and applies the LorisUI style overrides. A failed `initialize()` releases whatever it had set up (`DeferredRelease.runAfterFailure`) and leaves the renderer uninitialized, so it can be retried (a failure caused by a registered font recurs, because fonts cannot be unregistered).
    - `dispose()` releases, in order and running every step even after a failure: makes the context current, waits for the device to go idle (`SDL_WaitForGPUIdle` for SDL_GPU, `vkDeviceWaitIdle` for Vulkan, whose failure throws `IllegalStateException("vkDeviceWaitIdle failed with VkResult <n>")`; a no-op for the GL variants), the backend's textures (`unloadTextures()`), the renderer Impl (`ImGuiImplGl3`, `ImGuiImplGles3`, `ImGuiImplSdlGpu3` or `ImGuiImplVulkan`), the platform Impl (`ImGuiImplSdl3` or `ImGuiImplGlfw`), the context; then, even after a failure, it unbinds the font handles and drops the variant's Impl references (`clearBackends`). It is a no-op when not initialized, and the renderer can be initialized again afterwards (fonts are replayed, handles stay valid).
    - A private `rendering` flag (read through the package-private `isRendering()`) covers each `render` call: `initialize()`, `dispose()` and a re-entrant `render` throw `IllegalStateException` while a frame is open, before any state change. Hosts therefore defer teardown requested from inside a frame (see Screen Lifecycle).
    - Every entry point makes the renderer's context current and records its pointer in `ImGuiState.currentContextPtr`; the renderer leaves its context current afterwards, so an application with its own Dear ImGui context must make that context current again. Only one renderer may be in use at a time.
    - The variants' `render` methods take the screen size in **logical window coordinates**: `SDL_GetWindowSize` for the SDL variants, `glfwGetWindowSize` for the GLFW variant (on Windows and X11 GLFW measures windows in pixels, so the UI is not scaled up on HiDPI monitors); Dear ImGui's platform backend applies the framebuffer scale. `ImGuiSdlGl3Renderer`, `ImGuiGlfwGl3Renderer` and `ImGuiSdlGles3Renderer` have `render(screen, w, h, resolver)` and draw into the current OpenGL or OpenGL ES framebuffer. `ImGuiSdlGpuRenderer` has `render(screen, w, h, resolver, commandBuffer, targetTexture)`: a `0` command buffer throws `IllegalArgumentException` before any state check; a `0` target builds the frame but draws nothing; otherwise it runs `prepareDrawData` outside any pass, then draws in its own `LOADOP_LOAD`/`STOREOP_STORE` render pass on the application's command buffer, which the application has cleared before and submits after the call. `ImGuiSdlVulkanRenderer` has `render(screen, w, h, resolver, commandBuffer, targetImageView)`: before any state check it throws `NullPointerException` for a `null` `VkCommandBuffer`, then `IllegalArgumentException` for a command buffer of another device than the backend's. No render pass or dynamic rendering instance may be active on the command buffer, because the renderer records a barrier and a rendering instance of its own; the application ends the one it cleared the image with before the call. It records nothing when the target view is `0`, when `skipFrameDraw()` was called during the frame, when the framebuffer is empty or when there are no draw lists; otherwise it records one global colour-attachment write-after-write barrier and draws in its own `vkCmdBeginRendering` (`LOAD`/`STORE`, dynamic rendering) on the application's image view, which must be in `COLOR_ATTACHMENT_OPTIMAL`, have the format given at construction and be at least the window's pixel size. The render area is the draw data's framebuffer size (`SDL_GetWindowSizeInPixels`), since `render` has no extent parameter. It keeps one host-visible vertex/index buffer pair per frame in flight and moves to the next only on a frame that records draws, so the application keeps at most `framesInFlight` frames in flight. The public `skipFrameDraw()` (`IllegalStateException` when no frame is being rendered, idempotent within the frame, cleared at the start of every frame) makes the current frame record nothing, so the renderer may be disposed as soon as `render` returns, before the application submits. The frame is always closed; if the screen threw, its exception propagates and a frame-close failure is added to it as suppressed.
    - Input: `processSdlEvent(long)` on the four SDL variants; seven `processGlfw*` methods (window focus, cursor enter, cursor position, mouse button, scroll, key, char) on the GLFW variant, which installs no window callbacks itself. Each throws `IllegalStateException` before `initialize()`.
    - Input-capture queries for hosts: `wantsMouseInput()`, `wantsKeyboardInput()`, `wantsTextInput()` and `isHoveringScrollablePanel()`, each describing the most recently rendered frame and returning `false` while not initialized.
    - Dear ImGui UI state (selected tabs, scroll positions, open popups, keyboard focus) starts fresh after `dispose()` + `initialize()`; state held by LorisUI components and their bindings is unaffected.
  - `ImGuiFont.java`: final; the ImGui implementation of `Font`, in the `imgui` package so `ImGuiRenderer` can bind it through package-private members. Instances are created only by the renderer's registration methods; there are no static loaders. A handle keeps the font bytes and built glyph ranges for replay (imgui-java passes the glyph-range pointer from a JNI critical array, so keeping the array reachable does not guarantee Dear ImGui a stable address; a known binding limitation), is re-bound on each `initialize()`, and `useFont(Runnable)` throws `IllegalStateException` (without running the code) while its renderer is not initialized or another renderer's context is current.
  - `backend/ImGuiBackend.java`: implements `Backend` and `RendererProvider`; protected constructor that fills the registries `Map<Class<? extends Component>, Renderer<?>>` and `Map<Class<? extends Style>, StyleApplier<?>>` with the built-ins.
    - Registration: `public final registerRenderer(Class, Renderer)` and `registerStyleApplier(Class, StyleApplier)` replace any existing mapping (built-ins included), reject null arguments (`NullPointerException`) and interface classes (`IllegalArgumentException`, because lookup walks only the superclass chain). `getRenderer`/`getStyleApplier` are `final`: they walk up the superclass chain and throw `IllegalStateException` when nothing matches.
    - Textures: a per-instance cache keyed by path and the three masks, with keys normalized to class-path style (a leading `/` is an alias of the bare path). `public final loadTexture(...)` (two overloads, implementing the `RendererProvider` methods) creates a texture on a miss through `protected abstract createTexture(normalizedPath, maskedR, maskedG, maskedB)`; failed loads are not cached. `public final unloadTextures()` calls `protected abstract deleteTexture(TextureData)` once per distinct texture, always empties the cache (first failure rethrown, later ones suppressed), and throws `IllegalStateException` while the backend is drawing (`render` sets a private `drawing` flag). The concrete `renderTexture(long id, ...)` maps `ImageMode` variants to ImGui draw calls with an exhaustive pattern `switch`; `Repeat` is drawn as a grid of `ImGui.image` tiles placed with `sameLine` (spans from `TextureTiling`, partial UVs on edge tiles), like the *Resize modes, so it does not depend on the texture's wrap mode. The class is abstract with a protected constructor, and all four concrete backends are final: `ImGuiOpenGlBackend` pairs with the two GL3 renderers, `ImGuiOpenGlEsBackend` with `ImGuiSdlGles3Renderer`, `ImGuiSdlGpuBackend` with `ImGuiSdlGpuRenderer` and `ImGuiVulkanBackend` with `ImGuiSdlVulkanRenderer`.
  - `backend/TextureData.java`: the `TextureData(long id, int width, int height)` record returned by `RendererProvider.loadTexture`; `id` is an opaque, backend-specific handle (an OpenGL or OpenGL ES texture name, an `SDL_GPUTexture*` or a `VkDescriptorSet`)
  - `backend/ImGuiOpenGlBackend.java`: final; `createTexture` decodes with `DecodedImage` first (a missing image is an `IOException` before any GL call), then saves the active unit's texture binding, the four unpack parameters (`ALIGNMENT`, `ROW_LENGTH`, `SKIP_PIXELS`, `SKIP_ROWS`) and the pixel-unpack buffer binding, uploads a `GL_SRGB_ALPHA` texture with `GL_CLAMP_TO_EDGE` wrapping, and restores the saved state in `finally`, so engines with a GL state cache (jME) stay consistent; `deleteTexture` calls `glDeleteTextures`
  - `backend/ImGuiOpenGlEsBackend.java`: final; the same shape with `GLES30` calls, uploading `GL_SRGB8_ALPHA8` with `GL_RGBA`/`GL_UNSIGNED_BYTE` (OpenGL ES 3.0 rejects the unsized `GL_SRGB_ALPHA`), `LINEAR` filtering and `GL_CLAMP_TO_EDGE`, and restoring the same state; `deleteTexture` calls `glDeleteTextures`
  - `backend/ImGuiSdlGpuBackend.java`: final; holds the SDL_GPU device (`ImGuiSdlGpuBackend(long gpuDevice)`, `IllegalArgumentException` for `0`, no native calls; `getGpuDevice()`). `createTexture` decodes with `DecodedImage` and uploads an `R8G8B8A8_UNORM_SRGB` texture through a transfer buffer and a copy pass on its own command buffer, submitted at once (so a load needs no frame command buffer, and the upload executes before the frame's buffer); any SDL failure throws `IllegalStateException` naming the resource and `SDL_GetError()` after releasing what it created. `deleteTexture` calls `SDL_ReleaseGPUTexture`
  - `backend/ImGuiVulkanBackend.java`: final; `ImGuiVulkanBackend(VkDevice, int queueFamilyIndex, VkQueue)` checks a negative family first (`IllegalArgumentException`), then a null device or queue (`NullPointerException`), then a queue of another device (`IllegalArgumentException`), makes no Vulkan calls and offers `getDevice()`, `getQueueFamilyIndex()` and `getQueue()`. The queue must be the graphics-capable queue on which the application submits its frames (documented, not checked). `createTexture` decodes first, creates the shared sampler and descriptor-set layout lazily with the first texture, and uploads an `R8G8B8A8_SRGB` image synchronously through `VulkanTextures`; each texture owns its image, device-local memory, view and a one-set descriptor pool, and the `VkDescriptorSet` is the texture id. `deleteTexture` runs `vkQueueWaitIdle`, destroys the texture and, with the last live texture, the shared sampler and layout, through `DeferredRelease.runAll`. Uploads submit to the application's queue on the UI thread, so other threads that submit to that queue must synchronize with LorisUI calls, and a texture must not be unloaded while an unsubmitted command buffer uses it
  - `backend/impl/DecodedImage.java`: internal, `AutoCloseable`; reads a class-path resource (`IOException` naming a missing path), decodes it with STB to RGBA8 and applies the masks; shared by all four texture backends
  - `backend/impl/TextureMasking.java`: the pure pixel-masking loop used by `DecodedImage`
  - `backend/impl/TextureTiling.java`: the pure `spans(length, tileLength)` function behind the Repeat tile grid
  - `renderer/Renderer.java`: abstract per-component renderer base (explicit protected constructor); no texture state of its own
  - `renderer/RendererProvider.java`: renderer and style-applier lookup plus `loadTexture(path)`, `loadTexture(path, maskedR, maskedG, maskedB)` and `renderTexture(long id, ...)`; container renderers use it for their children and every renderer uses it for images
  - `renderer/impl/*Renderer.java`: one renderer per component type, all created with no-argument constructors
  - `renderer/impl/ButtonInputTracker.java`: package-private, final and native-free (plain ints and booleans through `update`, no imgui-java types); the press identity and hover start of buttons, keyed by the ImGui ID that `PanelRenderer` takes before `begin`/`beginChild`. A button clicks only when the press and the release land on it; the innermost button hovered at press time wins; a recorded press is forgotten on a new press, after its click, after a frame with a release and on a frame gap. `Button.hover()` runs once per transition to hovered (a button not drawn in the previous frame counts as not hovered), and a held press keeps its button hovered; all state is updated before `hover()`, then `click()`, run. `PanelRenderer` owns it as an instance field, so the state is per backend
  - `renderer/style/StyleApplier.java` and `renderer/style/impl/*StyleApplier.java`: one applier per style type, which push and pop ImGui style vars and colors
  - `impl/ImGuiState.java`: internal, final; global state shared by the renderer, renderers and fonts (`hoveringScrollableWindow`, read by hosts only through `ImGuiRenderer.isHoveringScrollablePanel()`, and `currentContextPtr`, compared by `ImGuiFont.useFont` without a per-frame allocation)
  - `impl/ClassPathResources.java`: internal; opens class-path resources through the class loader, with a leading `/` optional (used by the renderer's font registration and `DecodedImage`)
- **Toolkit dependency**: imgui-java is a runtime dependency only (`compileOnly` plus `runtimeOnly` `[1.92.7.1,1.93)`); no ImGui type appears in an exported signature, so it is not part of the module's compile-time API. `lwjgl-stb` is an `implementation` dependency (runtime scope for consumers). `lwjgl-sdl` is `compileOnly`, for the SDL_GPU calls; at runtime it comes with imgui-java. `lwjgl-opengles` and `lwjgl-vulkan` are `compileOnly` with no runtime scope: jME supplies the OpenGL ES binding for its ANGLE renderer, and a Vulkan application supplies the Vulkan binding. Vulkan types appear in the exported signatures of `ImGuiVulkanBackend` and `ImGuiSdlVulkanRenderer`, which only Vulkan applications use. The module depends on `loris-ui-imgui-gles3` and `loris-ui-imgui-vulkan` with `implementation` (runtime scope for consumers). It contains no MIT-licensed code: its jar and sources jar carry the root `LICENSE` (Apache-2.0) as `META-INF/LICENSE`, and its POM lists only Apache-2.0.

### loris-ui-imgui-vulkan (`imgui-vulkan/`) and loris-ui-imgui-gles3 (`imgui-gles3/`)
- **Purpose**: the Java ports of Dear ImGui's Vulkan and OpenGL ES 3 renderer backends, which `loris-ui-imgui` draws its Vulkan variant (`ImGuiSdlVulkanRenderer`, with `ImGuiVulkanBackend` sharing the texture code) and its GLES3 variant (`ImGuiSdlGles3Renderer`) with. They are internal parts of `loris-ui-imgui` with no API of their own, kept in their own subprojects only so that the MIT-licensed code ships under the MIT License alone, apart from the Apache-2.0 rest of LorisUI.
- **JPMS modules**: `lorisui.imgui.vulkan` (package `com.ivan1pl.lorisui.imgui.vulkan`) and `lorisui.imgui.gles3` (package `com.ivan1pl.lorisui.imgui.gles3`). Each exports its one package only to `lorisui.imgui` (`exports ... to lorisui.imgui;`) and carries `@SuppressWarnings("module")` on the declaration, because javac never finds the export target (`lorisui.imgui` depends on the port module, not the reverse) and `lorisui.imgui.gles3` ends in digits. Both `requires imgui.binding`; `lorisui.imgui.vulkan` also `requires lorisui.api` (for `DeferredRelease`) and `org.lwjgl`. The bindings are a plain `requires static` (`org.lwjgl.vulkan`, `org.lwjgl.opengles`), as in `lorisui.imgui`: the classes load only when their variant runs, and the application resolves the binding (see `lorisui.imgui`). Each module has a module doc comment and its package a `package-info.java`; the `javadoc` task excludes the qualified-exported package, so the generated Javadoc is the module page only.
- **Dependencies**: imgui-java and the LWJGL binding are `compileOnly` (`loris-ui-imgui` declares the imgui-java runtime range); `loris-ui-imgui-vulkan` has `implementation project(':loris-ui-api')`.
- **Licensing**: each subproject has its own MIT `LICENSE` file (Vulkan: Omar Cornut and Mikołaj Nowak; GLES3: Omar Cornut, Ilya "SpaiR" Prymshyts and Mikołaj Nowak) and points `ext.license` at it, so its jar and sources jar carry that file as `META-INF/LICENSE` and its POM lists only the MIT license. The ported source files keep their MIT headers.
- **Tests**: `loris-ui-imgui-vulkan` has `VulkanTexturesTest` (the upload's size guard, reached with `null` Vulkan objects) and `ImGuiImplVulkanShadersTest` (the embedded SPIR-V words), with `lwjgl-vulkan` as `testCompileOnly` + `testRuntimeOnly`; `loris-ui-imgui-gles3` has no tests.
- **Key Files** (`com.ivan1pl.lorisui.imgui.*`):
  - `vulkan/VulkanTextures.java` (Vulkan module): public, final, with an MIT header (derived from Dear ImGui's `imgui_impl_vulkan.cpp`); the Vulkan code shared by `lorisui.imgui`'s `ImGuiVulkanBackend` and this module's `ImGuiImplVulkan`: the sampler (`LINEAR`, `CLAMP_TO_EDGE`) and descriptor-set layout, the synchronous upload (it first rejects pixel data smaller than `width * height * 4` bytes with `IllegalArgumentException`; then a transient command pool and command buffer, a `HOST_COHERENT` staging buffer, layout barriers and a fence waited for, everything destroyed before returning, also on failure; if the fence wait fails after the submit, it waits for the queue to go idle before the objects the copy uses are released), `destroy`, `memoryType` (`IllegalStateException("No suitable Vulkan memory type for <what>")`) and `check(result, vkFunction, what)`, the one place that turns a failed `VkResult` into `IllegalStateException("<vkFunction> failed with VkResult <n> for <what>")`.   - `gles3/ImGuiImplGles3.java` (GLES3 module): public, final, with an MIT header; an OpenGL ES 3.0 port of imgui-java 1.92.7.1's `ImGuiImplGl3` that calls only `org.lwjgl.opengles.GLES30` (LWJGL's GL and GLES bindings share one per-thread function table, so `ImGuiImplGl3` cannot run under ANGLE).   - `vulkan/ImGuiImplVulkan.java` (public, final) and `vulkan/ImGuiImplVulkanShaders.java` (package-private), in the Vulkan module, with MIT headers; a port of the dynamic-rendering path of Dear ImGui 1.92.7's `imgui_impl_vulkan.cpp` to LWJGL's `VK10`/`VK13` (no render-pass path, MSAA, multi-viewport, pipeline cache or user callbacks). `init` builds the pipeline for the colour-attachment format, sets `RendererHasVtxOffset`, uploads the font atlas (`R8G8B8A8_UNORM`) through `VulkanTextures` and allocates one vertex/index buffer slot per frame in flight; `shutdown()` destroys what exists, also after a partial `init`, and is idempotent (it clears its device reference, and a second call returns at once; an instance is never initialized again). `ImGuiImplVulkanShaders` holds the upstream SPIR-V verbatim (324 vertex and 193 fragment words)

### loris-ui-jme3 (`jme3/`)
- **Purpose**: integrates the ImGui backend into jMonkeyEngine 3.

It has JUnit tests (`ImGuiJmeGraphicsApiTest`), which run without jME on the test classpath.
- **Key Files**:
  - `ImGuiJmeGraphicsApi.java`: package-private enum (`OPENGL`, `OPENGL_ES`), the pure seam behind the renderer choice. `forRenderer(String)` maps `AppSettings.ANGLE_GLES3` (`"ANGLE_GLES3"`, jME 3.10's default) to `OPENGL_ES` and any value starting with `"LWJGL-OpenGL"` (every `AppSettings.LWJGL_OPENGL*` constant; jME rejects the versions it does not support) to `OPENGL`; anything else, including `null`, throws `IllegalStateException` naming the value and the supported renderers. A private static factory builds the pair with an exhaustive `switch` expression and returns a private record that also carries the variant's `render` (captured as a private functional interface, because the variants share no `render` method) and the SDL event listener for the variant's `processSdlEvent`. The constructor checks a null context, a null viewport, the `LwjglWindow` cast (`ClassCastException`) and an unsupported renderer (`IllegalStateException`), in that order, before anything is created; the public API is unchanged. It also owns a `ScreenManager` and a `ResourceBundleKeyResolver`, and delegates screens (`addScreen`, `setCurrentScreen`), resource bundles (`setResourceBundle`), fonts (`registerFont*`, returning `Font`) and `registerRenderer`/`registerStyleApplier` to them. The constructor has no Dear ImGui side effects. Each frame, `postQueue` reads the window size in logical window coordinates with `SDL_GetWindowSize` (an `IllegalStateException` with the SDL error if that fails) and passes it to the renderer; jME's camera and `reshape` sizes are not used. The display's viewport must therefore render to the window; offscreen viewports (render-to-texture, or a `FilterPostProcessor` on the same viewport) are documented as unsupported, as are jME's emulated display-scale modes (an `AppSettings` display-scale mode above 1). The sRGB framebuffer that the sRGB textures need comes from jME's gamma correction, which is on by default, for both renderers. The display is re-attachable; see Screen Lifecycle.
  - `ImGuiInputSystem.java`: package-private, final; a jME `RawInputListener` that marks mouse and key events consumed using only the input-capture queries of `ImGuiRenderer`, so it works with either variant. jme3 has no `imgui.*` imports.

## Data Flow

**Setup**
1. The host app creates a display (`ImGuiJmeDisplay(context, inputManager, guiViewPort)`, `ImGuiLwjglSdlGl3Display(sdlWindow)`, `ImGuiLwjglGlfwGl3Display(glfwWindow)`, `ImGuiLwjglSdlGpuDisplay(sdlWindow, gpuDevice)` or `ImGuiLwjglSdlVulkanDisplay(sdlWindow, device, queueFamilyIndex, queue, colorAttachmentFormat, framesInFlight)`), registers fonts, custom renderers and style appliers and resource bundles, adds `LorisScreen`s and selects the current screen. Nothing native happens yet; the jME display has already chosen its GL3 or GLES3 pair from jME's renderer setting. The GLFW application also sets its own input callbacks; the SDL_GPU application creates the device, claims the window for it and sets an `SDR_LINEAR` swapchain; the Vulkan application loads one Vulkan library for SDL and LWJGL, creates the window with `SDL_WINDOW_VULKAN`, an instance and device for Vulkan 1.3 with `dynamicRendering`, and an sRGB swapchain with its per-frame resources.
2. The display is initialized: jME calls `initialize` lazily, on the first frame (or window resize, through `RenderManager.notifyReshape`) after the display is added to a viewport; the LWJGL application calls `initialize()` itself. The renderer creates its context, replays the fonts and sets up its variant's platform and renderer Impl objects (the GLES3 port creates its GL objects eagerly here, and the Vulkan port builds its pipeline and uploads the font atlas on the queue); the jME display then registers its input listeners, and the GLFW display gives the application's monitor callback back and chains its seven input callbacks. Finally `ScreenManager.activate()` fires `onStartScreen()` on the current screen.

**Per frame** (jME `postQueue`, LWJGL `render`):
1. The host passes the screen size in logical window coordinates: the jME display queries `SDL_GetWindowSize` each frame, and the LWJGL application passes the size to the display's `render` (`SDL_GetWindowSize` for the SDL displays, `glfwGetWindowSize` for the GLFW display). The SDL_GPU application first acquires a command buffer and the swapchain texture and clears the texture in its own pass, then passes both to `render(width, height, commandBuffer, targetTexture)`. The Vulkan application recreates the swapchain if its desired extent changed or it is out of date, waits on the frame slot's fence, acquires an image, begins the slot's command buffer, transitions the image to `COLOR_ATTACHMENT_OPTIMAL` and clears it (synchronized in the colour-attachment-output stage), then passes the command buffer and the image view to `render(width, height, commandBuffer, targetImageView)`, or `0` as the view while the swapchain extent is smaller than `SDL_GetWindowSizeInPixels`. The renderer variant's `render` makes its context current and starts an ImGui frame.
2. `LorisScreen.render(backend, w, h, resolver)`:
   - If the previous `layout()` call threw or returned `null`, the failure is rethrown once as an `IllegalStateException` (cause = original failure) and nothing is rendered in that call; later frames render the last successful layout. Hosts should treat it as fatal.
   - If the layout was invalidated (`setLayoutNeedsUpdate(true)`, callable from any thread; the update flag is an `AtomicBoolean`), `layout()` is scheduled on the shared single-thread daemon layout worker (`lorisui-layout`), which is created lazily and stopped by `LorisScreen.shutdownLayoutUpdates()`. The new `List<Component>` is published through a `volatile` field and replaces `content` asynchronously; in the meantime the previous content keeps rendering (an empty list before the first layout).
   - Calls `backend.render(w, h, content, resolver)`.
3. `ImGuiBackend.render` looks up the `Renderer` for each component, and each renderer emits ImGui calls. Containers (Panel, TabbedPanel, Popup) recurse through `RendererProvider`, passing the screen size unchanged, so size and content functions receive the screen's width and height at every nesting level, not the parent's size, and so do the position functions of top-level panels and popups (a nested panel is placed by its parent's layout; `TabbedPanel` tab-label functions, called once at build, receive the tab button's size). Styles are applied through `StyleApplier`s. Text keys are resolved through `BundleKeyResolver`. Images are loaded or fetched from the backend's cache through `RendererProvider.loadTexture(...)` and drawn with `RendererProvider.renderTexture(...)` according to their `ImageMode` (`Repeat` as a tile grid). On SDL_GPU, a texture loaded during the build is uploaded with its own command buffer, submitted at once, so it executes before the frame's buffer; on Vulkan, it is uploaded with its own command buffer submitted to the application's queue and waited for. The GL backends restore the texture binding and unpack state they change, so jME's GL state cache stays valid when an image loads mid-frame. A missing or unreadable image (`Image` or panel `Background`) makes the renderer throw a `RuntimeException` wrapping the `IOException`; failures are not cached, so the screen's render fails again on every draw.
4. ImGui draw data is rendered by the variant: the GL3 variants draw into the current OpenGL framebuffer and the GLES3 variant into the current OpenGL ES framebuffer (restoring the GL state it touched), and the application (or jME) swaps afterwards; the SDL_GPU variant runs `prepareDrawData` outside any pass and then draws in its own `LOADOP_LOAD`/`STOREOP_STORE` pass into the target texture on the application's command buffer (nothing when the target is `0`), and the application submits the buffer afterwards; the Vulkan variant records a colour-attachment barrier and its own `LOAD`/`STORE` dynamic rendering into the image view on the application's command buffer (nothing when the view is `0`, when `skipFrameDraw()` was called, or when the framebuffer is empty), and the application transitions the image for presenting, ends, submits (resetting the buffer instead if `render` threw) and presents. The renderer ends the ImGui frame even when `LorisScreen.render` throws; the screen's exception propagates, with any frame-close failure suppressed.

**Input**: SDL events reach ImGui IO through the SDL variants' `processSdlEvent`. In jME, an SDL event listener (bound to the chosen variant at construction) forwards them, and in parallel `ImGuiInputSystem` marks jME raw input events consumed when `wantsMouseInput()`/`wantsKeyboardInput()` report that the UI wants them; mouse-wheel events are consumed only while `isHoveringScrollablePanel()`. With the three SDL displays the application passes each event to `processEvent`, which forwards it and applies the same rule to its return value. The GLFW display's chained callbacks forward each event to the matching `ImGuiGlfwGl3Renderer.processGlfw*` method and call the application's previous callback only when the same rule says the UI does not consume it. Component callbacks (for example button actions and hover actions) run during rendering on the host's UI thread.

**Teardown**: removal (jME `cleanup`) or `close()` (LWJGL) → `ScreenManager.beginDeactivation()` → `DeferredRelease.request()`, deferred to the end of the outermost operation if requested during a frame, a screen switch or a hook → `ScreenManager.deactivate()` (`onEndScreen`) → LWJGL host input released (SDL text input stopped, or the GLFW callbacks restored and freed) → renderer `dispose()` (context current → device idle (`SDL_WaitForGPUIdle` for SDL_GPU, `vkDeviceWaitIdle` for Vulkan) → textures (for Vulkan, each texture waits for the queue to go idle and is destroyed, and the shared sampler and descriptor-set layout go with the last one) → renderer Impl (Gl3, Gles3, SdlGpu3 or Vulkan) → platform Impl (Sdl3 or Glfw) → context → font handles unbound) → `LorisScreen.shutdownLayoutUpdates()`. Each step runs even when an earlier one fails (`DeferredRelease.runAll`); the first failure propagates and later ones are suppressed. A Vulkan display closed during its own frame first calls `skipFrameDraw()`, so that frame records no LorisUI commands and the deferred release can destroy the Vulkan objects as soon as `render` returns, before the application submits. The SDL_GPU application then waits for the GPU to go idle, releases the window from the device and destroys the device, the window and SDL; the Vulkan application waits for the device to go idle and destroys its frame resources, swapchain, device, surface and instance, then the window; the GLFW application frees its own callbacks after `close()`.

## Screen Lifecycle
All display calls and screen hooks run on the host's UI thread (the jME render thread, or the thread that owns the window and its GL context, GPU device or Vulkan device; for GLFW, the main thread). The Vulkan display and backend submit uploads to the application's queue from that thread, so an application that submits to the same queue from other threads serializes those submissions with LorisUI calls. No display implements `BundleKeyResolver`; each passes its internal `ResourceBundleKeyResolver` to the renderer, and applications that need key resolution create their own resolver.

**Shared rules (`ScreenManager`)**:
- A screen receives `onEndScreen()` only if its `onStartScreen()` returned normally, and at most once per start; a screen whose `onStartScreen()` threw counts as not started. Hook exceptions propagate out of the method that fired them.
- `addScreen(name, screen)`: `NullPointerException` for null arguments, `IllegalStateException` for a name that is already registered. Fires no hooks and is allowed from inside hooks.
- `setCurrentScreen(name)`: `IllegalStateException` from inside a hook, then `NullPointerException` for null and `IllegalStateException` for an unknown name, all before any state change; switching to the current screen does nothing. While the display is not initialized it only records the name. While initialized the switch is immediate: the new screen becomes current, then `onEndScreen()` fires on the old screen and `onStartScreen()` on the new one, during the call; the new screen is drawn from the next frame. The switch always completes: if the old screen's `onEndScreen()` throws, the new screen is still started, then the end failure propagates (a different start failure is added to it as suppressed). It may be called from a component callback, in which case the old screen finishes drawing the current frame.
- **Re-entrancy guard**: `setCurrentScreen`, `activate()` and `deactivate()` called from inside `onStartScreen()`/`onEndScreen()` throw `IllegalStateException` before changing state. Screens switch later instead, for example from a component callback.
- **Two-phase deactivation**: `beginDeactivation()` makes the manager inactive without a hook (allowed inside hooks; a switch or activation already in progress still completes). From then on `setCurrentScreen` only records the choice, and `deactivate()` fires `onEndScreen()` on the screen started before, even if another screen has been selected since; it also ends a started screen while the manager is already inactive. `activate()` throws `IllegalStateException` while a begun deactivation has not been completed with `deactivate()`.

**Deferred teardown (all hosts)**: each display runs its operations that can call application code (rendering a frame, `setCurrentScreen`, and the activate step of `initialize`) through its `DeferredRelease`. A teardown request stops the display at once (the jME display removes its input listeners and `isInitialized()` returns `false`; an LWJGL display is closed, the SDL displays' `processEvent` returns `false` and the GLFW display passes every event to the application's callbacks), calls `ScreenManager.beginDeactivation()` and then `DeferredRelease.request()`. If an operation is running (a component callback, such as the examples' "Hide UI" button, or a screen hook), the release runs after the outermost one, once the frame has closed or the hook has returned. The renderer is therefore never disposed inside a frame and `deactivate()` never runs inside a hook. While the release is pending, `setCurrentScreen` fires no hooks and only records the choice; the recorded screen becomes current and, on the re-attachable jME display, starts on the next attach. Release failures propagate from that operation, or are added as suppressed to its exception if it is already throwing.

**jME host (`ImGuiJmeDisplay`)**:
- `initialize`: throws `IllegalStateException` if an earlier initialization failed, if the display is already initialized or its deferred release has not completed, or if no current screen is set, all before any side effect. If setting up the renderer or registering the listeners fails, it marks the display failed, removes the listeners, disposes the renderer and rethrows, so jME's per-frame retry fails fast; no hooks fire and the display is permanently unusable (registration also throws). Otherwise it ends with `ScreenManager.activate()` (`onStartScreen()`); a throwing `onStartScreen()` propagates and the display stays initialized.
- `postQueue` returns early when the display is not initialized, because jME iterates a snapshot of the viewport's processors and can still call a display removed earlier in the same frame.
- `cleanup`: jME calls it when the display is removed from its viewport (`ViewPort.removeProcessor`/`clearProcessors`). A no-op unless initialized. Otherwise it tears down (deferred if an operation run through its `DeferredRelease` is in progress).
- **Re-attach**: a cleaned-up display can be added to a viewport again. It re-creates the context, replays the fonts (the `Font` handles stay valid) and starts the current screen again; screens, bundles, renderers and style appliers stay registered, and fonts, renderers and style appliers can be registered again between removal and re-attach. Dear ImGui UI state starts fresh. Re-adding the display in the same callback that removed it is safe, because jME initializes it on a later frame, after the deferred release.
- Only one display may be attached at a time.
- **Application exit**: jME does not call `cleanup` on exit. Applications that want `onEndScreen()` and the native release at exit remove the display themselves; `LorisJme3Example` overrides `destroy()` and calls `guiViewPort.removeProcessor(imGuiJmeDisplay)` (only if attached, since `removeProcessor` calls `cleanup` even for a processor that is not attached) before `super.destroy()`.

**LWJGL host (`ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay`, `ImGuiLwjglSdlVulkanDisplay`)**: the rules below come from the shared base and apply to all four displays unless noted.
- `initialize()`: `IllegalStateException` if closed, already initialized, or no current screen is set, all before side effects. If the renderer fails to initialize, the exception propagates, the renderer has released what it set up, and the display stays uninitialized and can be retried (after a failure caused by a registered font, create a new display instead). Then it marks itself initialized and calls `ScreenManager.activate()`; a throwing `onStartScreen()` propagates and the display stays initialized.
- `render` throws `IllegalStateException` when not initialized or closed; the SDL displays' `processEvent` returns `false` then. The SDL_GPU display's `render` checks for a `0` command buffer first (`IllegalArgumentException`); the Vulkan display's `render` checks its own state first and then lets the renderer check the command buffer (`NullPointerException` for `null`, then `IllegalArgumentException` for another device).
- SDL text input (the three SDL displays, through `ImGuiLwjglSdlInput`): after each frame that returns normally (and only while still initialized), `render` compares the renderer's `wantsTextInput()` with the state it last applied and calls `SDL_StartTextInput`/`SDL_StopTextInput` for the window, because imgui-java's SDL3 backend does not port Dear ImGui's `Platform_SetImeDataFn` and SDL3 delivers no `SDL_EVENT_TEXT_INPUT` until text input is started. A refused start is not recorded, so the next frame retries; release stops text input if it was started (after `onEndScreen`, before the renderer's `dispose()`). The jME host needs no such step, as jME's `SdlKeyInput` starts text input itself, and neither does the GLFW display, as GLFW always delivers characters.
- `close()`: idempotent and **final** (`AutoCloseable` semantics): the display is marked closed at once, so later `register*`, `initialize` and `render` throw, while `addScreen`, `setCurrentScreen` and `setResourceBundle` only record. If initialized, it releases immediately, or deferred when called during a frame, a screen switch or a hook. To show UI again, the application creates a new display. Closing before `initialize()` only marks the display closed.
- GLFW display only: `close()` called during one of its GLFW callback dispatches (from the application's chained callback, or from a hook or component code that callback runs) throws `IllegalStateException` before any state change, because the release would destroy cursors and free the executing callback stub inside a GLFW callback; the application requests the close there and calls `close()` after `glfwPollEvents` returns. A failure thrown during a dispatch is kept, later events reach neither the UI nor the application, and the next `render()` (before drawing) or `close()` (after closing, with a release failure suppressed) rethrows it once. Closing from a component callback during `render()` ("Hide UI") is deferred as usual. `render()` must not be called from a GLFW callback.
- Vulkan display only: `close()` during one of its frames (from a component callback or a screen hook; the display tracks a frame-in-progress flag around the renderer's `render`) calls the renderer's `skipFrameDraw()` before closing, so that frame records no LorisUI commands and the deferred release (`vkDeviceWaitIdle`, then destroying the Vulkan objects) runs when `render` returns; the application submits the command buffer as usual. Closing between `render` and that frame's submit is unsupported, because the recorded commands use the display's resources. Its `initialize()` fails with `IllegalStateException` when the device does not expose Vulkan 1.3 functions.
- Only one display may be initialized at a time.

## Extension Points
- **New built-in component**: add a class to `api/component` (with a Builder), add a renderer in `imgui/renderer/impl`, and register it in the `ImGuiBackend` constructor.
- **New built-in style**: add a class to `api/component/style`, add an applier in `imgui/renderer/style/impl`, and register it in the `ImGuiBackend` constructor.
- **Custom components or styles (library users)**: extend `Renderer`/`StyleApplier` and register them with `registerRenderer`/`registerStyleApplier`, either on an `ImGuiBackend` or on a display (`ImGuiJmeDisplay`, `ImGuiLwjglSdlGl3Display`, `ImGuiLwjglGlfwGl3Display`, `ImGuiLwjglSdlGpuDisplay`, `ImGuiLwjglSdlVulkanDisplay`) before it is initialized. A registration replaces any existing mapping, including a built-in one, and subclasses without their own mapping use the nearest registered ancestor. Renderers load and draw textures through the `RendererProvider` they receive. A custom renderer calls Dear ImGui directly, so its code adds imgui-java to its own build and, on the module path, `requires imgui.binding`. The displays keep their backend private; registration is the only customization path, which also covers the former "custom backend in the jME host" need.
- **Custom texture backend / another graphics API**: a custom `ImGuiBackend` subclass (implementing `createTexture`/`deleteTexture`, for example to load textures differently on OpenGL) pairs only with the GL3 or GLES3 renderers (`ImGuiSdlGl3Renderer`, `ImGuiGlfwGl3Renderer`, `ImGuiSdlGles3Renderer`), because its textures must be texture names of the renderer's OpenGL or OpenGL ES context; the SDL_GPU and Vulkan renderers take their own typed backends. All four concrete backends are final, and each bundled display uses its own backend (`ImGuiOpenGlBackend` or `ImGuiOpenGlEsBackend` for jME, matching jME's renderer; `ImGuiOpenGlBackend` for the two GL3 displays; `ImGuiSdlGpuBackend` for the SDL_GPU display; `ImGuiVulkanBackend` for the Vulkan display). A new graphics API needs a new variant of the sealed `ImGuiRenderer` inside `lorisui.imgui`, so it is not an extension point.
- **New backend**: implement `Backend.render` (and its own registry mechanism) in a new module that depends only on `loris-ui-api`.
- **New host**: a module that depends only on `loris-ui-imgui`. Wrap an `ImGuiRenderer` variant and its matching backend (`ImGuiOpenGlBackend` for the GL3 variants, `ImGuiOpenGlEsBackend` for `ImGuiSdlGles3Renderer`, `ImGuiSdlGpuBackend` for `ImGuiSdlGpuRenderer`, `ImGuiVulkanBackend` for `ImGuiSdlVulkanRenderer`) in the target's render hook, keep screens in a `ScreenManager`, resolve text with a `ResourceBundleKeyResolver`, use the renderer's input-capture queries for input routing (starting SDL text input on `wantsTextInput()` unless the framework does; with the GLFW variant, forwarding the window's callbacks and restoring the global monitor callback after `initialize()`), provide an sRGB framebuffer, and defer teardown requested during a frame or hook with a `DeferredRelease` plus `ScreenManager.beginDeactivation()`, as the bundled hosts do (a Vulkan host also calls `skipFrameDraw()` when it is closed during a frame).

## Known Architectural Concerns
- **Emulated jME display-scale modes (> 1) unsupported**: with an `AppSettings` display-scale mode above 1, jME renders the GUI into a framebuffer sized framebuffer × mode, while Dear ImGui sizes its viewport from the logical window size times the framebuffer scale, so the UI covers only part of the window. The jME Javadoc documents this; there is no runtime detection.
- **jME viewport must render to the window**: the jME display sizes the UI from the window's logical size, so its viewport must render to the window. Offscreen viewports (render-to-texture, or a `FilterPostProcessor` on the same viewport) are unsupported; the jME Javadoc documents this, and there is no runtime detection.
- **Dear ImGui asserts end the JVM**: imgui-java calls `System.exit(1)` after any failed Dear ImGui assertion, even with a custom `ImGui.setAssertCallback` handler, which can only log or pick the exit code. The renderer disables error-recovery asserts so frame exceptions reach the host, and its in-frame guard plus the hosts' deferred teardown remove the known `DestroyContext` trigger (a locked font atlas); other asserts still terminate. This is documented in the `ImGuiRenderer` and `lorisui.imgui` Javadoc. An SDL_GPU validation failure in debug mode can also end the process.
- **Native lifecycle verified manually only**: context creation and destruction, Impl shutdown, font replay, GL and GLES texture upload and deletion, GPU texture upload and release, the SDL_GPU frame, the GLES draw path under ANGLE, the Vulkan pipeline, uploads, synchronization, swapchain recreation and teardown, native GLFW callback chaining and re-attach cannot be unit-tested (no native context or `VkDevice` in tests), and are checked by hand with the six examples, one at a time or all at once with `runAllExamples`. Only the native-free paths are unit-tested: the deferred-teardown state machine (`DeferredRelease`, `ScreenManager.beginDeactivation`, and their host composition mirrored in `HostLifecycleCompositionTest`), the gating of the five renderer variants and of `ImGuiSdlGpuBackend` and `ImGuiVulkanBackend`, the GL backends' decode-before-GL order, `ImGuiFont` glyph-range validation, `TextureTiling`, `ButtonInputTracker` (press identity and hover start), `DecodedImage`'s missing-resource path, the SPIR-V words of `ImGuiImplVulkanShaders` and `VulkanTextures`' upload size guard (both in `loris-ui-imgui-vulkan`), the pre-initialize paths of the four LWJGL displays, the GLFW display's dispatch rules (through its package-private `dispatch` seam) and the jME renderer choice (`ImGuiJmeGraphicsApi`); `examples` has no tests. The Vulkan classes can be tested only for the argument checks reachable with `null` Vulkan objects, so the Vulkan backend's, renderer's and display's paths behind a successful construction are an accepted gap covered only by the manual checklist: the display's close-during-frame logic (`skipFrameDraw`, the restored frame flag and the deferred release), its render check order (its own state checks, then the renderer's command-buffer checks), calls before `initialize()`, `close()` and registration after `close()`; the shared base behavior stays covered by the SDL3 + OpenGL 3 tests.
- **UI state on re-attach**: every re-attach creates a new Dear ImGui context, so selected tabs, scroll positions, open popups and keyboard focus reset; LorisUI-held state (bindings, `TabbedPanel`/`ComboBox` model values) is kept.
- **Global SDL hints**: imgui-java's SDL3 backend (all four SDL variants) sets `SDL_HINT_MOUSE_FOCUS_CLICKTHROUGH`, `SDL_HINT_MOUSE_AUTO_CAPTURE` and `SDL_HINT_BORDERLESS_WINDOWED_STYLE` on every `initialize()`; they stay set after `dispose()`.
- **GLFW monitor callback**: Dear ImGui's GLFW backend replaces GLFW's global monitor callback on every `initialize()` and never restores it. `ImGuiLwjglGlfwGl3Display` gives the application's callback back; a host using `ImGuiGlfwGl3Renderer` directly must do so itself.
- **GLFW close and callback failures**: `close()` is rejected inside the GLFW display's callbacks, and must not be called from any other GLFW callback either (such as a window-close callback; not detected), so integrators request the close there and call `close()` after `glfwPollEvents` returns. A failure in a callback dispatch surfaces from the next `render()`/`close()`, and events arriving in between (usually the rest of that poll) reach neither the UI nor the application. Calling `render()` from a GLFW callback the display does not own, such as a window-refresh callback, is unsupported.
- **GLFW HiDPI on Windows and X11**: GLFW measures windows in pixels there (no `GLFW_SCALE_TO_MONITOR`), so the UI is not scaled up on HiDPI monitors. Documented, not fixed.
- **sRGB framebuffer required**: textures are sRGB on every variant (`GL_SRGB_ALPHA` / `GL_SRGB8_ALPHA8` / `R8G8B8A8_UNORM_SRGB` / `R8G8B8A8_SRGB`) and the Dear ImGui font atlas is UNORM, so every host must write through an sRGB framebuffer: `GL_FRAMEBUFFER_SRGB` on an sRGB-capable default framebuffer for the GL3 hosts, jME's gamma correction (on by default) for both jME renderers, the `SDR_LINEAR` swapchain composition for SDL_GPU, and an sRGB swapchain format (such as `B8G8R8A8_SRGB`) for Vulkan. A host without it shows different colors.
- **`SDR_LINEAR` support**: the `SDR_LINEAR` swapchain composition depends on the driver. The SDL_GPU example checks `SDL_WindowSupportsGPUSwapchainComposition` and fails with a clear message; a host that cannot get it sees darker images than the GL path. The swapchain parameters must not change while the renderer is initialized.
- **GPU release before submit**: closing the SDL_GPU display inside a frame releases GPU resources at the end of `render`, before the application submits that frame's command buffer; this relies on SDL_GPU deferring the release of resources already recorded in a command buffer, and is checked by hand ("Hide UI" in the SDL_GPU example, ideally with `-Dlorisui.example.gpuDebug=true`).
- **No Vulkan close between `render` and submit**: Vulkan does not defer destruction, so the Vulkan display handles only a close during its own frame (`skipFrameDraw`, then the release after `render` returns). A `close()`, or a screen hook that closes the display, after `render` has recorded but before the application submits destroys objects the command buffer uses; this is documented as unsupported, not detected.
- **Vulkan render area from SDL**: `render` has no extent parameter, so the renderer draws over the draw data's framebuffer size (`SDL_GetWindowSizeInPixels`, cached by SDL while events are pumped). If the swapchain is smaller, for example while the window shrinks between the event pump and the swapchain recreation, the render area would exceed the image (a validation error); the application passes `targetImageView = 0` on such a frame (the UI updates, nothing is drawn), as the example does. The example recreates the swapchain only when the desired extent changes or after `OUT_OF_DATE`; a `SUBOPTIMAL` result keeps presenting with the current swapchain, so a surface that stays suboptimal does not cause a recreation and a device-idle wait every frame.
- **Vulkan queue requirements and synchronization**: the backend's queue must be graphics-capable (from `queueFamilyIndex`) and must be the queue the application submits its frames on, because uploads, their layout transitions and `deleteTexture`'s `vkQueueWaitIdle` rely on submission order on that one queue; neither is checked. Uploads submit from the UI thread and wait for completion, so applications that submit to the queue from other threads must serialize those submissions with LorisUI calls.
- **Vulkan colour-attachment format fixed per instance**: the format is a constructor argument baked into the pipeline. Rendering into another format needs a new renderer or, because closing is final, a new display with its fonts, renderers, style appliers, bundles and screens registered again. The example keeps its swapchain format across recreations, so this does not arise there.
- **Modular Vulkan applications `requires org.lwjgl.vulkan` themselves**: `lorisui.imgui` and `lorisui.lwjgl` use a plain `requires static org.lwjgl.vulkan` (and `lorisui.imgui` `requires static org.lwjgl.opengles`; the port modules `lorisui.imgui.vulkan` and `lorisui.imgui.gles3` do the same, and no application requires them), so GL-only and jME consumers need no Vulkan binding; a modular jME application on the ANGLE renderer must still have `org.lwjgl.opengles` resolved at runtime (`requires` or `--add-modules`). The cost is a `javac -Xlint:exports` warning about Vulkan types in exported signatures, which the build does not enable; do not add `-Xlint:all` with `-Werror` to `javac` without suppressing `exports` for these modules.
- **Vulkan loader sharing on macOS**: SDL and LWJGL must load the same Vulkan library; the example passes LWJGL's loaded library path to `SDL_Vulkan_LoadLibrary`, which needs a manual check on macOS.
- **MoltenVK and Vulkan 1.3**: Vulkan 1.3 support (dynamic rendering) in the MoltenVK build that ships with LWJGL 3.4.1 is unverified; the example fails with a clear message naming the missing requirement when no suitable device is found, and the renderer's `initialize()` throws when the device does not expose Vulkan 1.3 functions.
- **OpenGL ES 3.0 vertex limit**: the GLES3 port has no base-vertex draw and imgui-java uses 16-bit indices, so a single Dear ImGui window above 65,535 vertices fails a Dear ImGui assertion, which ends the JVM. Accepted and documented in the `ImGuiSdlGles3Renderer` and `lorisui.imgui` Javadoc; typical menus and HUDs stay far below it.
- **ANGLE checked manually only**: the GLES3 draw path under jME's ANGLE renderer (and the ANGLE drivers per platform) is verified only by running `runJme3Example`, side by side with `runJme3Gl3Example` and the LWJGL examples. The ANGLE path depends on the jME 3.10.0-SNAPSHOT in `mavenLocal()`.
- **Unsupported jME renderers rejected**: `ImGuiJmeDisplay`'s constructor throws `IllegalStateException` for any jME renderer other than `ANGLE_GLES3` and `LWJGL-OpenGL*` (for example `JOGL_*` or a `null` renderer), before anything is created.
- **Repeat item count**: a `Repeat` image creates one Dear ImGui item per tile, so a small texture over a large area costs many items. Like the *Resize modes, it assumes it is drawn from the left edge of the current window, which holds for the built-in renderers.
- **Wrap mode**: GL and GLES textures use `GL_CLAMP_TO_EDGE` (and the Vulkan sampler `CLAMP_TO_EDGE`), so sprite cells at a texture border no longer blend with the opposite edge when filtered linearly.
- **Context left current**: the renderer leaves its Dear ImGui context current after every call, so an application that uses its own Dear ImGui context must restore it.
- **One backend per renderer**: `PanelRenderer` keeps the button press and hover state (`ButtonInputTracker`) in its instance, which belongs to one backend, so a backend shared between renderers or Dear ImGui contexts loses button presses and mixes hover state. The `ImGuiBackend` Javadoc and the five renderer variants' `@param backend` require a backend used by one renderer only (re-initializing the same renderer is fine), as the bundled hosts do; it is documented, not enforced, and there is no per-context state.
- **Button input (accepted behaviors)**: the hover check stays `isWindowHovered(ChildWindows)` without `AllowWhenBlockedByActiveItem`, so there is no hover start and no click while another control holds the mouse (a scrollbar, a press in another window, a drag-selection in a text field). A text field that is merely being edited does not block buttons: Dear ImGui lets other widgets hover while the mouse is up (`ActiveIdAllowOverlap`), so hover starts and clicks work as usual. Nested buttons each get their own hover start and only the innermost one clicks, but the outer one may draw its active background on the press frame. A press and a release in the same frame click both nested buttons; this needs Dear ImGui's input trickling (`ConfigInputTrickleEventQueue`, on by default, unchanged by LorisUI) turned off. A disabled button still claims the press, so a disabled inner button swallows its enabled outer button's click, and a press on a disabled button that becomes enabled before the release clicks; a button that becomes enabled while hovered does not run its hover action, while one whose input is re-enabled while hovered does. The click that closes a popup or the ComboBox dropdown does not click the button underneath, as in native Dear ImGui.
- **Global state**: `ImGuiState` holds static flags (`hoveringScrollableWindow`, `currentContextPtr`), and `LorisScreen` shares one static layout worker across screens; only one renderer and one display may be in use at a time. The button press and hover state is not global: it is per backend (`ButtonInputTracker` in `PanelRenderer`).
- **Texture cache**: per backend, cleared as a whole by `unloadTextures()` (and by renderer teardown); there is no per-path eviction while a backend is in use.
- **Missing images**: a texture that fails to load is retried and fails again on every draw instead of failing once.
- **Renderer robustness**: `ImGuiRenderer` disables ImGui's error-recovery assert and tooltip, so state left open by a throwing renderer (windows, IDs, style stacks) is unwound when the frame closes and the original exception propagates to the host; the trade-off is that an imbalance that does not throw is recovered silently instead of failing fast. The input renderers pop their item width in `finally`, the combo box uses `setNextItemWidth`, and the progress bar pops its style in `finally`, but other push/pop pairs (combo style vars, per-item IDs, `beginChild`/`endChild` in the panel and combo renderers) are still not in `try/finally`. `TextInput` and `NumberInput` both use the bare `"##"` ImGui label without a per-component ID, so two inputs in the same window share an ImGui ID.

## Configuration
- Build-time: Gradle `ext` versions in the root `build.gradle`; Checkstyle rules in `config/checkstyle/`; editor settings in `.editorconfig`
- Runtime: done in code through any display (fonts, renderers and style appliers, resource bundles, screens). - i18n: `ResourceBundle`s registered by name (for example `bundles.global`)
- Resources (fonts, textures) are class-path resource names; a leading `/` is optional. On the module path they must be outside any package of a named module, or in a package the application module opens unconditionally.

## Deployment Architecture
LorisUI is a library, so it isn't deployed as a service. It's published as Maven artifacts (`loris-ui-api`, `loris-ui-imgui`, `loris-ui-imgui-gles3`, `loris-ui-imgui-vulkan`, `loris-ui-jme3`, `loris-ui-lwjgl`), each with sources and Javadoc jars and a POM with name, description, url, exactly one license (Apache-2.0, or MIT for the two port artifacts, which `loris-ui-imgui` brings as runtime-scope dependencies), developer and scm, and consumed by desktop game applications. Publishing goes only to the local Maven repository (`./gradlew publishToMavenLocal`); no remote repository is configured, and `examples` is not published. `loris-ui-jme3` does not bring jMonkeyEngine: its consumers declare `jme3-core` and `jme3-lwjgl3` (plus any other jME modules they use) themselves. imgui-java (which brings LWJGL with its SDL, GLFW and OpenGL bindings and natives, the GLFW and SDL natives only for Linux, macOS, macOS arm64 and Windows) is pulled in at runtime; `lwjgl-stb` is an `implementation` dependency of `loris-ui-imgui` (runtime scope for consumers) with natives for Windows, Linux, macOS and macOS arm64. LWJGL's OpenGL ES and Vulkan bindings are not brought: jME supplies the OpenGL ES binding for its ANGLE renderer, and a Vulkan application declares `lwjgl-vulkan` itself (plus its `natives-macos`/`natives-macos-arm64` classifiers for MoltenVK on macOS). Every library jar and sources jar contains `META-INF/LICENSE`: the root Apache-2.0 `LICENSE`, or the port subproject's own MIT `LICENSE` in `loris-ui-imgui-gles3` and `loris-ui-imgui-vulkan`. On JDK 25, applications pass `--enable-native-access` (`ALL-UNNAMED` on the class path, the module names on the module path) to avoid the restricted-method warnings of imgui-java and LWJGL; the examples' run tasks pass `ALL-UNNAMED`. Running the SDL- and GLFW-based examples on macOS may additionally need `-XstartOnFirstThread`, which the run tasks don't pass. Consumer Javadoc states `--enable-native-access` in the `lorisui.imgui`, `lorisui.lwjgl` and jme3 package docs, and `-XstartOnFirstThread` in the LWJGL host's docs.
